# V-3 技術調査 — モック生成と結合テストの選定記録

V-3「モックによる並行開発」を実装するにあたって採用したツールと、その設定・落とし穴の記録。
親設計 P-5「codegen ツールは PoC 内で比較選定し、選定理由を記録して本番判断の入力にする」に対応する。

## 1. モック生成: orval の MSW 出力

### 1.1 なぜ別ツールを足さず orval か

V-1/V-2 で型・api-client を **orval** で生成済み。orval は同じ契約から MSW ハンドラも出せる。
→ 型/クライアント/モックを**単一ツール・単一の契約**から出すことで「型は最新だがモックは古い」を構造的に防げる。別のモック生成器を足すと源泉が二重化する。

### 1.2 設定（実採用値）

```ts
// orval.config.ts
mock: {
  type: "msw",        // setupServer/worker に渡せる http ハンドラ群を生成
  useExamples: true,  // 応答本文を faker 乱数ではなく契約 examples にする
  delay: false,       // 既定の擬似遅延(1秒/件)を無効化(結合テストを速く回す)
}
```

| オプション | 既定 | 採用 | 理由 |
|---|---|---|---|
| `type` | — | `"msw"` | ブラウザ(worker)/node(server)双方で使える。本 PoC は node テストで使用 |
| `useExamples` | `false` | `true` | **モックの源泉を契約 examples に固定**。faker 乱数だと毎回値が変わり期待値を書けない／契約と無関係になる |
| `delay` | `1000`(ms) | `false` | 擬似遅延は UI 体感確認には有用だがテストを無駄に遅くする。結合テストでは切る |

### 1.3 生成物の形（split mode）

`mode: "split"` で client と mock を**ファイル分離**する(採用理由は §1.5):

```text
packages/api-client/src/generated/
├ poc.ts       … 型付き fetch クライアント（msw を import しない＝本番経路は純粋）
├ poc.msw.ts   … MSW ハンドラ（msw に依存。テスト/モック専用の入口）
└ model/       … 型（poc.ts も poc.msw.ts も同じ ./model を import＝型は単一系統）
```

`poc.msw.ts` に生成されるもの:

- `getXxxResponseMock()` … 契約 example をそのまま返す純関数
- `getXxxMockHandler(overrideResponse?, options?)` … `http.get('*/masters/:masterId/meta', ...)` 等
- `getPoCMasterAPIMock()` … 全ハンドラの配列。`setupServer(...getPoCMasterAPIMock())` で一発起動

> `useExamples: true` の効果で、全フィールドが examples で埋まるため **faker のインポートは生成されない**。
> mock 由来の追加依存(`msw`)は `poc.msw.ts` だけに乗り、本番 client(`poc.ts`)には乗らない(実測: `poc.ts` の msw import 数 = 0)。

### 1.4 ハンドラのステータスは 2xx のみ

orval の mock は各オペレーションにつき **代表 1 応答(2xx success)** を生成する。
404/409 等のエラー応答は別ハンドラとしては生成されない。
→ エラー分岐を結合テストする場合は、契約のエラー example を載せた MSW ハンドラを `server.use()` で**上書き**する(本 PoC の異常系テストはこの方式。上書き先もあくまで MSW = BE ではない)。

### 1.5 生成 mock の置き場所（技術的課題と判断）

**課題**: 基本設計 §2.2 は生成物を `api-client/`(生成) と `msw-mocks/`(生成) の**別パッケージ**に分ける。
一方で「generated は契約起点で一元生成」が第一原則。当初 `mode: "single"` + `mock: true` で実装したところ、
**api-client の `poc.ts` に mock が同梱され、本番 client が `msw`(テスト用依存)に依存**してしまった。
これは設計(別パッケージ)とも第一原則(本番経路の純度)とも乖離する。3案を実測で比較した。

| 観点 | 案1: 別パッケージ `msw-mocks/` | **案2: 同パッケージ split（採用）** | 案3: single 同梱 |
|---|---|---|---|
| 本番 client(poc.ts)の msw 依存 | 無し（実測 import 0） | **無し（実測 import 0）** | あり ✗ |
| mock の型 | 自前 `./model` を**再生成（二重）** | 同パッケージの `./model` を import（**単一**） | 単一 |
| 余分な生成物 | 使わない client(poc.ts)も生成 ✗ | 無し | 無し |
| orval プロジェクト数 | 2（契約変更時に両方再生成） | **1** | 1 |
| 設計§2.2 忠実度 | ◎ 別パッケージそのもの | △ ファイル分離どまり | ✗ |

**実測で判明した決定的事実**: orval は **mock 単独生成ができない**(`client: false` 相当が無い)。
このため案1(別パッケージ)は、mock プロジェクトが**型 model 12ファイルと未使用 client を必ず重複生成**する。
`poc.msw.ts` の型 import は自パッケージの `./model` 固定で、api-client の型を再利用させる手段が無い(手で書き換えれば生成物の手書き改変＝ADR-0009 違反)。

**判断: 案2(split)を採用**。理由:

- V-3 が本質的に要求するのは「mock は契約から生成」「本番 client は msw 非依存」の2点。**両方とも案2で実測達成**(`poc.ts` の msw import = 0)。
- 案1の「型の二重生成＋未使用 client」は、むしろ「generated は契約起点で一元生成」の第一原則と相性が悪い(同じ型の生成元が2系統になる)。
- 設計§2.2 の「別パッケージ」は**本番構成**の話。PoC(縮小相似形)では「mock を client と分離生成・client は純粋」を split で示せば原則を実証できる。
- **本番への昇格パス**: 別パッケージ化が要るなら、orval の出力先を分けて `msw-mocks/` へ昇格する(構造は変えず "分ける" だけ)。その時に型重複を避けるなら、mock プロジェクトの型 import を api-client パッケージ参照へ向ける後処理 or orval 機能拡張が要る、という宿題も判明済み。

## 2. インターセプタ: MSW（node）

- `msw/node` の `setupServer` は `@mswjs/interceptors` で `globalThis.fetch` を差し替え、リクエストをハンドラに照合する。
- `onUnhandledRequest: "error"` … 契約に無い通信を即エラーに。「実は本物の BE を叩いていた」を機械的に排除(V-3 の肝)。
- ハンドラ URL が `*/masters/...` と**ワイルドカード origin** なので、どの origin からの相対/絶対 URL でも一致する。

## 3. ランナー: Vitest（node 環境・暫定）

- 既存ツールチェーンが pnpm + TS + ESM。Vitest は Vite ベースで TS/ESM/paths をそのまま解決でき、追加設定が最小。Vite は明示導入していないが Vitest が依存として連れてくる(store に `vite@5`)。
- `environment: "node"` を採用。理由は本 V-3 の結合対象が「app→features→api-client→fetch」の**データ経路**であり、DOM 描画(ui-engine=V-5)は対象外だから。jsdom は入れていない。
- ワークスペース解決: テストは `@poc/api-client/generated/poc.msw`(モック)と `@poc/api-client/generated/poc`(型/client) を package exports 経由で解決(web パッケージが `workspace:*` 依存)。tsconfig paths の別途エイリアスは不要。

### 3.1 ランナー選定は暫定（React/Next 導入時に本決め）

本 PoC はまだ **React も Next.js も未導入**。`services/master/web` は JSX を持たない素の TS 関数(app/features 層の代役)で、テストが踏むのは**経路(データ)**であって**画面(描画)ではない**。よって:

- 現状の Vitest+MSW は **V-3 の核(契約→モック→生成client→消費・BEゼロ)を今実証するための最小ランナー**。実際に動き、4テスト緑(検証メモ §2)。
- ただし**ランナーの本決めは V-5(React/Next 導入)に先送り**。判断材料:
  - **Vite はアプリには不要**。Next は Turbopack/webpack+SWC で動く。Vitest が使う Vite は**テスト実行専用**でアプリビルドと無関係(共存可)。
  - **Next.js 公式は Vitest も Jest も両方サポート**。"Vitest が不適切" ということはない。Jest は `next/jest` 一級サポート、Vitest は高速・モダン。
  - **async React Server Components は Jest/Vitest とも未対応**で、Next 公式は **RSC は E2E(Playwright)** を推奨。→ V-5 の定石は「client/ロジック=Vitest or Jest + 描画/RSC=Playwright」。
  - **MSW はランナー非依存**。Vitest→Jest→Playwright のどれに移っても**そのまま持ち越せる**ため、今 Vitest に賭けても損が小さい。

```ts
// vitest.config.ts
test: {
  environment: "node",
  include: ["services/**/test/**/*.test.ts"],
  setupFiles: ["services/master/web/test/setup.ts"],
}
```

## 4. 落とし穴: 相対 fetch の URL 解決（node には origin が無い）

### 4.1 症状

生成 api-client は相対 URL(例 `/masters/dept/meta`)で fetch する。
ブラウザでは document origin が付いて絶対 URL になるが、**node 実行の結合テストには origin が無い**ため、相対 URL のままでは fetch が URL を解決できず、MSW に届く前に失敗する。

### 4.2 採用した対処（テスト専用 origin 補完 shim）

`setup.ts` で MSW 差し替え後の `globalThis.fetch` に薄い層を被せ、`/` 始まりの URL に `http://localhost` を前置してから渡す。

```ts
const patched = globalThis.fetch;               // MSW が差し替えた fetch
globalThis.fetch = ((input, init) => {
  const url = typeof input === "string" && input.startsWith("/")
    ? "http://localhost" + input : input;        // ブラウザの origin を補うだけ
  return patched(url, init);
}) as typeof fetch;
```

- 本番コード・生成物には触れない。**ブラウザの origin を再現するテストハーネス**。
- MSW の `*` パターンが `http://localhost/...` に一致するため素通り。

### 4.3 不採用にした代替案

| 代替案 | 不採用理由 |
|---|---|
| 生成 client に `baseUrl` を焼き込む | 本番クライアントに環境固有 host を埋めることになる。経路の純度(契約=正)を汚す |
| `environment: "jsdom"` にする | jsdom は `location` を与えるが node の global fetch はそれを見ず、相対 URL 解決には寄与しない。DOM も V-3 では不要 |
| msw ハンドラを絶対 URL 固定にする | orval 既定のワイルドカード origin の方が汎用。テスト側 origin に依存させない |

## 5. lint / 構造解析との折り合い

- **ESLint**: テストハーネス(`web/test/**`)は V-2 の生fetch禁止ルール(対象 `web/src/**`)の**外**に置く。setup.ts が意図的に `globalThis.fetch` を扱うため。本番側の機械ゲートは不変。
- **dependency-cruiser**: `generated-only-via-sanctioned-consumers` の許可対象に `web/test/` を追加。テストは V-3 における**正規の生成モック消費者**だから(api-client 自身・features と同格に扱う)。

## 6. 本番への持ち越し（判断の入力）

- モック生成は **orval 単一ツール**で型/client と同源に保つ。`useExamples` を必須運用にし、契約に examples を必ず書く(親設計 §6.1)。
- **mock は client とファイル/パッケージを分け、本番 client を mock 依存(msw)非依存に保つ**(§1.5)。PoC は split、本番は出力先分離で `msw-mocks` 別パッケージへ昇格。型の二重生成だけは避ける(orval の mock 単独生成不可が制約)。
- ランナーは Vitest。DOM が要る結合(描画)は jsdom/`@testing-library` を**その時に**足す(V-5 とセット)。
- 相対 fetch の origin は**テスト側で補う**。本番クライアントに host を焼かない。
- モックと本番で**経路を分けない**(V-2 の api-client 1本)。モード切替は向き先の差し替えだけにする。
