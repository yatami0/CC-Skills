## 「BE 待ち」をなくす — モックも契約から生成する

### V-3：モックによる並行開発

<span class="small">contracts_poc / orval(MSW) + MSW + Vitest / TypeScript</span>

## V-1 / V-2 のおさらい — どこまで来たか

| 段 | 何を機械化したか |
|---|---|
| **V-1** | 契約↔型の**ドリフト**。契約を変えると消費コードが `tsc` で止まる |
| **V-2** | 実装側の**配線**。生fetch・層違反・生成物改変を lint/構造解析が落とす |

> V-1・V-2 は「正しさ」を機械に寄せた。
> だが残る課題は **時間軸** — **BE がまだ無い間、FE は何を相手に作るのか？**

---

## V-3 が解こうとする課題 — 「BE 待ち」

FE と BE を並行で作りたい。でも素朴にやると:

- BE が出来るまで FE の結合確認ができない（**待ち**が発生）
- しかたなく **モックを手書き** → 契約とズレる → 「モックでは通るが本番で落ちる」
- モックの保守が契約と二重管理になる

> 結局「人がモックを契約に合わせ続ける」に戻ってしまう。

**V-3 の主張：モックも契約から生成し、BE ゼロで FE を完成形まで作り切る。**

---

## V-3 で検証する仮説（合格基準）

| # | 検証項目 | 合格基準 |
|---|---|---|
| **V-3** | モックによる並行開発 | BE未完成の状態で、**MSWモックだけでFEの画面結合テストが通る** |

判定は「人が画面を触る」ではなく
**「BE プロセスを一切起動せず `pnpm test` が終了コード 0」** で行う。

<span class="small">※ このリポジトリに BE(Java)は無い。つまり「BE未完成」を地で満たした状態でテストが緑になる。</span>
<span class="small">※ 本 PoC はまだ React/Next 未導入。実装するのは「契約→モック→生成client→消費」の**経路結合テスト**で、
React 描画(render→DOM)＝"画面"の結合は ui-engine(V-5)領域。"画面結合"は親仕様の引用。ランナー(Vitest)も V-5 で本決め。</span>

## ワンスイッチで足せる — orval の MSW 出力

V-1/V-2 で型・client を生成済みの **orval** が、同じ契約から MSW モックも出す。

```ts
// orval.config.ts — mock を off → on にするだけ
mock: {
  type: "msw",        // setupServer に渡せるハンドラ群
  useExamples: true,  // 本文を faker乱数でなく「契約 examples」に
  delay: false,       // 擬似遅延(1秒/件)を切る
}
```

> 型/クライアント/モックを**単一ツール・単一契約**から出す。
> → 「型は最新だがモックは古い」が構造的に起きない。`useExamples` が源泉を契約に固定。

---

## 生成されるもの（契約 examples がそのまま本文）

```ts
// packages/api-client/src/generated/poc.msw.ts（client とは別ファイル）
export const getListRecordsResponseMock = (): RecordPage => ({
  items: [
    { id: "1", name: "Pen",  unitPrice: 120, effectiveDate: "2026-04-01", version: 1 },
    { id: "2", name: "Note", unitPrice: 80,  effectiveDate: "2026-04-01", version: 3 },
  ],
  paging: { page: 1, size: 20, total: 2 },          // ← 契約 yaml の example と一致
});

export const getPoCMasterAPIMock = () => [ /* 全エンドポイントのハンドラ */ ];
```

<span class="small">手書きハンドラはゼロ。`useExamples` で全項目が埋まるため faker も不要。
mode:split で client(poc.ts)と分離し、**本番 client は msw を import しない**(後述)。</span>

---

## 設計判断 — 生成 mock は client から分離する

当初 `mode: single` は mock を `poc.ts` に同梱 → **本番 client が `msw`(テスト依存)に依存**。
「generated は契約起点で一元生成・本番経路は純粋」の原則に反する。3案を実測比較した。

| 観点 | 案1 別パッケージ | **案2 split（採用）** | 案3 single 同梱 |
|---|---|---|---|
| 本番 client の msw 依存 | 無し | **無し（実測 0）** | あり ✗ |
| mock の型 | 二重生成 ✗ | 単一 | 単一 |
| 余分な生成物 | 未使用 client ✗ | 無し | 無し |

> **決定的事実**: orval は **mock 単独生成不可** → 別パッケージ案は型を二重生成し、
> 「一元生成」原則とむしろ相性が悪い。**split で client を純粋に保ちつつ型は単一**に。
> 設計§2.2 の別パッケージ化は本番昇格時の宿題(技術調査 §1.5)。

## 結合テスト — FE の実コード経路を踏む

テストが import するのは **FE の入口(app 層)だけ**。中で V-2 の経路を一気通貫で踏む。

```ts
// setup.ts : 契約由来ハンドラで MSW 起動。BE は起動しない
export const server = setupServer(...getPoCMasterAPIMock());
server.listen({ onUnhandledRequest: "error" });   // 契約外の通信は即エラー

// path.msw.test.ts : app → features → api-client → fetch → MSW
const summaries = await getRecordsRoute("price");
expect(summaries).toEqual([
  "Pen = 120 (since 2026-04-01, v1)",              // ← 期待値 = 契約 example
  "Note = 80 (since 2026-04-01, v3)",
]);
```

> テストが緑 = **FE は BE ゼロで完結**している、の機械的な証明。
> モックと本番は**同じ api-client 1本**(V-2)なので、差し替えても経路は変わらない。

## 落とし穴と対処 — node には origin が無い

生成 client は相対 URL(`/masters/dept/meta`)で fetch する。
ブラウザは document origin を付けるが、**node テストには origin が無い**。

```ts
// setup.ts : ブラウザの origin を補うテスト専用 shim(本番コードには触れない)
const patched = globalThis.fetch;                 // MSW 差し替え後の fetch
globalThis.fetch = (input, init) =>
  patched(input.startsWith("/") ? "http://localhost" + input : input, init);
```

| 不採用案 | 理由 |
|---|---|
| client に `baseUrl` を焼く | 本番クライアントに環境固有 host が混入 |
| jsdom 環境にする | node の fetch は location を見ない・DOM も V-3 では不要 |

## ゲートとスクリプト

| script | 役割 | V |
|---|---|---|
| **`pnpm test`** | **Vitest。MSW モックだけで経路結合テスト** | **V-3** |
| `pnpm codegen` | bundle→orval(型+client+**MSWモック**)→prettier | V-1(+V-3) |
| `pnpm codegen:check` | 再生成→差分。モック含む生成物の改変を検知 | V-1 |
| `pnpm typecheck` | `tsc --noEmit`。契約→消費の型破壊 | V-1 |
| `pnpm lint` | ESLint。生fetch/http直書き | V-2 |
| `pnpm depcruise` | 層違反・生成物直参照 | V-2 |
| **`pnpm verify`** | **codegen:check→typecheck→lint→depcruise→test** | V-1+2+3 |

<span class="small">codegen は決定的(2回実行で同一ハッシュ)。モック込みベースラインをコミットすれば codegen:check がモック改変も検知。</span>

---

## モックは「契約に縛られている」

V-3 のモックは契約から生成 → V-1 の破壊が**そのままモックに波及**する。

```text
契約 MasterRecord.unitPrice をリネーム
  → pnpm codegen → 生成モックの本文も型も変わる
  → 消費コードが tsc で落ちる(V-1)＋テスト期待値も追従
```

> 「モックでは通るが契約と違う」状態を**作れない**。
> モックと契約の乖離は、二重管理ではなく**構造的に発生しない**。

## スコープと割り切り（明示）

| 項目 | 本PoCでの扱い |
|---|---|
| モック生成(契約 examples→MSW) | ✅ orval `useExamples` |
| データ経路の結合テスト(app→…→MSW) | ✅ Vitest(node) |
| BE 非依存の担保 | ✅ `onUnhandledRequest:"error"` + BE プロセス無し |
| React render→DOM 断言 | ❌ 描画エンジン(ui-engine=V-5)とセットで後付け |
| 状態遷移シナリオ(複数 example 出し分け) | ❌ `server.use()` で拡張可能(構想) |
| 本物 BE との双方向 contract test | ❌ BE 実装後(Pact/schema 突合) |

<span class="small">割り切りは「やらない」ではなく「同じ思想を後で足せる形にしてある」。</span>

---

## まとめ & 次の一歩

**V-3 で示せたこと**
- モックを手書きすると契約からズレる → **モックも契約から生成**すれば乖離は構造的に消える
- 契約由来の MSW だけで、FE の実コード経路を結合テストし **BE ゼロで緑**
- モックと本番は同じ api-client 1本(V-2) → BE 完成時は**向き先の差し替え**だけ

**次の一歩（構造を変えず "足す" だけ）**
- ui-engine(V-5)実装後、render→DOM まで結合(`@testing-library`)
- 複数 example で成功/各エラー画面遷移(ADR-0010)まで結合テスト化
- BE 実装後、同一契約で双方向 contract test、CI でモード二面実行

<span class="small">本PoCは原則使い捨て。持ち越すのは「モックを生成する設計・examples必須運用・モードを経路で分けない」。</span>
