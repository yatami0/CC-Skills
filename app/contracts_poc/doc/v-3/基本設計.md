# V-3 基本設計 — モックによる並行開発

> 親設計: [doc/v-1/基本設計.md](../v-1/基本設計.md) §1 検証項目表・§4.4 FE先行開発時(モック)。
> 本書はそのうち **V-3** を、この TS 縦切り PoC で実装した範囲の設計を記す。
> 前提として V-1(契約→codegen 破壊検知)・V-2(越境・改変の機械検知)が成立している。

## 1. V-3 の検証項目と合格基準

| # | 検証項目 | 合格基準 |
|---|---|---|
| V-3 | モックによる並行開発 | BE未完成の状態で、**MSWモックだけでFEの画面結合テストが通る** |

判定は「人が画面を触って確認」ではなく「**BE プロセスを一切起動せず、`pnpm test` が終了コード 0 で通る**」で行う。

- V-1 は「契約と型の一致」、V-2 は「実装側の配線」を機械化した。
- V-3 は時間軸の課題を解く: **BE がまだ無い段階でも FE を完成形まで作り切れるか**。
  契約(OpenAPI)の examples を唯一の真実とし、そこから生成した MSW モックで FE の実コード経路を丸ごと回す。

## 2. V-3 が解く課題 — 「BE 待ち」をなくす

```text
契約(OpenAPI = 正) ──codegen──▶ api-client(型付き fetch)
                    └─codegen──▶ MSW ハンドラ(examples が応答本文)
FE は MSW を相手に、BE 完成を待たずに画面と結合テストを作り切る。
BE が出来たら、向き先を MSW → 本物の BE に変えるだけ(FE コードは不変)。
```

肝は **モックを手書きしないこと**。手書きモックは契約から乖離し、「モックでは通るが本番で落ちる」を生む。
本 PoC は **契約 examples からモックを生成**するため、モックは定義上つねに契約と一致する(ズレたら V-1 が落とす)。

## 3. スコープと割り切り（前提の明示）

- V-1/V-2 と同じく **TS(フロント側)に集中**。BE(Java/Spring)はこの縦切りに未実装で、それ自体が「BE未完成」という V-3 の前提を地で行く構図になっている。
- モック生成は **orval の MSW 出力**(`mock: { type: "msw", useExamples: true }`)。応答本文は faker 乱数ではなく**契約 examples** を使う。
- 結合テストランナーは **Vitest**(node 環境)。ブラウザ DOM は使わない(描画エンジン=ui-engine は V-5 スコープのため、本 V-3 は「app→features→api-client→fetch」のデータ経路を結合対象とする)。
- 合格基準の「画面結合テスト」の**本 PoC での実装範囲**: まだ React/Next を導入していないため、ここで結合するのは **FE の入口(app 層)から呼び出し、契約 examples が画面表示用の値として取り出せるところまで**=**経路(データ)結合**。React 描画の結合(render→DOM 断言)＝"画面"の結合は ui-engine 実装(V-5)とセットで足す。
  - したがって本 PoC のテストは正確には **経路結合テスト**(`path.msw.test.ts`)であり、"画面結合"の語は合格基準(親仕様)の引用としてのみ用いる。
  - ランナー(Vitest)も暫定。React/Next 導入時(V-5)に最終決定する(Next なら client/ロジック=Vitest/Jest + 描画/RSC=Playwright が定石。MSW はランナー非依存で持ち越せる)。

## 4. 守る原則（V-3 で新たに効くもの）

| 原則 | 何を防ぐか | 強制/担保 |
|---|---|---|
| モックは契約 examples から生成し手書きしない | モックと契約の乖離(モックでは通るが本番で落ちる) | orval `useExamples` + V-1 `codegen:check` |
| テストは FE の実コード経路を踏む(app→features→api-client) | 「テスト用の偽の経路」を作って通すごまかし | テストは app 層の関数だけを import |
| BE を起動しない | 実は本物の BE に依存していた、を排除 | MSW `onUnhandledRequest: "error"` + そもそも BE プロセス無し |
| API への経路は生成 api-client の1本(V-2 継続) | モック時だけ別経路、を作らない | V-2 の ESLint/dependency-cruiser |

## 5. 実装した構成

```text
contracts_poc/
├ orval.config.ts               ← mock を off→on(type:"msw" / useExamples:true / delay:false)+ mode:split
├ vitest.config.ts              ← 新規。node 環境・テストの include / setupFiles
├ package.json                  ← scripts に test を追加、verify に test を連結
├ packages/api-client/
│ ├ package.json                ← exports に ./generated/poc.msw を追加
│ └ src/generated/
│   ├ poc.ts                    ← 型付き fetch クライアント（msw を import しない＝本番経路は純粋）
│   ├ poc.msw.ts                ← MSW ハンドラ + getPoCMasterAPIMock()（mock 専用入口・msw 依存）
│   └ model/                    ← 型（poc.ts も poc.msw.ts も同じ ./model を import）
└ services/master/web/test/     ← 新規。テスト(V-2 の src/** 越境ルール対象外)
  ├ setup.ts                    ← MSW server を生成ハンドラ(poc.msw)で起動 + origin 補完 shim
  └ path.msw.test.ts            ← 経路結合テスト(BE 不要。React 描画は V-5)
```

- 生成 `poc.msw.ts` に、各エンドポイントの `getXxxMockHandler()` と、全部を束ねる `getPoCMasterAPIMock()` が**契約 examples を本文として**生成される(手書きハンドラはゼロ)。
- **client(`poc.ts`)と mock(`poc.msw.ts`)を `mode: split` でファイル分離**した。本番経路が触る `poc.ts` は `msw` を import しない(本番 client にテスト用依存を漏らさない)。判断の経緯は §6.4。
- `test/` を `src/` の外に置いたのは、V-2 の生fetch禁止ルール(対象 `web/src/**`)とテストハーネス(後述の fetch origin 補完)を衝突させないため。テストは別レイヤとして扱う。

## 6. テストハーネスの設計判断（記録）

### 6.1 モックの源泉は契約 examples（faker 乱数を使わない）

`useExamples: true` により、orval は契約の `examples` をそのまま応答本文の mock 関数に落とす。
たとえば一覧は契約の `page1` example(Pen v1 / Note v3)が `getListRecordsResponseMock()` になる。
→ テストの期待値が**契約 yaml の値と一字一句一致**する。契約を変えれば再生成でモックが変わり、期待値も追従する(V-1 と地続き)。

### 6.2 BE を起動しないことの担保

- MSW `setupServer(...getPoCMasterAPIMock())` を node で起動し、`onUnhandledRequest: "error"`。
- 契約に無いリクエストが飛べば即エラー = 「実は本物の BE/別 API を叩いていた」を機械的に排除。
- そもそもこのリポジトリに BE プロセスは無い。テストが緑 = **BE ゼロで FE が完結**している証拠。

### 6.3 相対 fetch の origin 補完（テスト専用 shim）

生成 api-client は相対 URL(例 `/masters/dept/meta`)で fetch する。ブラウザなら document origin で解決されるが、node 実行の結合テストには origin が無く、相対 URL のままでは fetch が URL を解決できない。
→ `setup.ts` で、MSW 差し替え後の `globalThis.fetch` に「相対 URL を絶対化してから渡す」薄い層を被せる。

- これは **ブラウザの origin を補うだけのテストハーネス**であり、本番コード・生成物には一切触れない。
- MSW のハンドラは `*/masters/...` のワイルドカード origin パターンなので、補った origin(`http://localhost`)と一致する。
- 代替案として生成側に `baseUrl` を焼き込む手もあるが、本番クライアントに環境固有の host を埋めるのは避け、テスト側で吸収する方針を採った。

### 6.4 生成 mock の置き場所（client から分離する）

**技術的課題**: 当初 `mode: "single"` で実装したところ、mock が client と同じ `poc.ts` に同梱され、
**本番 client が `msw`(テスト用依存)に依存**してしまった。これは「generated は契約起点で一元生成」の第一原則(本番経路の純度)と、
設計 §2.2 が api-client と msw-mocks を**別パッケージ**に分ける意図の双方に反する。

**判断: `mode: "split"` を採用**(client=`poc.ts` / mock=`poc.msw.ts` にファイル分離)。

- 本番 client(`poc.ts`)は `msw` を import しない(実測: import 数 0)。本番経路の純度を保つ。
- 型(`model/`)は単一系統。`poc.ts` も `poc.msw.ts` も同じ `./model` を import する。
- 別パッケージ(`msw-mocks/`)化は見送り。orval は **mock 単独生成ができず**、別プロジェクトにすると
  **型 model を二重生成＋未使用 client も生成**してしまい、第一原則(一元生成)とむしろ相性が悪いため。
- 設計 §2.2 の「別パッケージ」は本番構成の話。PoC では split で「mock を分離生成・client は純粋」を実証し、
  本番は出力先分離で `msw-mocks` へ昇格する(§9 拡張パス)。詳細な3案比較は [技術調査.md §1.5](技術調査.md)。

## 7. ゲートとスクリプト

| script | 役割 | V |
|---|---|---|
| `pnpm test` | Vitest。MSW モックだけで FE 経路結合テストを実行 | **V-3** |
| `pnpm codegen` | bundle→orval(型+client+**MSW モック**)→prettier | V-1(+V-3でモック追加) |
| `pnpm codegen:check` | 再生成→`git diff --exit-code`。モック含む生成物のドリフト/手書き改変を検知 | V-1 |
| `pnpm typecheck` | `tsc --noEmit`(strict)。契約→消費の型破壊 | V-1 |
| `pnpm lint` | ESLint。生fetch/http直書きを検知 | V-2 |
| `pnpm depcruise` | dependency-cruiser。レイヤ違反・生成物直参照を検知 | V-2 |
| `pnpm verify` | 上記を一括(codegen:check→typecheck→lint→depcruise→**test**) | V-1+V-2+V-3 |

## 8. この PoC で「言えること / まだ無いもの」

| | V-3 で実装済み | まだ無い |
|---|---|---|
| モック生成 | 契約 examples→MSW ハンドラ(orval) | 複数 example の出し分け(状態遷移シナリオ) |
| 結合テスト | app→features→api-client→MSW のデータ経路 | React render→DOM 断言(ui-engine=V-5 とセット) |
| BE 非依存 | `onUnhandledRequest:"error"` + BE プロセス無し | 本物 BE との contract test(Pact 等)による双方向保証 |
| 並行開発 | FE は BE 完成を待たず作り切れる | CI でのモック/本番の二面実行 |

V-3 は「**契約から生成したモックだけで FE を完成形まで作り切り、結合テストを機械が通す**」縦1本を、実際に動く形で固めた段階。
モックと本番の経路が同一(api-client 1本/V-2)なので、BE 完成時は向き先を差し替えるだけで FE は不変。

## 9. 拡張パス（V-3 後）

- **状態シナリオ**: 契約に複数 example(成功/各エラー)を持たせ、`server.use()` で出し分け → エラー画面遷移(ADR-0010)まで結合テスト化。
- **render 結合**: ui-engine(V-5)実装後、`@testing-library` で「メタ定義→フォーム描画→送信→MSW 応答→画面更新」を1テストで通す。
- **双方向保証**: BE 実装後、同じ契約から BE 側スタブ/contract test を生成し「モックと本物が同じ契約に従う」ことを機械化(Pact / schema 突合)。
- **CI 二面実行**: 同一テストを「MSW モード(BE不要・常時)」と「実 BE モード(夜間)」で回し、モックドリフトを検知。
- **mock の別パッケージ昇格**: 設計 §2.2 どおり `packages/msw-mocks/` へ分離(現状は split でファイル分離)。orval 出力先を分けるだけだが、型の二重生成を避けるには mock 側の型 import を api-client 参照へ向ける後処理が要る(技術調査 §1.5 の宿題)。
