# V-3 検証メモ — 実測結果

実施環境: Node 24.13.0 / pnpm 10.28.1 / orval 7.21.0 / msw 2.14.6 / vitest 2.1.9 / typescript 5.x。
（V-1/V-2 の環境に msw・vitest を追加。jsdom は不要のため入れていない。）

## 0. 前提: BE プロセスは無い

このリポジトリには Java/Spring の BE 実装が存在しない。つまり「BE未完成」という V-3 の前提を地で満たしている。
以下のテストはネットワーク上に何も listen していない状態で実行し、それでも緑になる = **MSW モックだけで成立**している証拠。

## 1. モック生成の確認（契約 examples が源泉・client と分離）

`orval.config.ts` を `mode: "split"` + `mock: { type: "msw", useExamples: true, delay: false }` にして `pnpm codegen`。
生成物は client と mock に**ファイル分離**された:

```text
packages/api-client/src/generated/
├ poc.ts       … 型付き fetch クライアント（msw を import しない）
├ poc.msw.ts   … MSW ハンドラ（mock 専用入口）
└ model/       … 型（単一系統）
```

`poc.msw.ts` に生成されたもの:

- 応答本文 mock: `getGetMasterMetaResponseMock()` / `getListRecordsResponseMock()` ほか
  → 中身は契約 yaml の examples と一致(例: 一覧 = Pen v1 / Note v3、メタ = dept)。
- ハンドラ: `getGetMasterMetaMockHandler()` 〜 `getDeleteRecordMockHandler()`(`*/masters/...` パターン)
- 束ね: `getPoCMasterAPIMock()` … 全ハンドラの配列(setupServer にそのまま渡せる)

> 手書きハンドラはゼロ。モックは契約から生成され、`useExamples` により本文も契約 examples。
> faker のインポートは生成されない(examples が全フィールドを満たすため)。

**本番 client の純度を実測**: `poc.ts` の `msw` import 数 = **0**(split により mock 依存は `poc.msw.ts` だけに乗る)。
当初 `mode: "single"` では mock が `poc.ts` に同梱され本番 client が msw に依存していたが、split で解消した(判断は §6)。

## 2. 結合テスト（合格基準そのもの）

`pnpm test`(= `vitest run`)。テストは FE の入口(app 層)だけを import し、内部で
`app → features → @poc/api-client → fetch → MSW(契約 examples)` を一気通貫で踏む。

| テスト | 検証内容 | 期待値の出所 |
|---|---|---|
| 一覧ルート | `getRecordsRoute("price")` が2件を画面表示用文字列に整形 | 契約 listRecords example |
| 1件ルート | `getRecordRoute` / `loadRecord` が単一レコード取得 | 契約 getRecord example |
| 更新 | `bumpPrice`(楽観排他 version 付き PUT)が更新結果を返す | 契約 updateRecord example |
| 異常系 | 404 を返すモックに差し替えると features が `null` に分岐 | 契約 404(ErrorResponse)example |

実測:

```text
 ✓ services/master/web/test/path.msw.test.ts (4 tests) 18ms

 Test Files  1 passed (1)
      Tests  4 passed (4)
```

**vitest 終了コード `0`**。BE を一切起動せず、契約由来の MSW モックだけで4テスト緑。
→ V-3 合格基準（MSWモックだけで FE のテストが通る）を、**経路結合テスト**として満たす。
　React 描画(render→DOM)＝"画面"の結合は ui-engine 実装(V-5)の領域で、本 PoC では未対象(親仕様の「画面結合」はその引用)。

## 3. 周辺ゲートが緑のまま（退行なし）

V-3 の追加(モック生成 on・テスト追加)で V-1/V-2 のゲートが壊れていないことを確認。

| ゲート | 終了コード | 備考 |
|---|---|---|
| `pnpm typecheck` | `0` | 生成 poc.ts が `msw` 型に依存するようになったが解決 OK |
| `pnpm lint` | `0` | テストハーネスは `web/src/**` 対象外(ignore)。本番側ルールは不変 |
| `pnpm depcruise` | `0` | `no dependency violations found (21 modules, 29 dependencies cruised)` |
| `pnpm test` | `0` | 上記 §2 |

> depcruise のモジュール数が V-2 の 14→21、依存 18→29 に増えたのは、生成ハンドラ(`poc.msw.ts`)・msw・テストが依存グラフに乗ったため(split で `poc.msw.ts` が独立モジュールになり single 時より +1)。
> `generated-only-via-sanctioned-consumers` の許可対象に `services/master/web/test/` を追加し、テストが生成モックを消費できるようにした(テストは V-3 の正規のモック消費者)。

## 4. codegen の決定性（codegen:check が意味を持つこと）

`pnpm codegen` を2回連続実行し、`packages/api-client/src/generated/poc.ts` の SHA-256 が一致することを確認(idempotent = True)。
→ モック生成は決定論的。よって `codegen:check`(再生成→`git diff --exit-code`)は、

- モック生成 ON のベースラインを**コミットしておけば**、生成物(モック含む)の手書き改変・ドリフトを引き続き検知できる(V-1 と同じ仕組み)。

> V-1/V-2 と同様、`codegen:check` を有効にするにはモック込みの生成物を**ベースラインとしてコミット**しておくこと(`git diff --exit-code` は tracked のみ比較)。

## 5. 破壊テスト的な確認（モックが契約に縛られていること）

V-3 のモックは契約から生成されるため、V-1 の破壊が**そのままモックにも波及**する:

- 契約 `MasterRecord.unitPrice` をリネーム → `pnpm codegen` → 生成モック本文も型も変わる
  → 消費側 `recordsView.ts` が `tsc` で落ちる(V-1)＋テスト期待値も追従が必要。
- つまり「モックでは通るが契約と違う」状態を作れない。**モックと契約の乖離は構造的に発生しない**。

## 6. 設計判断の記録: 生成 mock を client から分離（split 採用）

V-3 実装中、「生成 mock の置き場所」を議論した。発端は **api-client 配下の generated は契約起点で一元生成する第一原則**に対し、当初実装(`mode: single`)が **本番 client(`poc.ts`)に mock を同梱＝ msw 依存を持たせていた**こと。

3案をスパイクで実測比較した(詳細は [技術調査.md §1.5](技術調査.md)):

| 観点 | 案1: 別パッケージ `msw-mocks/` | **案2: split（採用）** | 案3: single 同梱 |
|---|---|---|---|
| 本番 client の msw 依存 | 無し | **無し（実測 import 0）** | あり ✗ |
| mock の型 | `./model` を二重生成 ✗ | 同パッケージの `./model`（単一） | 単一 |
| 余分な生成物 | 未使用 client も生成 ✗ | 無し | 無し |
| 設計§2.2 忠実度 | ◎ 別パッケージ | △ ファイル分離 | ✗ |

**決定的事実(実測)**: orval は **mock 単独生成不可**。よって案1(別パッケージ)は型 model を**二重生成**し、第一原則(一元生成)とむしろ相性が悪い。

**結論: 案2(split)を採用**。本番 client を msw 非依存に保ちつつ(実測 import 0)、型を単一系統に保てる。設計§2.2 の別パッケージ化は本番昇格時の宿題として技術調査§1.5に記録。

| 観点 | 結果 |
|---|---|
| 生成 mock | client(poc.ts)と分離(poc.msw.ts)。本番経路は msw 非依存(実測 import 0) |
| BE プロセス | 起動せず(そもそも無し) |
| モックの源泉 | 契約 examples(手書きゼロ) |
| 経路結合テスト | `pnpm test` 終了コード `0`(4 tests。画面=描画結合は V-5) |

## 持ち越す知見（本番へ）

- **モックは生成、手書きしない**。契約 examples を一次情報にすれば「モックと本番の乖離」は構造的に消える。examples を契約に必ず書く運用(親設計 §6.1)がそのまま効く。
- **生成 mock は client から分離し、本番 client を mock 依存(msw)非依存に保つ**。orval は mock 単独生成不可なので、PoC は split(ファイル分離)、本番は出力先分離で別パッケージへ。型の二重生成だけは避ける(§6・技術調査§1.5)。
- **モックと本番で経路を分けない**。V-2 で API 経路を api-client 1本に固定してあるから、モード切替(MSW↔実BE)が「向き先の差し替え」だけで済む。
- **テストハーネスは本番ルールの外に置く**。生成クライアントの相対 fetch は、本番(ブラウザ)では origin が付くが node テストでは付かない。本番コードに baseUrl を焼かず、テスト側で origin を補う。
- **ランナーに DOM を要求しない**。データ経路の結合は node 環境で軽く回る(18ms)。DOM 結合は描画(ui-engine/V-5)とセットで足す。
