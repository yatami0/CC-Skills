# V-4「CSV契約の機械検証」を本 PoC に含めない判断（記録）

> 親設計: [doc/基本設計.md](基本設計.md) §1 検証項目表（V-4）・§2.1 構成図（Java世界）・§4.3 実行時(CSV配布)・§6.2 ファイル連携。
> 本書は「V-4 をこの TS-only PoC では実装せず、BE PoC / BE 実装フェーズへ送る」という判断と理由を残すもの。
> 一度 TS で試作（commit `v4実装`）したが、下記の理由で**完全に revert** し、知見だけを本書に残した。

## 1. 判断

**V-4（CSV契約の機械検証）は、この TS-only PoC のスコープに含めない。BE PoC（または BE 実装フェーズ）の領分とする。**

この PoC が自然にカバーするのは **V-1 / V-2 / V-3**、および今後の **V-5（メタ定義駆動UI）** ——いずれも FE-native な検証項目。

## 2. なぜ含めないか

### 2.1 V-4 は BE-native。V-1〜V-3 とは性質が違う

| V | 本来の住処 | この PoC(TS)での意味 |
|---|---|---|
| V-1 codegen破壊 | FE-native（FE が生成型を消費） | 代役ではない・本物の検証 |
| V-2 越境検知 | FE-native（FE の層・経路） | 代役ではない・本物の検証 |
| V-3 モック並行開発 | FE-native（MSW） | 代役ではない・本物の検証 |
| **V-4 CSV契約** | **BE-native**（Java batch / Java DTO＋バリデータ・親設計 §2.1/§4.3） | TS では**代役にしかならない** |

V-1〜V-3 はもともと TS/FE の話なので TS-only PoC に収まる。V-4 だけが、本来 BE(Java) でやる「配布CSV の出力・契約照合」を TS に持ち込む初めてのケースで、PoC の前提（TS-only・Java/ArchUnit はスコープ外）と噛み合わない。

### 2.2 TS で実装しても「検証」にならない

V-4 の合格基準は「JSON Schema → **Java** DTO＋バリデータ → batch が出力前に弾く」。
TS（ajv）で組むと、**本番で使う Java ツールチェーン（openapi-generator / Bean Validation / ArchUnit）とは別物**を動かしているだけになる。

- 実証できるのは「契約からバリデータを生成して I/O 境界で弾く、という**設計思想**が成り立つ」ことのみ。
- V-4 が本来確かめるべき「**Java** での生成・照合・出力前ゲートが動くか」は何も確かめられない。

→ TS-only の制約下では、V-4 は「検証」ではなく「パターンの素描」にしかならない。素描を検証項目の達成として残すと、未検証の Java 部分を検証済みと誤認させる火種になる。

### 2.3 ファイル連携における FE の役割は限定的

CSV/ファイル連携は **BE ↔ 外部システム**の責務（親設計 §4.3 の配布CSVは batch が出力。FE は登場しない）。

- FE がファイルに触れるのは精々アップロードUI で、行うのは**拡張子・サイズ等の最低限のバリデーション**まで。
- 本格的な契約照合（項目・桁・コード値）は BE。FE は BE の API を叩くだけ。
- 取込側（vehicle-import）は親設計でもスコープ外。

## 3. それでも持ち越す気づき（本書に残す価値）

試作で確認できた、本番（BE PoC / 実装）へ持ち越す設計知見:

1. **`contracts/` は OpenAPI 専用ではない。** ファイル連携の契約は **JSON Schema** として `contracts/files/` に置く（親設計 §2.2 §6.2）。`contracts/` は「FE↔BE の HTTP」だけでなく「全システム間インターフェースの正」。
2. **「契約→生成→境界で機械照合＋ codegen:check でドリフト検知」という思想は、HTTP でもファイルでも同型**に効く。HTTP は OpenAPI→orval、ファイルは JSON Schema→（本番なら）Java DTO＋バリデータ。
3. **ファイルメタ（文字コード/区切り/改行/ヘッダ）も契約に同居**させる（JSON Schema の拡張プロパティ等）。CSV の入出力もそこから駆動し、手書き定数にしない。
4. **取込/出力は同一の生成バリデータで照合**する（片肺チェック・二重管理を作らない）。V-2 で通信経路を api-client 1本に固定したのと同じ考え方をファイル契約へ適用する。
5. **実装メモ（Java 以外で組む場合の落とし穴）**: 試作では ajv standalone を使ったが、`maxLength`/`minLength` が `ucs2length` runtime を `require` するため ESM の生 node で割れた（CommonJS 出力で回避）。「テスト（バンドラ経由）が緑でも本番ランタイムで割れる」例として記録。Java で組むなら無関係だが、TS で再挑戦する場合の注意。

## 4. V-4 を実装するときの置き場所（将来）

親設計どおり、V-4 は BE 側で実装する:

- 契約: `contracts/files/*.schema.json`（JSON Schema＋ファイルメタ）
- 生成: JSON Schema → **Java** DTO＋バリデータ
- 出力: `services/master/batch`（Spring Boot）が出力直前に生成バリデータで契約照合（NG は異常終了＋件数ログ）
- ゲート: codegen:check（生成物ドリフト）＋ ArchUnit（生成IF implements 強制）

→ HTTP 契約（本 PoC で実証済み）と同じ構造を、Java 世界で「増やすだけ」。
