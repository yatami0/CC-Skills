# V-5 基本設計 — メタ定義駆動 UI（画面結合）

> 親設計 [doc/基本設計.md](../基本設計.md) §1 / 本番 FE 設計 [doc/基本設計/10-FE.md §8](../../../../doc/基本設計/10-FE.md) を一次情報とし、本書は V-5 の PoC 実装の具体に絞る。

## 1. V-5 の検証項目と合格基準

| 項目 | 合格基準 |
|---|---|
| V-5 メタ定義駆動 UI | マスタ個別の画面コードなしで、メタ定義の差し替えだけで 2 種類のマスタ画面が動く（render→DOM で機械判定） |

判定は「人が見て確認」ではなく、**同一の `<MasterCrudPage>` を masterId だけ替えて 2 回描画し、DOM の差を断言する**自動テスト（`services/master/web/test/screen.v5.test.tsx`）で行う。

## 2. V-5 が解く課題 — 「マスタ 62 本ぶんの画面を書かない」

実システムには多数のマスタがあるが、CRUD 画面の構造は共通（一覧＋登録/編集フォーム）。マスタごとに画面を量産すると、項目追加のたびに全画面へ波及し、契約と画面の乖離も生む。

V-5 は **契約のメタ定義（項目名・型・必須・コード値）を汎用エンジンが解釈して描画する**ことで、マスタ個別コードを 0 にする（ADR-0003）。エンドポイントも `{masterId}` でパラメタライズし、マスタごとにパスを増やさない。

V-5 は V-3 の昇格でもある: V-3 は「契約→モック→生成 client→消費」の経路（データ）結合まで。V-5 で React を入れ、戻り値が **画面（render→DOM）** に出るところまでを結合テストする。

---

## 3. スコープと割り切り（前提の明示）

- エンジンは **一覧＋登録/編集フォームのみ**。検索条件・項目間連動・ページャ UI は対象外（親設計 §3 ui-engine 行）。
- レコード契約は **単一固定形**（`MasterRecord` = name/unitPrice/effectiveDate/version）。メタは dept/price で異なるが、書込（Create/Update）リクエストは契約の固定項目へ写像する。型バリエーションを持つ `price` が固定契約と一致するため、**書込の往復は price で実証**する。
- 状態は Jotai まで本番設計に寄せる（読み取り/書込フック分離）。一方で **Next.js は導入しない**。render→DOM の成立に必要なのは React + Testing Library であり、Next ルーティング/RouteHandler の配線は本番化の関心事（ランナーは Vitest で本決め）。
- orval の `useExamples` は契約の**先頭 example のみ**モック化する。2 つ目の `price` メタは契約と同値を MSW override で供給する（V-3 が 404 を override するのと同じ流儀）。

---

## 4. 守る原則（V-5 で新たに効くもの）

- **マスタ個別コード/フォルダを作らない**（ADR-0003）。画面は 1 本（`MasterCrudPage` / `MasterCrudView`）。
- **ui-engine は generated/ にも特定マスタにも依存しない**汎用描画層に保つ。契約への静的依存は features（`mappers.ts`）に集約する（dependency-cruiser `generated-only-via-sanctioned-consumers` を満たす）。
- **API 呼び出しは Action フック内のみ・生成 api-client 経由のみ**（V-2 継続）。ui-engine は API/状態に触れず props 駆動。
- **状態は store/ に集約**し、読み取り `useXxxState` と書込 `useXxxAction` を分離（06-state-and-hooks）。
- **不要 useEffect を書かない**（03-react-rules）。初期ロードのみ「外部システムとの同期」として `useEffect` を 1 つ使う（派生状態でも連鎖更新でもない正当な用途）。

## 5. 実装した構成

```
packages/ui-engine/                         汎用メタ駆動レンダラ（API/状態/generated 非依存）
  src/types.ts            MasterUiMeta / FieldMeta / RecordRow / AppError（エンジンのドメイン型）
  src/buildSchema.ts      メタ定義 → Zod スキーマ（必須/型をメタから機械導出・ts-pattern で分岐）
  src/MetaForm.tsx        型→入力UI（string=text / number=number / date=date / code=select）。RHF+Zod、必須エラーをインライン
  src/MasterList.tsx      カラムをメタから、セルを項目名で引く一覧テーブル
  src/MasterCrudView.tsx  一覧＋フォーム＋エラーの合成（V-5 の主役・編集対象は画面ローカル useState）

services/master/web/src/
  store/masterStore.ts                    Jotai Atom（meta/records/loading/error）。型はエンジンのドメイン型
  features/masterRecords/mappers.ts       generated 型 ⇄ エンジン型の写像（契約への静的依存=V-1 波及点）
  features/masterRecords/hooks/
    useMasterCrudState.ts                 読み取り専用（useAtomValue のみ）
    useMasterCrudAction.ts                load/create/update/remove（api-client + Atom 更新 + エラー正規化）
  app/MasterCrudPage.tsx                  hooks を組み立ててエンジンに渡すだけの薄い app 層

services/master/web/test/screen.v5.test.tsx   画面結合テスト（jsdom・render→DOM）
```

依存方向（V-2 で機械強制）に V-5 で加わるもの:

```
app(MasterCrudPage) → features(hooks) → @poc/api-client（API 経路は不変・1 本）
app                 → @poc/ui-engine（描画）
features            → store（Atom 更新）→（型のみ）@poc/ui-engine
```

いずれも generated/ には触れず、契約への接点は features（mappers）に限定。ui-engine は leaf（誰にも依存されるが何も逆流させない）。

## 6. メタ → 画面 の導出（エンジンの中核）

| メタの type | 入力 UI（MetaForm） | 一覧セル（MasterList） | Zod（buildSchema） |
|---|---|---|---|
| string | `<input type=text>` | 文字列表示 | `z.string()`（required で `.min(1)`） |
| number | `<input type=number>` | 文字列表示 | 空→undefined 前処理 + `z.number()`（required_error） |
| date | `<input type=date>` | 文字列表示 | `z.string()`（required で `.min(1)`） |
| code | `<select>`（codeValues→option） | コード値表示 | `z.enum(codeValues)`（任意なら空許容） |

- フォームのキー＝メタの項目名。`buildFormSchema(meta)` がメタから Zod オブジェクトを組み立てるため、項目が増減しても画面コードは不変。
- 必須・型のエラーはフィールド直下にインライン表示（クライアント Zod）。サーバエラー（契約 `ErrorResponse`）は `AppError` に正規化して画面上部に表示（表示レイヤーを分離）。
- 二重送信は `formState.isSubmitting` で submit 中の無効化により抑止。

## 7. ゲートとスクリプト

| 守りたいこと | 強制手段 | 実測 |
|---|---|---|
| 同一画面が 2 マスタを描画（render→DOM） | Vitest(jsdom) + Testing Library（`screen.v5.test.tsx`） | 0（4 tests passed） |
| Rules of Hooks / exhaustive-deps | eslint-plugin-react-hooks（error） | `pnpm lint` = 0 |
| 生成物直参照禁止（ui-engine が generated に触れない） | dependency-cruiser | `pnpm depcruise` = 0 |
| 生 fetch 直書き禁止（tsx も対象） | ESLint（files: `**/*.{ts,tsx}`） | `pnpm lint` = 0 |

## 8. この PoC で「言えること / まだ無いもの」

言えること:
- 契約のメタ定義だけで、マスタ個別コード 0 のまま 2 種のマスタ画面が render→DOM で動く（合格基準そのもの）。
- 入力 UI・一覧カラム・バリデーションがすべてメタから機械導出される（型/必須/コード値）。
- V-3 が経路結合から画面結合へ昇格し、登録の往復が MSW 経由で画面に反映される。
- 契約破壊（property リネーム）が features の写像で `tsc` を止める（メタ駆動経路も契約に縛られる）。

まだ無いもの（本番/別フェーズ）:
- Next.js ルーティング/RouteHandler の配線、認証ガード、i18n、Datadog。
- VRT（Storybook + storycap + reg-suit）。本 PoC は DOM 断言までで視覚回帰は対象外。
- レコード契約の可変スキーマ化（マスタごとに record 形が変わる契約）。本 PoC は固定形のため書込は price で実証。

## 9. 拡張パス（V-5 後）

- マスタを増やす＝**契約にメタ example を足すだけ**。画面コードは不変。
- record 契約を可変化する場合も、写像は features（mappers）に閉じる。エンジンと store は generated 非依存のため影響しない。
- Storybook を足せば、ui-engine のプレゼンテーション層をそのまま VRT に載せられる（props 駆動の純粋描画層のため）。
- Next.js 化は app 層（`MasterCrudPage`）の上に RouteHandler/ルーティングを被せるだけ。features 以下は不変。
