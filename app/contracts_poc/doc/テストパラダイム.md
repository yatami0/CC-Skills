# 契約駆動開発のテストパラダイム — orval モック・テスト観点・責務の分離

> 横断ドキュメント。特定の V-x に閉じず、この PoC のテストの考え方を整理する。
> 中心は V-3(モックによる並行開発)だが、契約駆動全体のテスト戦略として読む。
> 関連: [v-3/基本設計.md](v-3/基本設計.md) / [v-3/技術調査.md](v-3/技術調査.md) / [v-3/検証メモ.md](v-3/検証メモ.md)。

## 0. なぜこのドキュメントが要るか

「契約から生成したモックでテストする」と聞くと、**orval が作る「モック」を「テスト」だと無意識に同一視**しやすい。
だが両者は別物で、混同すると「テストは通るが、何を検証したのか説明できない」状態になる。

このドキュメントは次を整理する:

- 契約(contracts)パラダイムの上で、**orval が作るもの / 作らないもの**は何か
- 「example をモック兼期待値にする」テストは**実際に何を検証しているのか**
- テスト観点を**どの層が担うか**(単体 / 結合 / 契約 / E2E)
- 実務でテストデータ・テストケースを**どう用意するか**

## 1. 前提:この設計の contracts パラダイム

```text
contracts(OpenAPI / JSON Schema = 唯一の正・人が書く)
  ──codegen(一方向)──▶ 型 / api-client / MSW モック（/ 将来 zod・Java IF）
  ドリフトは機械が落とす（V-1: tsc・codegen:check ／ V-2: lint・depcruise）
```

- **契約が一次情報**。コードから契約は作らない(ADR-0002)。
- 契約から**複数の生成物**が同源で出る。型も client もモックも、出所は同じ契約。
- だから「型は最新だがモックは古い」が構造的に起きない。**モックも契約に従う**。

このパラダイムの帰結として、テストも「契約が約束する形」を土台に置ける。
**FE は BE 完成を待たず、契約由来のモックを相手に作り切れる**(V-3 の主張)。
——ただし、ここで「モック」と「テスト」を切り分ける必要がある。それが次節。

## 2. 核心:orval のモックは「BE の代役」であって「テスト」ではない

テストにまつわる3つの物を分けて捉える。**orval が作るのは①だけ**。

| # | もの | 誰が作るか | 中身 |
|---|---|---|---|
| ① | **モック(BE の代役)** | **orval が生成** | 契約 `examples` を返す**固定レスポンス**。1エンドポイント1個 |
| ② | **テストデータ(観点ごとの入力/期待値)** | **人が作る** | 空配列・任意項目 null・境界値・各エラー応答… |
| ③ | **テストケース / テスト観点** | **人が設計する** | 何を・どの分岐を・どの条件で確かめるか |

> 「orval がテストを勝手に作る」わけではない。orval が用意するのは**①の土台(happy path の見本)**だけで、
> **②③は別途、テスト観点を整理して人が作る**。

## 3. orval モックの性質と限界（"違和感"の正体）

orval の `mock: { type: "msw", useExamples: true }` で生成されるモックは、次の性質を持つ。

### 3.1 リクエストを見ない＝データ/状態を持たない

生成モックは固定の example を返すだけで、**パスパラメータやボディを参照しない**。

```ts
getRecord("price", "1")   → { id:"1", name:"Pen", ... }  // example
getRecord("price", "999") → { id:"1", name:"Pen", ... }  // ★ 999 でも同じ example が返る
```

- 「id=999 は存在しないから 404」のような**データに基づく振る舞いは表現できない**。
- メタ定義は契約に `dept` / `price` の2例があるが、生成モックは **`useExamples` が先頭(dept)に固定**。`price` のメタは生成モックからは取れない。

### 3.2 異常系(エラー応答)は生成されない

orval は各オペレーションにつき**代表1応答(2xx success)**だけをハンドラ化する。
401/403/404/409 は生成されない。→ 異常系は契約のエラー example を載せた MSW ハンドラを **`server.use()` で上書き**して作る。

### 3.3 まとめ:モックは「形の見本」であってデータストアではない

> 生成モック = **契約が約束する happy path の"形"の見本**。
> **シナリオを表現するデータ層ではない**。ここが、契約駆動のモックに感じる違和感の正体。

`useExamples: false` にすると faker 乱数になり、値が毎回変わって期待値が書けない/契約と無関係になる。だから本 PoC は `useExamples: true`。
ただしそれでも上記 3.1〜3.2 の限界は残る。

## 4. 「example をモック兼期待値」にすると何を検証しているか

現状の V-3 テストはこう書ける:

```ts
const summaries = await getRecordsRoute("price");
// モックも期待値も出所が同じ契約 example
expect(summaries).toEqual(["Pen = 120 (since 2026-04-01, v1)", "Note = 80 (since 2026-04-01, v3)"]);
```

このテストが検証しているのは:

- ✅ **配線(経路)**: `app → features → api-client → fetch → MSW → JSON parse → status 分岐` が繋がる
- ✅ **FE 整形ロジック1点**: `summarize()` がその1データを正しく文字列化する

検証**していない**のは:

- ❌ データのバリエーション(空配列・任意項目 null・境界値・大きな桁)
- ❌ 異常分岐(401/403/409 など。404 は `server.use` 上書きで別途確認)
- ❌ リクエストの形(PUT が version を載せているか 等)

> モックと期待値の**出所が同じ**(どちらも契約 example)だと、テストは本質的に**配線しか見ない**(半循環)。
> これは V-3 の合格基準「**経路が繋がる**」としては妥当。だが「テスト観点を網羅した」とは**別物**。
> 「テストは通るのに薄く感じる」のは、この**配線観点とデータ/ロジック観点のギャップ**を見ているから。

## 5. テスト観点を層で切る（orval の関与を明示）

観点を1つのテスト層に詰め込まない。**層ごとに責務とデータの作り方を分ける**。

| 観点 | 層 | テストデータの作り方 | orval の関与 |
|---|---|---|---|
| 整形/分岐ロジック(空配列・null任意項目・境界値) | **単体** | **人が型付きで作る**(MSW 不要) | 不関与 |
| 経路が繋がる(happy path) | **結合(V-3 / MSW)** | 契約 example(生成モック)で十分 | ① 生成モック |
| 各エラー→画面分岐(401/403/404/409) | **結合(V-3 / MSW)** | **人が `server.use()` で上書き** | 不関与 |
| リクエスト形が契約準拠(PUT が version を送る等) | **結合(V-3 / MSW)** | 人が `info.request` を検証 | 不関与 |
| example 自体が schema 準拠 | **契約検証** | 契約 example を schema/zod で照合 | V-1 / V-4 領域 |
| 実 BE と一致 | **E2E / 契約テスト** | seed データ / Pact 等 | スコープ外 |

- **単体**: FE のロジック(整形・分岐・計算)を、入力データを観点ごとに自作して網羅。MSW すら要らないことが多い。
- **結合(V-3)**: 「経路が契約どおり繋がる」ことを確認。happy は生成モック、異常・境界は `server.use` で観点を足す。
- **契約検証**: 「example/レスポンスが契約に従う」こと。型(V-1)・実行時(zod / V-4)で担保。
- **E2E**: 実ブラウザ＋実/seed BE。本 PoC スコープ外。

## 6. 実務指針（テストデータ・テストケースの作り方）

### 6.1 モックは happy path の見本として割り切る

生成モックはそのまま「正常系の形」を表す土台に使う。改変しない(生成物の手書き改変は禁止 / ADR-0009)。

### 6.2 シナリオは「型付きビルダ」で自作する（契約型に紐付ける）

テストデータは契約型(`MasterRecord` 等)を使って組み立てる。こうすると**契約変更時にテストデータも tsc で落ちる**(V-1 と地続きを維持)。

```ts
import type { MasterRecord } from "@poc/api-client/generated/model/masterRecord";
import { getGetRecordMockHandler } from "@poc/api-client/generated/poc.msw";

const rec = (o: Partial<MasterRecord> = {}): MasterRecord =>
  ({ id: "1", name: "Pen", unitPrice: 120, effectiveDate: "2026-04-01", version: 1, ...o });

// 境界値シナリオ: 200 で unitPrice=0 を返すモックに差し替え
server.use(getGetRecordMockHandler(rec({ unitPrice: 0 })));
```

### 6.3 異常系は `server.use()` で上書きして作る

生成モックに無い 401/403/404/409 は、契約のエラー example を載せた MSW ハンドラで上書きする(上書き先も BE ではなくモック)。

```ts
import { HttpResponse, http } from "msw";
server.use(
  http.get("*/masters/:masterId/records/:id", () =>
    HttpResponse.json(
      { errorCode: "ERR-0001", message: "record not found",
        correlationId: "00000000-0000-0000-0000-000000000000" },
      { status: 404 },
    ),
  ),
);
```

### 6.4 ロジック観点は単体テストへ逃がす

結合テストに全観点を詰めない。整形・分岐・計算は**入力を自作した単体テスト**で網羅する方が速く・明瞭。

### 6.5 期待値の出所を意識的に分ける

- **配線(happy path)**: 期待が契約 example と一致して**OK**(検証対象は配線そのもの)。
- **ロジック/シナリオ**: 期待は**自分で独立に計算した値**にする。でないと「example == example」の循環になる。

## 7. このPoC（V-3）の現状と差分

| 観点 | 現状 |
|---|---|
| 結合・happy(経路が繋がる) | ✅ 実装済み(一覧/1件/更新) |
| 結合・異常(status 分岐) | △ 404 の1本のみ(`server.use` 上書き) |
| 結合・リクエスト形(version 送信等) | ❌ 未 |
| 単体・整形/分岐ロジック | ❌ 未(`summarize` 等の観点は happy 1点のみ) |
| データ境界(空配列・null任意項目・桁) | ❌ 未 |

> 現状の4テストは **結合(配線)観点としては妥当**。埋めるべき空白は
> **①単体(ロジック)層** と **②結合の異常/境界(型付きビルダ)** の2つ。
> これらは「テストが薄い」のではなく「**別の層が未着手**」と捉えるのが正しい。

## 8. まとめ（持ち越す原則）

- **モック ≠ テスト**。orval が作るのは①モック(happy path の見本)だけ。②テストデータ③テスト観点は人が作る。
- **生成モックはデータ/状態を持たない**。リクエストに応じた振る舞い・異常系・データ境界は表現できない。割り切って happy の土台として使う。
- **観点は層で切る**。配線=結合(MSW)、ロジック=単体、契約準拠=型/zod、実BE一致=E2E。1層に詰めない。
- **テストデータは契約型に紐付けて自作**(型付きビルダ)。契約が変わればテストも tsc で落ちる=V-1 と地続き。
- **期待値の出所を分ける**。配線テストは example 一致でよい(検証対象が配線だから)。ロジックテストは独立に計算した期待値で循環を断つ。
- 契約駆動が消すのは「モックと契約の乖離」。**テスト観点の設計まで自動化するものではない**——そこは人の仕事として残る。
