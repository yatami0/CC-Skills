## なぜやるのか — 解こうとしている課題

API の「仕様」と「実装」は、放っておくと **必ずズレる（ドリフト）**。

- BE がレスポンス項目をリネーム → FE は古い項目のまま気づかない
- ドキュメントと実コードが食い違う → レビューで人が目視チェック
- **人の目視は漏れる。漏れたまま本番に出る。**

> 課題：**「正しさ」をレビュー（人の注意力）に依存している**

このPoCの主張：
**正しさを "機械が落とす制約" に寄せる** = 契約を一次情報にし、ズレたらビルドが止まる。

## ① 契約定義 — 人が書くのはここだけ

「動詞（paths）」と「名詞（schemas）」に分けて、人が手で書く。

**paths**（`poc-master-api.yaml`）= エンドポイント
```yaml
/masters/{masterId}/records:
  get:  { operationId: listRecords,  ... }
  post: { operationId: createRecord, ... }
```

**schemas**（`shared/components.yaml`）= データ型
```yaml
MasterRecord:
  required: [id, name, unitPrice, effectiveDate, version]
  properties:
    unitPrice: { type: number, format: double }
    version:   { type: integer }   # 楽観排他
```

<span class="small">`{masterId}` でパラメタライズ＝マスタごとにパスを増やさない。全レスポンスに examples を持たせモック/テストの源泉にする。</span>

---

## なぜ `http/` と `.bundled/` に分かれるのか

| | `contracts/http/` | `contracts/.bundled/` |
|---|---|---|
| 誰が書く | **人**（手書き・正） | redocly が**自動生成** |
| 形 | 分割（paths + schemas） | 1ファイルに統合 |
| git | コミットする | **gitignore**（中間物） |

- `poc-master-api.yaml` は別ファイルを `$ref` で跨ファイル参照している
- orval は跨ファイル `$ref` の解決が不安定 → **一度1ファイルに展開してから渡す**
- `.bundled/` は消して作り直すビルド成果物。真実は常に `http/` 側

## ② orval が生成するもの（2種類・中身）

### (A) `model/*.ts` — 型（schemas → interface）
```ts
export interface MasterRecord {
  id: string;
  name: string;
  unitPrice: number;      // ← yaml の unitPrice
  effectiveDate: string;
  version: number;
}
```

### (B) `poc.ts` — API を叩く唯一の経路（paths → 関数）
```ts
export const updateRecord = async (masterId, id,
  updateRecordRequest: UpdateRecordRequest) => {   // 引数も型付き
  const res = await fetch(...,
    { method: "PUT", body: JSON.stringify(updateRecordRequest) });
};
```

<span class="small">生 fetch を自分で書かない＝経路が1本に固定される（将来の越境検知 V-2 の布石）。</span>

---

## ② 賢いところ：ステータスで判別する応答型

orval は応答を **HTTPステータスで判別できるユニオン型**にする。

```ts
export type updateRecordResponse =
  | { data: MasterRecord;  status: 200; ... }            // 成功
  | { data: ErrorResponse; status: 400|403|404|409; ... }; // 失敗
```

消費側で `status` を見るだけで `data` の型が自動で絞り込まれる：

```ts
const res = await updateRecord(masterId, id, body);
if (res.status === 200) {
  res.data; // ← ここでは MasterRecord 型に確定
}
```

## ③→④ 消費コードへのつながり

生成物を features 層 `recordsView.ts` が import し、**契約由来の項目に静的依存**する。

```ts
import { listRecords, updateRecord } from "@poc/api-client/generated/poc";
import type { MasterRecord } from "@poc/api-client/generated/model/masterRecord";

export function summarize(rec: MasterRecord): string {
  const price: number = rec.unitPrice;     // ← 契約項目に直接依存
  return `${rec.name} = ${price} (v${rec.version})`;
}
```

> ここが意図的に作られた **「破壊が現れる場所」**。
> 契約の項目が消えれば、このファイルが型エラーになる。

---

## ⑤ 機械ゲート ① — `tsc --noEmit`（V-1の主役）

仮説：**人が契約を変える → 再生成 → 消費コードが止まる**

```text
contracts の unitPrice を unitPriceJpy にリネーム（人）
  → pnpm codegen
      → model の interface から unitPrice が消える（機械）
  → pnpm typecheck（tsc strict）
      → recordsView.ts の rec.unitPrice が「存在しない」でエラー（機械が落とす）
```

**消費コードを一切触っていないのに、契約変更だけで型チェックが落ちる。**

## ⑤ 機械ゲート ② — `codegen:check`

`再生成して git diff --exit-code`。2つのズレを検知する：

1. **契約を変えたのに再生成し忘れた** → generated が古く diff が出る
2. **generated を手で改変した** → 再生成で戻り diff が出る

そのために生成物は**あえて gitignore せずコミット**する。
<span class="small">（比較対象が無いと diff チェックが空振りするため）</span>

| script | 役割 |
|---|---|
| `pnpm codegen` | bundle → orval → prettier |
| `pnpm codegen:check` | 再生成して差分ゼロを検証 |
| `pnpm typecheck` | `tsc --noEmit`（strict）= V-1 の機械ゲート |

## デモ：破壊テスト

```bash
# (0) ベースラインをコミット（diff比較の基準）
git add -A && git commit -m "baseline (green)"

# (1) 契約 yaml だけ改変
#     MasterRecord.unitPrice → unitPriceJpy にリネーム

# (2) 再生成 → 型チェック
pnpm codegen
pnpm typecheck
#   期待：非ゼロ終了。消費コード未編集なのに止まる
#   TS2551: Property 'unitPrice' does not exist on type 'MasterRecord'

# (3) 復帰
git checkout -- contracts/http/shared/components.yaml
pnpm codegen && pnpm typecheck   # 緑に戻る
```

## 実測結果

| ステップ | typecheck 終了コード |
|---|---|
| ベースライン | **`0`（緑）** |
| `unitPrice` リネーム後 | **`2`** … TS2551 Property 'unitPrice' does not exist |
| 復帰後 | **`0`（緑）** |

別の破壊例：`UpdateRecordRequest` から `version` を削除すると、
`bumpPrice` が渡す object literal が **必須プロパティ欠落でコンパイルエラー**
→ 楽観排他項目の契約逸脱も検知できる。

> **仮説は実証された。** 契約と実装のドリフトを、機械（型チェック）が確実に落とす。

## V-1 で言えること / まだ無いもの

| 段 | V-1 で実装済み | V-1 ではまだ無い |
|---|---|---|
| 契約 | OpenAPI（paths + schemas） | CSV用 JSON Schema（V-4） |
| 生成 | TS型 + fetch client | MSWモック(V-3) / Java IF(双方向) |
| 消費 | features の recordsView.ts | 実画面・ui-engine（V-5） |
| ゲート | tsc / codegen:check | dependency-cruiser / ArchUnit（V-2） |

V-1は **「契約 → TS型 → 消費 → 型チェックで落ちる」縦1本の循環**を、
実際に動く形で固めた段階。

## codegen ツール選定の記録

| 項目 | 採用 | 理由 |
|---|---|---|
| ツール | **orval 7.21.0** | OpenAPI→型+client を一括生成。examples をモック源泉に流用可 |
| client | `fetch` | 純TSで tsc だけで完結。react-query 依存を持ち込まない |
| mode | `single` | 生成物が1ファイルで diff がクリーン |
| mock/zod | off | スコープ外。examples 保持済みで**1スイッチで後付け可** |
| ref解決 | redocly bundle 前段 | 跨ファイル `$ref` の不具合を回避 |

<span class="small">検証時：orval 7.21.0 / typescript 5.9.3 / @redocly/cli 1.34.15 / Node 24 / pnpm 10</span>

## まとめ & 次の一歩

**V-1 で示せたこと**
- 契約を一次情報にし、そこから型・clientを生成
- 契約を変えるだけで、消費コードがコンパイルエラーで止まる
- ドリフト検知が「人のレビュー」から「機械のゲート」へ移った

**次の一歩（構造を変えず "足す" だけ）**
- `mock: false → true` で MSWモック並行開発（V-3）
- Java codegen を足して V-1 を**双方向**に
- dependency-cruiser / ArchUnit で越境検知（V-2）

<span class="small">本PoCは原則使い捨て。持ち越すのは「契約の書き方・codegen設定・破壊テスト手順」。</span>
