# V-2 基本設計 — 越境・改変の機械検知

> 親設計: [doc/v-1/基本設計.md](../v-1/基本設計.md) §1 検証項目表・§5.4 破壊テスト表。
> 本書はそのうち **V-2** を、この TS 縦切り PoC で実装した範囲の設計を記す。

## 1. V-2 の検証項目と合格基準

| # | 検証項目 | 合格基準 |
|---|---|---|
| V-2 | 越境・改変の機械検知 | 生fetch直書き／レイヤ違反／`generated/` 手書き改変が**CIで落ちる** |

判定は「人がレビューで気づく」ではなく「機械(lint/構造解析/差分)が**非ゼロ終了で落とす**」で行う。V-1(契約→codegen 破壊検知)が「契約と実装のドリフト」を機械化したのに対し、V-2 は「**実装側の配線ミス(経路逸脱・層の逆流・生成物の手書き改変)**」を機械化する。

## 2. スコープと割り切り（前提の明示）

- 本 PoC は **TS(フロント側)に集中**(V-1 と同じ)。よって V-2 も **TS 世界の越境検知**を実装する。
  - **ESLint** … 生fetch直書きを構文レベルで禁止
  - **dependency-cruiser** … レイヤ依存方向・生成物直参照などモジュール境界を禁止
- 親設計 §2.2 / §5.4 が挙げる **ArchUnit(Java レイヤ・生成IF implements 強制)は対象外**。Java 世界(services/master/api)はこの縦切りに未実装のため(V-1 のTS-only と同じ割り切り)。Java codegen を足す段で同形に追加する(親設計 §9 拡張パス)。
- `generated/` 手書き改変の検知は **V-1 の `codegen:check`(再生成→`git diff --exit-code`)が既に担う**。V-2 で新設はせず、ゲート一覧に位置づけ直すのみ。

## 3. 守る境界（依存方向）

```text
app(ルーティング/BFF入口)  →  features(オーケストレーション)  →  @poc/api-client(生成・唯一の経路)  →  [BE]
```

一方向。逆流・近道・別経路をすべて機械で塞ぐ。

| 規約(不変条件) | 何を防ぐか | 強制手段 |
|---|---|---|
| 生 fetch / XHR / WebSocket を書かない | 生成クライアントを迂回した直接通信 | ESLint(`no-restricted-globals` / `-syntax`) |
| http クライアントライブラリ(axios 等)を import しない | 別経路の混入 | ESLint(`no-restricted-imports`)＋ dependency-cruiser(`no-http-client-libs`) |
| `app` は `features` 経由でのみ API へ到達 | 層を飛ばした近道(app→api-client 直叩き) | dependency-cruiser(`app-must-go-through-features`) |
| `features` は `app` を参照しない | 依存方向の逆流 | dependency-cruiser(`features-no-reverse-to-app`) |
| `@poc/api-client` は `services/` を参照しない | 共通層→消費側 の逆流 | dependency-cruiser(`api-client-stays-common`) |
| `generated/` に触れるのは api-client 自身と features のみ | 生成物への無秩序な直参照 | dependency-cruiser(`generated-only-via-sanctioned-consumers`) |
| 循環依存なし | 層の独立性崩壊 | dependency-cruiser(`no-circular`) |
| `generated/` の手書き改変 | 生成物の逸脱 | `codegen:check`(V-1) |

## 4. 実装した構成

```text
contracts_poc/
├ eslint.config.js              ← 新規。生fetch/http直書き禁止(消費側 web のみ対象)
├ .dependency-cruiser.cjs       ← 新規。レイヤ依存方向・生成物直参照を禁止
├ package.json                  ← scripts に lint / depcruise / verify を追加
└ services/master/web/src/
  ├ app/                        ← 新規。ルーティング/BFF入口の代役(features へ委譲するだけ)
  │ └ recordsRoute.ts
  └ features/masterRecords/
    └ recordsView.ts            ← 既存。api-client 経由でのみ API に触れる(V-1 から継続)
```

- `app/` 層を新設したのは「**層の方向を機械で検証できる対象**」を作るため。V-1 時点では `features/` 単層で逆流を試せなかった。
- `eslint.config.js` の対象は `services/master/web/src/**` のみ。生成 `api-client` は **唯一 fetch を持ってよい正規の経路**なので除外している(`packages/api-client/src/generated/**` は ignore)。

## 5. ゲートとスクリプト

| script | 役割 | V |
|---|---|---|
| `pnpm lint` | ESLint。生fetch/http直書きを検知 | V-2 |
| `pnpm depcruise` | dependency-cruiser。レイヤ違反・生成物直参照を検知 | V-2 |
| `pnpm codegen:check` | 再生成→`git diff --exit-code`。生成物のドリフト/手書き改変を検知 | V-1 |
| `pnpm typecheck` | `tsc --noEmit`(strict)。契約→消費の型破壊を検知 | V-1 |
| `pnpm verify` | 上記4つを順に実行(= ローカルの CI 相当) | V-1+V-2 |

> 注: `verify` を `ci` という名前にすると `pnpm ci`(pnpm 組み込みの clean install)と衝突して落ちる。`pnpm run ci` なら動くが、誤用を避けるため **`verify`** にしている。

## 6. 破壊テスト（V-2 の主役）

意図的に違反を起こし、機械が非ゼロ終了で落とすことを確認する。各テストは一時ファイルを作り、ゲートを走らせ、削除して緑に戻す。実測値は [検証メモ.md](検証メモ.md) を参照。

| # | 違反操作 | 落とすゲート | 期待 |
|---|---|---|---|
| A | `features` に生 `fetch()` を直書き | `pnpm lint` | `no-restricted-globals` / `-syntax` でエラー、非ゼロ終了 |
| B | `app` が `@poc/api-client/generated/*` を直 import | `pnpm depcruise` | `app-must-go-through-features` ＋ `generated-only-via-sanctioned-consumers` |
| C | `features` が `app/*` を逆 import | `pnpm depcruise` | `features-no-reverse-to-app` |
| D | `generated/` を手で書き換え | `pnpm codegen:check` | 再生成で戻り `git diff` が出て非ゼロ終了(V-1) |

## 7. 設計上の判断（記録）

- **ESLint と dependency-cruiser の役割分担**: 生 `fetch` は「グローバル呼び出し」でモジュール依存ではないため dependency-cruiser では捕まえられない → ESLint(構文)担当。層の依存方向・生成物の直参照は「モジュール間の辺」なので dependency-cruiser 担当。親設計 §5.4 が「ESLint/dependency-cruiser」と両者を併記しているのはこの分担による。
- **エイリアス解決**: dependency-cruiser は `options.tsConfig` で `tsconfig.json` の `paths`(`@poc/api-client/*` → `packages/api-client/src/*`)を解決してから判定する。よって消費側の `@poc/api-client/generated/poc` 参照は実ファイル `packages/api-client/src/generated/poc.ts` として境界判定される。
- **生成物を gitignore しない**(V-1 から継続): `codegen:check` の `git diff --exit-code` は tracked ファイルのみ比較するため、生成物をコミットしておくことが D の前提。
- **flat config / 非型情報 lint**: V-2 のルールはすべて構文・import 名ベースで判定できるため、`parserOptions.project`(型情報付き lint)は使わず軽量構成にしている。

## 8. この PoC で「言えること / まだ無いもの」

| | V-2 で実装済み | まだ無い |
|---|---|---|
| 生fetch直書き | ESLint で検知(TS消費側) | — |
| レイヤ違反 | dependency-cruiser で検知(app/features/api-client) | Java レイヤ(ArchUnit) |
| 生成物改変 | `codegen:check`(V-1 継続) | Java 生成IF の implements 強制(ArchUnit) |

V-2 は「実装側の配線を、人のレビューではなく機械(lint/構造解析)が落とす」縦1本を、実際に動く形で固めた段階。Java 世界は同じ思想を ArchUnit で同形に足す(親設計 §9)。

## 9. FE層の役割とBFF（前提整理）

V-2 が守る依存方向 `app → features → BFF → @poc/api-client` の各層が「何をする層か」を確定させる。親設計 §3 / §4.2 の補足。

### 9.1 層ごとの責務

```text
ブラウザ
  → app/      (薄いルーティング)
  → features/ (画面オーケストレーション・UI＋ロジック)
  → BFF       (Route Handler = サーバ側の縁。整形・トークン受け渡しのみ)
  → @poc/api-client (契約から生成・BEへの唯一の経路)
  → Spring Controller → Service(認可・業務) → Mapper → DB
```

| 層 | 責務 | 入るもの | 入れないもの |
|---|---|---|---|
| `app/` | 薄いルーティング。URL と feature を繋ぐだけ | `page.tsx` / `layout.tsx`(featureを呼ぶだけ) | 業務ロジック・fetch |
| `features/` | 画面オーケストレーション。画面単位で一式まとめる(コロケーション) | 画面固有 `components/`・`hooks/`・段取りロジック | マスタ個別の画面コード(ADR-0003)・生fetch |
| `BFF` | サーバ側の縁。整形・トークン受け渡しのみ | Route Handler(`app/api/.../route.ts`) | 業務ロジック・**認可判定**(BE Service層のみ／ADR-0008)・生fetch |
| `@poc/api-client` | 契約から生成された BE への唯一の扉 | 生成された型付き fetch 関数 | 手書き改変(ADR-0009) |

- **薄いルーティング**とは「URLを受けて feature を描画するだけ、ロジックもfetchも持たない」こと。
- **features は UI もロジックも両方入る**。「この画面に必要なのは meta + records、取って ui-engine に渡す」という段取り役。実際の描画は `packages/ui-engine`(メタ定義駆動／V-5)に委譲する。

### 9.2 BFF の役割

BFF の仕事は「**整形・トークン受け渡しのみ**」(親設計 §3)に限定する。

- **やること**: トークン注入(ブラウザにBEトークンを持たせず、サーバ側でJWTを付けてBEを叩く)、軽い整形
- **やらないこと**: 業務ロジック・認可判定(BE Service層のみ／ADR-0008)

### 9.3 fetch は生成 → BFF はグルーコード

fetch の実体(HTTP・型・ステータス判別)は全部 api-client に生成済みなので、BFF は自分で fetch を書かない:

```ts
// BFF: app/api/masters/[masterId]/records/route.ts のイメージ
import { listRecords } from "@poc/api-client/generated/poc";

export async function GET(req, { params }) {
  const token = await getToken(req);              // ① トークン用意(サーバ側だけ)
  const res = await listRecords(params.masterId,  // ② 生成モジュールを呼ぶだけ
    { page: 1, size: 20 }, { headers: { Authorization: token } });
  return Response.json(res.data);                  // ③ 返すだけ
}
```

→ BFF =「トークン付与 + 生成モジュール呼び出し + 返す」のグルー。これが **V-2 で生fetchを禁止した狙い**そのもの。BFFですら生fetchを書かせず、必ず生成 api-client を通させ「BEへの扉は契約由来の1枚だけ」を強制する。

### 9.4 contracts を頂点とした自動同期

```text
contracts(OpenAPI=正) ──codegen──▶ api-client(型付きfetch) ──▶ BFF/features が呼ぶだけ
```

- 各層(features/BFF)は **contracts を直接知らない**。生成された api-client を呼ぶだけ。
- 契約を変える → api-client が再生成 → **呼び出し箇所が型エラーで落ちる**(V-1)。
- つまり「契約を頂点に下流が自動同期し、ズレたら機械が落ちる」。BFFもfeaturesもこの仕組みに**ぶら下がるだけ**で、独自に契約と整合を取る作業が要らない。

### 9.5 Next.js のクライアント / サーバ実行（Route Handler と SSR）

肝は「importする場所」ではなく「**コードがどこで実行されるか(ブラウザ or サーバ)**」。

| 種別 | 実行場所 | 秘密(トークン)を持てるか | 役割 |
|---|---|---|---|
| Server Component | サーバ(Node)のみ | ○ 持てる(ブラウザにJSとして送られない) | サーバ側で api-client を直接呼べる |
| Client Component(`"use client"`) | ブラウザでも動く | ✗ 書くと漏れる | state / onClick など対話的UI |
| Route Handler(`app/api/.../route.ts`) | サーバのみ | ○ | URLで叩けるサーバ側HTTPエンドポイント = **BFF** |

- **SSR** = サーバ側でHTMLを先に作って返すこと。Server Component の描画はサーバ実行(=SSR文脈)。
- BEトークンのような**ブラウザに出したくない情報はサーバ側(Server Component / Route Handler)にだけ置く**。ブラウザ(JS)は安全にUIだけ受け取る。
- api-client は単なるモジュール(関数)なので**どちらでも動く**。重要なのは「**サーバ側の実行文脈で呼ぶ**」こと。ブラウザで呼べばトークンが露出する。BFF(Route Handler)は「ブラウザからHTTPで到達できるサーバ側の実行枠」。

### 9.6 「サーバ」が2つある（Next.jsサーバ と Java-BE）

混乱しやすい最大の点。この構成には**サーバが2つ**ある。分けて捉える。

```text
ブラウザ(クライアント)
  ⇅ ① 内部通信(ブラウザ ↔ 自分のNext.js)
Next.jsサーバ   … JS/TS。Server Component・Route Handler(BFF)が動く。"FEのサーバ側"
  ⇅ ② ここで生成 api-client が使われる(contractsが規定する境界)
Java(Spring)サーバ … 本物のBE。業務・認可判定・DBはここだけ(ADR-0008)
```

- **Next.jsサーバ** = 「FEの一部だがサーバで動く部分」。BEではない。トークン注入・整形をやる薄い縁(BFF)。
- **Javaサーバ** = 本物のBE。業務ロジック・認可・DBはここだけ。
- **contracts が規定するのは ② の Next.js → Java 間**のインターフェース。①(ブラウザ↔Next.js)は内部通信であり契約の対象外。
- だから BFF は「ブラウザと Java-BE の間に立つ、サーバで動く FE 側の中継」。Javaが別言語で存在することと矛盾しない。むしろ「ブラウザに秘密を出さず、契約(api-client)経由でだけ Java を叩く」ための関所が BFF。

### 9.7 トークンの流れ（方向に注意）

トークンは**ブラウザから BFF へ渡すのではない**。渡した時点でブラウザが秘密を持ってしまう。正しくは「**最初からサーバ側にだけ存在し、ブラウザは触らない**」。

```text
ブラウザ:「records ちょうだい」(トークンは知らない)
   ↓ ① HTTP
BFF(サーバ): 自分でトークンを用意 → api-client に付けて Java-BE(②) を叩く → 結果だけ返す
```

- ログイン後のトークン(やAPIキー)はサーバ側に保持し、ブラウザのJSからは読めない形(例: httpOnly cookie)にする。
- ブラウザは httpOnly cookie を「持って自動送信」はしても、**JSから中身を読めない**。だから露出しない。
- 結果として「BFF(サーバ)= 秘密を扱う / ブラウザ(JS)= 安全にUIだけ」という分担が成立する。

### 9.8 今の PoC とのズレ（BFF 未分離）

設計は `features → BFF → api-client` の4段だが、**現状の PoC は BFF を独立させていない**。`features/masterRecords/recordsView.ts` が直接 api-client を叩いており、BFF の役割を features が兼ねている(= Server Component がサーバ側で api-client を直接呼ぶ、というもう一つの正しい実現形)。V-2 の検証(一方向＋API経路1本)はこの簡略形で成立する。BFFを独立させる場合は §9.3 の Route Handler を新設し、dependency-cruiser の `generated-only-...` を「generated に触れてよいのは BFF のみ」へ締め直す。
