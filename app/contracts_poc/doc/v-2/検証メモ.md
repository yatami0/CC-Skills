## 破壊テスト（機械が落とすことの確認）

各テストは一時ファイルを作成 → ゲート実行 → 削除して緑へ復帰。

### A. 生 fetch 直書き（features 層） → `pnpm lint`

```ts
// services/master/web/src/features/masterRecords/__bad_fetch.ts
export async function badRawFetch(masterId: string): Promise<unknown> {
  const res = await fetch(`/api/masters/${masterId}/records`);
  return res.json();
}
```

実測: **lint 終了コード `1`**、エラー2件
- `no-restricted-globals`：Unexpected use of 'fetch'.
- `no-restricted-syntax`：生fetch直書き禁止。

### B. app が generated を直接 import（層飛ばし） → `pnpm depcruise`

```ts
// services/master/web/src/app/__bad_direct.ts
import { listRecords } from "@poc/api-client/generated/poc";
export const direct = listRecords;
```

実測: **depcruise 終了コード `2`**、違反2件
- `generated-only-via-sanctioned-consumers`：app → packages/api-client/src/generated/poc.ts
- `app-must-go-through-features`：app → packages/api-client/src/generated/poc.ts

### C. features が app を逆 import（方向逆流） → `pnpm depcruise`

```ts
// services/master/web/src/features/masterRecords/__bad_reverse.ts
import { getRecordsRoute } from "../../app/recordsRoute";
export const reverse = getRecordsRoute;
```

実測: **depcruise 終了コード `1`**、違反1件
- `features-no-reverse-to-app`：features → app/recordsRoute.ts

### D. generated 手書き改変 → `pnpm codegen:check`（V-1 から継続）

生成物を手で編集 → 再生成で上書きされ `git diff --exit-code` が非ゼロ。V-1 検証済みのため V-2 では再掲のみ。

## 持ち越す知見（本番へ）

- 生 fetch は構文(ESLint)、層の辺はモジュール解析(dependency-cruiser)、と**検知器を性質で分ける**。1ツールに寄せない。
- dependency-cruiser は `options.tsConfig` を渡せば paths エイリアスを解決して境界判定できる。本番のモノレポでも同手法でアプリ間直接参照(`import/no-restricted-paths` 相当)を機械化できる。
- 集約スクリプト名に `ci` は使わない(`pnpm ci` が組み込み clean install と衝突)。`verify` 等にする。

## BFF構成の検討と決定（Model B を採用）

V-2 実装後、「BFFを独立させて設計(app→features→BFF→api-client の4段)に忠実にすべきか」を議論した。結論として **Model B（BFF未分離）のまま進める**と決定。

### 前提整理：混同しやすい2軸（独立している）

| 軸 | 何を決める | コントロール | 強制 |
|---|---|---|---|
| ① 層(フォルダ) | 依存方向・整理 | `app/` `features/` `BFF` のどこに置くか | dependency-cruiser(V-2) |
| ② 実行場所 | サーバ実行かブラウザ実行か | `"use client"` の有無 | Next.js ビルド |

- この2軸は**直交**。「app/=サーバ、features/=クライアント」のようなフォルダ⇔実行場所の固定対応は**ない**。
- App Router は **デフォルトが Server Component(サーバ実行=SSR)**。`page.tsx`/`layout.tsx` がサーバで動くのは正しい挙動で、問題ではない。対話が要る部分だけ `"use client"` でブラウザ側へ引き剥がす。

### Server / Client コンポーネントの振り分け基準

| Server(デフォルト) | Client(`"use client"`) |
|---|---|
| page.tsx / layout.tsx、秘密(トークン)を使う処理、api-client を呼ぶデータ取得、静的UI | useState/useEffect、onClick/onChange、フォーム入力(RHF)、window/localStorage、Context Provider |

判断基準:「秘密を触る / データ取得 → サーバ」「ユーザー操作・state が要る → クライアント」。迷ったらサーバ、対話が必要な所だけクライアントへ。

### Model A vs Model B

| | Model A: Route Handler を BFF として独立 | Model B: Server Component が api-client を直接呼ぶ(採用) |
|---|---|---|
| 経路 | features(Client) → `app/api/.../route.ts`(BFF/Server) → api-client → Java | features の Server 実行部が api-client を直接呼ぶ → Java |
| 設計図忠実度 | 高(4段そのまま) | 中(BFF役を features のサーバ部が兼ねる) |
| HTTPホップ | browser→自BFF の内部fetchが増える | 余計なホップなし |
| 留意点 | 内部fetch(自Next.jsサーバ宛)は BE への生fetch とは別物。ESLint に例外設計が要る | idiomatic な現代 Next.js。トークンはサーバに留まる |

### 採用理由（Model B）

- 本 PoC はマスタCRUD縦1本。Model B でも V-2 の設計思想（**API経路は生成 api-client の1本／秘密はサーバ側に留める**）は満たせる。
- Model A は「外部システムも同APIを叩く」「複数FEで共有する」等の動機がある時に効くが、本 PoC にその要件はない。余計な内部HTTPホップと ESLint 例外設計のコストに見合わない。
- 「BFF」は独立フォルダではなく **features 内のサーバ実行部分**として存在する、という整理で運用する。

> Model A を採る場合の差分: `app/api/.../route.ts` を新設し api-client 呼び出しをそこへ集約 → dependency-cruiser の `generated-only-...` を「generated に触れてよいのは BFF のみ」へ締め直し → ESLint に「自BFFへの内部fetchは許容」例外を追加。本 PoC ではスコープ外とする。
