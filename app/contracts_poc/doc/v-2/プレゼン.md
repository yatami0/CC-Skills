## 「経路の逸脱」も人ではなく機械が落とす

<span class="small">contracts_poc / dependency-cruiser + ESLint / TypeScript</span>

## V-1 のおさらい — どこまで来たか

V-1 は **「契約と実装のドリフト」** を機械が落とすところまでを固めた。

```text
契約yaml を変更 → 再生成 → 消費コードが tsc で止まる
```

| ゲート | 検知するズレ |
|---|---|
| `tsc --noEmit` | 契約の型変更 → 消費コードのコンパイルエラー |
| `codegen:check` | 生成し忘れ / `generated/` の手書き改変 |

> だが V-1 は「**契約と型の一致**」しか見ていない。
> 型が合っていても、**実装の"配線"はいくらでも踏み外せる。**

---

## V-2 が解こうとする課題 — 配線は踏み外せる

生成 api-client を用意しても、人は経路を**迂回・逆流・改変**できてしまう:

- api-client を無視して **生 `fetch()` を直書き** → 経路が二重化、契約の外へ
- 層を飛ばして **app から直接 api-client を叩く** → 依存方向が崩れる
- **`generated/` を手で修正** → 契約と生成物が乖離

> これらは **型チェックを素通りする**（型は合っているから）。
> 結局「人のレビューで気づく」に戻ってしまう。

**V-2 の主張：実装側の"配線ミス"も、機械が落とす制約に寄せる。**

---

## V-2 で検証する仮説（合格基準）

| # | 検証項目 | 合格基準 |
|---|---|---|
| **V-2** | 越境・改変の機械検知 | 生fetch直書き／レイヤ違反／`generated/`手書き改変が **CIで落ちる** |

判定は「人が読んで確認」ではなく **「機械が非ゼロ終了で落とす」** で行う。

<span class="small">※ 親設計 §5.4 が挙げる ArchUnit(Javaレイヤ) は Java世界が未実装のため対象外。本PoCは V-1 と同じく TS世界に集中し、Java は同形で後付けする前提。</span>

## 鍵は「2つの番人」を性質で分けること

踏み外しには2種類あり、**検知器も2つ**要る。

| 違反の性質 | 例 | 番人 |
|---|---|---|
| **1ファイルの構文** | `fetch()` を書く | **ESLint** |
| **モジュール間のグラフ** | 層を飛ぶ・逆流・循環 | **dependency-cruiser** |

> 生 fetch は「グローバル関数の呼び出し」＝**依存(import)ではない**ので
> dependency-cruiser では捕まえられない。
> 逆に「層の方向」は1ファイルを見ても分からない＝ESLint では苦しい。

**だから両方使う。** 親設計が「ESLint/dependency-cruiser」と併記する理由。

---

## なぜ ESLint だけでは縛れないのか

ESLint は **1ファイルの AST** しか見ない。dependency-cruiser は **プロジェクト全体の依存グラフ**を作る。

| 縛りたい性質 | 種類 | ESLint | dependency-cruiser |
|---|---|---|---|
| `fetch()` を書くな | 1ファイルの構文 | ✅ 得意 | ✗ 依存ではない |
| 層 A→B 禁止（方向） | グラフの辺 | △ plugin | ✅ `from`/`to` |
| 循環依存 A→…→A | グラフの閉路 | ✗ 実質不可 | ✅ `circular` |
| 到達可能性・孤立コード | グラフの連結性 | ✗ | ✅ `reachable` |

> 「方向・循環・到達」は**グラフ全体を見ないと判定できない性質**。
> これが dependency-cruiser を別途使う必然性。

## dependency-cruiser とは — 1エンジン2出口

公式タグライン: **"Validate and visualise dependencies. With your rules."**

## ルールはこう書く（実設定）

`.dependency-cruiser.cjs` の forbidden ルール。`severity: "error"` が **CIを落とす**。

```js
{ name: "app-must-go-through-features", severity: "error",
  from: { path: "^services/master/web/src/app/" },  // app から
  to:   { path: "^packages/api-client/" }}          // api-client 直叩き → 禁止

{ name: "features-no-reverse-to-app", severity: "error",
  from: { path: "^.../features/" },                 // features から
  to:   { path: "^.../app/" }}                      // app へ逆流 → 禁止

{ name: "no-circular", severity: "error",
  from: {}, to: { circular: true }}                 // 循環 → 禁止（ESLint不可）
```

<span class="small">`options.tsConfig` を渡すと `@poc/api-client/*` エイリアスを実ファイルに解決してから判定する。</span>

```js
  "error", { paths: [{ name: "axios", message: "..." }, /* ... */ ] },

```

## デモ：破壊テスト（機械が落とすことの確認）

意図的に違反を作り、ゲートが**非ゼロ終了**で落とすことを確認 → 削除して緑へ。

| # | 違反操作 | ゲート | 実測 終了コード |
|---|---|---|---|
| A | features に生 `fetch()` 直書き | `pnpm lint` | **`1`** |
| B | app が generated を直 import | `pnpm depcruise` | **`2`** |
| C | features が app を逆 import | `pnpm depcruise` | **`1`** |
| D | `generated/` を手で改変 | `pnpm codegen:check` | **非ゼロ**（V-1） |

> err レポータは **error 件数を終了コードに返す**（B=2件→`2` / C=1件→`1`）。
> 1件でも error があれば CI が落ちる。

## ゲートとスクリプト

| script | 役割 | V |
|---|---|---|
| `pnpm lint` | ESLint。生fetch/http直書きを検知 | V-2 |
| `pnpm depcruise` | dependency-cruiser。層違反・循環を検知 | V-2 |
| `pnpm codegen:check` | 再生成→差分。生成物の改変を検知 | V-1 |
| `pnpm typecheck` | `tsc --noEmit`。契約→消費の型破壊 | V-1 |
| **`pnpm verify`** | **上記4つを一括 = ローカル CI 相当** | V-1+V-2 |
| `pnpm depcruise:graph` | 依存グラフを mermaid 出力（可視化） | — |
| `pnpm depcruise:affected` | 変更の影響範囲だけ mermaid 出力 | — |

<span class="small">※ 集約名に `ci` は使わない（`pnpm ci` が組み込み clean install と衝突）。`verify` にする。</span>

## 次の絵：CI/CD で PR コメントに貼る

<div class="mermaid">
flowchart LR
  PR["PR 作成"] --> CI["GitHub Actions"]
  CI --> V["pnpm verify<br/>（落ちたらマージ不可）"]
  CI --> AF["depcruise:affected<br/>変更の影響サブグラフ"]
  AF --> CM["mermaid を PR コメントへ<br/>（GitHubが標準描画）"]
  style V fill:#f9ebea,stroke:#c0392b
  style CM fill:#eaf3fb,stroke:#1a4d7c
</div>

- `--affected`：main 以降に**変更されたモジュール＋それに到達できる全モジュール**を抽出
- レビュー前に「この変更がどこへ波及するか」が一目で分かる

---

## 発展：変更箇所から「PR の重要度」を測る

dependency-cruiser の出口を使い、**PR の重さを機械的に見積もる**:

| 手段 | 何が分かるか |
|---|---|
| `--affected` の規模 | 影響モジュール数が多い＝波及が広い＝レビュー重め |
| `--output-type json` | `api-client` / `contracts` に触れたか → *needs-contract-review* 自動ラベル |
| `--output-type metrics` | instability（不安定度）。安定モジュールを触る PR ほど影響大 |

> 「契約境界に触れる PR は重要度高」を機械判定し、ラベル＋グラフで提示。
> **境界変更を人間レビュー必須にする方針**（親設計 02-api-contract）と噛み合う。

<span class="small">※ ここは構想段階。本PoCのスコープは graph / affected スクリプトまで。</span>

## スコープと割り切り（明示）

| 項目 | 本PoCでの扱い |
|---|---|
| 生fetch直書き | ✅ ESLint で検知（TS消費側） |
| レイヤ違反・循環 | ✅ dependency-cruiser で検知 |
| generated 改変 | ✅ codegen:check（V-1 から継続） |

<span class="small">割り切りは「やらない」ではなく「同じ思想を後で足せる形にしてある」。</span>

## V-2 で言えること / まだ無いもの

| 段 | V-2 で実装済み | まだ無い |

V-2 は **「実装側の配線を、人のレビューではなく機械が落とす」縦1本**を、
実際に動く形で固めた段階。

## まとめ & 次の一歩

**V-2 で示せたこと**
- 生成クライアントを用意しても、人は経路を迂回・逆流・改変できる
- それを **構文の番人(ESLint)** と **グラフの番人(dependency-cruiser)** で機械的に落とす
- 検証と同じ設定から、依存グラフを図としても出せる

**次の一歩（構造を変えず "足す" だけ）**
- GitHub Actions で `verify` をマージ条件化、affected グラフを PR コメントへ
- 変更箇所から PR 重要度を自動判定（契約境界タッチ → レビュー必須）
- Java codegen＋ArchUnit で越境検知を**双方向**に

<span class="small">本PoCは原則使い捨て。持ち越すのは「境界ルールの書き方・2番人の分担・破壊テスト手順」。</span>
