# 引き継ぎ：残りの `00_standards/` 一式を作成する

> **このドキュメントの目的**：別セッションのClaude（または別の人）が読んで、`00_standards/`（第1層・設計書標準）の **残りファイル一式のたたき台** を作成できるようにするための作業指示書。
> **同梱物**：本ファイルと一緒に `design_architecture.md`（第1層の最上位標準・確定済み）を渡している。**それが正本である。** 本ファイルはその作業指示にすぎない。矛盾したら `design_architecture.md` を優先すること。
> **やってほしいこと（1行）**：`design_architecture.md` を読み、そこで「存在することになっている」が「まだ中身が無い」ファイル群のたたき台を作る。

---

## 0. 最初に読むべき要約（30秒で状況を把握する）

- 進行中の作業：複数サイト（A/B/C）を横断する **設計書の標準（第1層）** を確定し、`00_standards/` に置いていく作業。
- 全体構造：設計書は **3層構造**。第1層=標準（サイト非依存・1セット）、第2層=各サイトの設計書、第3層=実ファイル。詳細は同梱の `design_architecture.md`。
- スタック前提：**全サイト Next.js（App Router）+ Java で統一**。モバイルは想定しない。だから **強い標準**（フォルダ番号体系・章立て・フォーマットまで全サイト固定）を採る。
- 既に確定・作成済みのもの：
  - `design_architecture.md`（3層構造・全体方針）★同梱
  - `fe-architecture.md`（FE横断アーキテクチャ標準）★作成済み・**今回の対象外**
  - `be-architecture.md`（BE横断アーキテクチャ標準）★未作成だが**今回の対象外**
  - ADR 6本（設計判断の記録。`adr/` に既存）
- **今回作ってほしいもの（対象）**：`00_standards/` の残り4種。
  - `document_guideline.md`
  - `diagram_format.md`
  - `naming_convention.md`
  - `templates/`（空テンプレート5種）
- 重要な制約：これらは **全サイト共通＝サイト非依存**。特定サイト（特にサイトAのメタデータ駆動・EAV）の事情は **絶対に混ぜない**。混ぜたらこの標準は壊れる。

## 1. ユーザーの根本的なスタンス（これを外すと噛み合わない）

過去セッションから一貫している。応答・成果物は必ずこれに従うこと。

1. **想像で情報を足さない。** 要件・既存資料にないことを勝手に補完しない。必要なら確認する。やむを得ず足すなら「要件にないが論理的に必要」と明示する。
2. **「絶対に必要な情報」だけに絞る。** 判断基準は一貫して次の1つ：
   > それが決まっていないと、2人以上の開発者が別々の実装をしてしまうか？
   > Yes → 標準に書く。No → 別の正本（型定義 / Figma / Storybook / Lint設定）に置く。
3. **概念を整理してから具体に落とす。** 構造・前提を先に。
4. **根拠を求める。** 「なぜこの形か」「手本はあるか」を必ず添える。手本が無いなら「無い」と正直に言う。
5. **二重管理を嫌う。** 正本は1つ。
6. **粒度に厳しい。** 「プロジェクト全体の標準（第1層）」と「特定サイト固有（第2層）」の混同を強く嫌う。発言・成果物がどちらの層の話かを常に明示すること。**これが最大の地雷。**

## 2. 作るもの・詳細指示（4種）

`design_architecture.md` の該当節を正本とし、それを具体化する。各ファイルの冒頭に「第1層（サイト非依存）に属する」旨と判断基準を必ず書くこと。トーンは簡潔、過剰な前置き・装飾を避け、各項目に「なぜ必要か（破綻ライン）」を添える。

### 2-1. `document_guideline.md`（成果物カタログ）
- **役割**：標準フォルダ体系（`design_architecture.md` §4 の01〜10）の各成果物について「何を書くか・何は書かないか」を1枚で示すカタログ。
- **必ず入れる**：各成果物ごとに「目的」「書くこと」「書かないこと（正本の場所）」「使用テンプレート」「使用フォーマット（§5 のどれか）」。
- **粒度の注意**：ここは「どの成果物に何を書くか」の標準。各サイト固有の中身は書かない。FEの実装方式の詳細は `fe-architecture.md` に委譲し、ここからは参照に留める（二重管理しない）。
- **手本対応**：フューチャーのフォルダ階層・各設計書サンプルが下敷き。FE記載境界（見た目はFigma、APIやイベントやバリデーションを書く）を踏襲。

### 2-2. `diagram_format.md`（図フォーマット詳細）
- **役割**：`design_architecture.md` §5.1 を具体化。どの図に何のツールを使い、どう書くか。
- **必ず入れる**：用途別ツール表（シーケンス/状態遷移/ER → PlantUML テーマ`toy`、複雑な構成図 → draw.io の `.drawio.png/.jpg/.svg`、代替 Mermaid）。各ツールの最小サンプル。ファイル配置・命名（図ファイルをどこに置くか）。色使いの方針（フューチャーは色を多用しない）。
- **手本対応**：フューチャーの「システム構成図」節をそのまま下敷きに。PlantUMLのテーマ指定は必須。
- **想像で足さない**：フューチャーに無いルール（例：図のレビュー手順）は勝手に作らない。必要そうなら「要確認」として印を付ける。

### 2-3. `naming_convention.md`（命名規約）
- **役割**：フォルダ番号・ファイル名・各種ID（画面ID等）の命名を統一。
- **必ず入れる**：
  - フォルダ番号規約（`01_` 形式、番号に体系を持たせず必要時インクリメント、固有成果物は番号挿入可。ずれ容認）。
  - 設計書ファイル名規約（例：`screen-SC-001.md` / `api-*.md` 等。実際のパターンは `design_architecture.md` と既存ファイルから抽出）。
  - 画面ID等のID体系（`SC-001` のような採番。プレフィックスの意味）。
  - FE側の命名は `fe-architecture.md` §9 に既にある → **重複定義せず参照**。ここでは「設計書ドキュメント側の命名」を扱い、コード側はFE標準に委譲する（二重管理回避）。
- **粒度の注意**：ID採番ルールは標準として固定するが、具体の画面名・マスタ名はサイト固有なので書かない。

### 2-4. `templates/`（空テンプレート5種）
- **役割**：第3層の実ファイルを作るときに複製する空のひな形。
- **作るファイル**（`design_architecture.md` のリポジトリツリーに準拠）：
  - `screen-list.md`（画面一覧。ID/画面名/URL/描画方式/認証/画面別設計書へのリンクの表）
  - `screen-design.md`（画面別設計書。基本情報/読むデータ/画面遷移/データ状態(loading,empty,error,success)/入力・バリデーション）
  - `api-design.md`（API設計書。openapi.yaml参照＋BL設計＋複数テーブル検索の由来表）
  - `enum-design.md`（区分値。概要〔目的/物理名/型/スコープ frontend,backend/マスターテーブル〕＋定義表）
  - `message-def.md`（メッセージ定義。識別子/レベル(E,W,F)/ステータス/メッセージ/コメント）
- **必ず守る**：各テンプレートは**空のひな形**。サイト固有の中身（サイトAのfield_def等）は入れない。記入箇所は `〔記入〕` で示す。各テンプレ冒頭に「サービス共通設計書は別途参照し重複を書かない」旨の位置づけコメントを付ける。
- **手本対応**：フューチャーの区分値・メッセージ・API応答サンプルのフォーマットを厳守。FE記載境界も反映。

## 3. 守るべきフォーマット（`design_architecture.md` §5 の要点・再掲）

- **図**：PlantUML（テーマ`toy`）/ Mermaid 基本。複雑な構成図は draw.io（`.drawio.png/.jpg/.svg`）。
- **API**：`openapi.yaml` に定義。自明な重複項目は省略。複数テーブル参照の検索APIは由来表（Parameter / Description / Settings / Note）。
- **FE記載境界**：Figmaで判断できる見た目は書かない。API呼び出し・イベント・パラメータ・バリデーション・画面遷移・データ状態を書く。
- **区分値**：概要（目的/物理名/型/スコープ frontend,backend/マスターテーブル）＋表（論理名/物理名/値/バージョン/コメント）。
- **メッセージ**：識別子 / レベル(E/W/F) / ステータス / メッセージ / コメント。`{domain}` のようにプレースホルダを記す。
- **Markdown例外**：項目数が数十以上で保守性が落ちる場合は Excel 等を許容。採用時は当該フォルダ README に明記。

## 4. やってはいけないこと（地雷リスト）

1. **サイト固有を標準に混ぜる。** 特にサイトAのメタデータ駆動・EAV・field_def・data_type解釈。これらは第2層の話。`00_standards/` には一切書かない。
2. **二重管理。** FEの実装方式は `fe-architecture.md` が正本。`document_guideline.md` や `naming_convention.md` で同じことを書き直さず、参照する。
3. **想像で規約を足す。** 手本（フューチャー）に無いルールを勝手に発明しない。必要に見えるものは `〔要確認〕` を付けて残し、ユーザーに確認する。
4. **粒度を曖昧にする。** 各記述が第1層か第2層かを常に意識。曖昧なら書かずに確認。
5. **冗長化。** 長い前置き・過剰なboldや見出しを避ける。要点と「なぜ必要か」を簡潔に。

## 5. 進め方の指定（別セッションのClaudeへ）

1. まず同梱の `design_architecture.md` を通読し、3層構造と §4 フォルダ体系・§5 フォーマットを把握する。
2. 4種を一括で作るが、**作成前に章立て（見出し構成）だけを先に提示**し、ユーザーの合意を取ってから本文を書く（過去セッションでこの進め方が好まれた）。
3. 確認が必要な点は、想像で埋めず選択式で簡潔に問う（会話から推測できないか先に確認する）。
4. 各ファイルは Markdown で作成し、`00_standards/` 配下に置く想定でパスを示す。`templates/` 配下は5ファイル。
5. 図を使う場合は §3 のフォーマット（PlantUML テーマ`toy` 等）を厳守する。
6. 完成物には各ファイルの冒頭に「第1層・サイト非依存」の位置づけと判断基準を明記する。
