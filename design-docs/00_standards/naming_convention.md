# 命名規約（naming_convention）

> **位置づけ：第1層・標準（サイト非依存）。** 設計書ドキュメント側の命名を統一する。コード側の命名は扱わない。
> **判断基準：** フォルダ番号・ファイル名・ID採番が決まっていないと、人により付け方が分かれて参照・採番が破綻する。だから標準化する。
> **対象範囲：** 本ファイルは**設計書ドキュメント側**の命名を扱う。コード側（変数・コンポーネント・ディレクトリ等）の命名は `fe-architecture.md` §9 が正本であり、ここでは重複定義せず参照する（二重管理回避）。

---

## 1. フォルダ番号規約

- フォルダは `NN_名称` 形式（2桁ゼロ埋め + アンダースコア + 日本語名称）。例：`06_画面設計書`。
- 番号は**体系（意味）を持たせず**、並び順を表すだけ。必要時にインクリメントする。
- サイト固有成果物が必要なときは、適切な位置に番号を**挿入**してよい（例：サイトA `07_メタデータ定義設計`）。
- 挿入の結果、以降の番号が標準とずれることは**許容する**（`design_architecture.md` §3 注記）。番号に体系を持たせないため、ずれても破綻しない。
- 標準フォルダ（01〜10）の意味・順序は変えない。追加した固有成果物は第2層に閉じる。

---

## 2. 設計書ファイル名規約

- ファイル名は半角英小文字・数字・ハイフン（ケバブケース）を基本とする。拡張子は `.md`。
- 種別ごとのパターン：

| 成果物 | ファイル名パターン | 例 |
|--------|------------------|-----|
| 画面一覧 | `screen-list.md`（固定） | `screen-list.md` |
| 画面別設計書 | `screen-{画面ID}.md` | `screen-SC-001.md` |
| API設計書 | `api-{機能名}.md` | `api-user-search.md` |
| 区分値設計 | `enum-{物理名}.md` | `enum-user-status.md` |
| メッセージ定義 | `message-def.md`（固定） | `message-def.md` |
| ADR | `ADR-{NNN}-{タイトルをケバブケース}.md` | `ADR-001-repository-structure.md` |

- テンプレート（`00_standards/templates/`）は上表の「固定」名または種別名のひな形であり、複製時に上表の命名へリネームする。
- 具体の機能名・物理名はサイト固有なので本ファイルでは定めない（§5）。

---

## 3. ID体系

### 3.1 画面ID

- 形式：`SC-{連番3桁}`。`SC` は Screen のプレフィックス。例：`SC-001`。
- 連番はサイト内で一意。欠番が出てもよい（再利用しない）。
- 画面IDは `screen-list.md` で採番し、画面別設計書ファイル名（`screen-SC-001.md`）と一致させる。

### 3.2 その他のID

- 区分値・メッセージは ID ではなく**物理名／識別子**で一意化する（区分値＝物理名、メッセージ＝識別子）。フォーマットは `design_architecture.md` §5.4 / §5.5 に従う。
- 〔要確認〕画面ID以外に採番が必要なID（API ID 等）が出た場合のプレフィックス体系は、必要になった時点で本節に追加する。現時点では画面IDのみ規定。

---

## 4. コード側命名の委譲

- FE のコード側命名（コンポーネント名・ファイル名・ディレクトリ構成・Hook 命名等）は `fe-architecture.md` §9 が正本。
- 本ファイルでは**重複定義しない**。設計書からコード側の命名に言及する必要があるときは `fe-architecture.md` §9 を参照する。
- BE のコード側命名は `be-architecture.md` を参照（作成後）。

---

## 5. 適用範囲（標準として固定するもの／書かないもの）

- **固定する（第1層）：** フォルダ番号形式、ファイル名パターン、ID採番ルール（プレフィックスと桁数）。
- **書かない（第2層・サイト固有）：** 具体の画面名・機能名・マスタ名・区分値の物理名そのもの。これらは各サイトが採番ルールに従って付ける。
