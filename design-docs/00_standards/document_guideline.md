# 成果物カタログ（document_guideline）

> **位置づけ：第1層・標準（サイト非依存）。** 本ファイルは全サイト共通の規約であり、特定サイトの業務・方式（例：サイトAのメタデータ駆動・EAV）は一切書かない。
> **判断基準（全記述に適用）：** それが決まっていないと、2人以上の開発者が別々の実装をしてしまうか？ Yes → ここ（標準）に書く。No → 別の正本（型定義 / Figma / Storybook / Lint設定）に置く。
> **正本の所在：** 3層構造とフォルダ体系は `design_architecture.md` が正本。本ファイルはその §4 標準フォルダ体系を「各成果物に何を書くか」の粒度で具体化したカタログである。

---

## 1. このカタログの読み方

各サイト（第2層）は §4 標準フォルダ体系の各成果物を埋める。本カタログは、その各成果物について次の5項目を1枚で示す。

| 項目 | 意味 |
|------|------|
| 目的 | その成果物が存在する理由。これが無いと何が破綻するか。 |
| 書くこと | この成果物に記述する内容。 |
| 書かないこと（正本の場所） | ここには書かず、別の正本を参照する内容。二重管理を避けるため。 |
| 使用テンプレート | 複製元（`templates/` 配下）。無いものは「—」。 |
| 使用フォーマット | `design_architecture.md` §5 のどのフォーマット規約に従うか。 |

> **層を間違えないチェック：** 書こうとしている内容が「全サイト共通」なら標準（第1層）、「特定サイトの業務・方式・構成」なら第2層。本カタログは「どの成果物に何を書くか」の標準であり、サイト固有の中身そのものは扱わない。

---

## 2. 成果物カタログ（標準体系 01〜10）

番号・フォルダ名は `design_architecture.md` §4 に準拠する。サイト固有成果物（例：サイトAの `07_メタデータ定義設計`）は第2層で番号を挿入して追加してよく、本カタログには載せない。

### 01_キャッチアップ
- **目的：** 新規参画者がドメインを理解するための前提知識。これが無いと用語・業務の解釈が人によりずれる。
- **書くこと：** ドメイン知識、業務上の前提、用語集（このサイトで使う語の定義）。
- **書かないこと（正本の場所）：** 実装方式 → `fe-architecture.md` / `be-architecture.md`。画面・APIの仕様 → 各設計書。
- **使用テンプレート：** —
- **使用フォーマット：** 自由記述（図を使う場合は §5.1）。

### 02_環境構築
- **目的：** 誰がやっても同じローカル環境が立ち上がる手順。これが無いと環境差で「動く/動かない」が分かれる。
- **書くこと：** 必要ツール・バージョン、セットアップ手順、起動・確認方法、よくある詰まりどころ。
- **書かないこと（正本の場所）：** 依存バージョンの正本は各リポジトリの設定ファイル（`package.json` 等）。ここからは参照に留める。
- **使用テンプレート：** —
- **使用フォーマット：** 自由記述（手順は番号付きリスト）。

### 03_開発規約
- **目的：** チームの開発プロセスを揃える。これが無いとブランチ運用・リリース手順が人により異なる。
- **書くこと：** Gitフロー、ブランチ命名、レビュー/マージ方針、リリース方式、CI/CD の構成。
- **書かないこと（正本の場所）：** コードのLint/フォーマット規則は Lint設定が正本。命名の詳細は `naming_convention.md`（ドキュメント側）/ `fe-architecture.md` §9（コード側）。
- **使用テンプレート：** —
- **使用フォーマット：** 自由記述。CI/CD のフロー図は §5.1。

### 04_アーキテクチャ
- **目的：** このサイト固有のシステム構成を示す。実装方式の横断ルールではなく、サイト固有の構成だけを扱う。
- **書くこと（サイト固有のみ）：** システム構成図、認証方式、外部連携（連携先・I/F）。
- **書かないこと（正本の場所）：** 実装方式の横断ルール（レンダリング・状態管理・コンポーネント設計・品質ガードレール等）→ 第1層 `fe-architecture.md` / `be-architecture.md` が正本。ここからは参照する。
- **使用テンプレート：** —
- **使用フォーマット：** システム構成図は §5.1（複雑なものは draw.io、詳細は `diagram_format.md`）。

### 05_UI設計
- **目的：** 見た目の正本（Figma）への入口。見た目は設計書で二重管理しない。
- **書くこと：** Figma のパス/リンク、対象画面とFigmaの対応。
- **書かないこと（正本の場所）：** レイアウト・色・余白・文言の見た目 → Figma が正本（§5.3）。
- **使用テンプレート：** —
- **使用フォーマット：** 参照リンクの一覧。

### 06_画面設計書
- **目的：** 画面の振る舞い（API/イベント/バリデーション/状態/遷移）を定義する。これが無いと同じ画面を別の振る舞いで実装してしまう。
- **書くこと：** 画面一覧（`screen-list.md`）と画面別設計書。Web API呼び出し、イベント定義、パラメータ受け渡し、バリデーションロジック、画面遷移、データ状態（loading/empty/error/success）。
- **書かないこと（正本の場所）：** 見た目 → Figma（§5.3）。FEの実装方式（Container/Presenter 等）→ `fe-architecture.md`。
- **使用テンプレート：** `templates/screen-list.md`、`templates/screen-design.md`
- **使用フォーマット：** §5.3（FE記載境界）。図は §5.1。

### 07_API設計書
- **目的：** FEとBEが共有するAPIの正本。これが無いと呼び出し側と実装側のI/Fがずれる。
- **書くこと：** `openapi.yaml`、各BL（ビジネスロジック）設計、複数テーブルを参照する検索APIの項目由来表。
- **書かないこと（正本の場所）：** `openapi.yaml` と重複する自明な項目（リクエストパラメータ・レスポンス項目）はプログラム設計書側で省略（§5.2）。
- **使用テンプレート：** `templates/api-design.md`
- **使用フォーマット：** §5.2（API）。由来表は §5.2 の表。

### 08_データモデル
- **目的：** データ構造の正本。これが無いとテーブル設計・参照が分散する。
- **書くこと：** ERD、テーブル定義。
- **書かないこと（正本の場所）：** 区分値の値そのもの → `09_区分値設計`。メッセージ → `10_メッセージ定義`。
- **使用テンプレート：** —（ERDは §5.1、テーブル定義表はサイトで定義）
- **使用フォーマット：** ERは §5.1（PlantUML/Mermaid）。

### 09_区分値設計
- **目的：** 区分値（ENUM）の唯一の正本。スコープ（frontend/backend）を明記し、FE/BEの食い違いを防ぐ。
- **書くこと：** 概要（目的/物理名/型/スコープ frontend,backend/マスターテーブル）と定義表（論理名/物理名/値/バージョン/コメント）。
- **書かないこと（正本の場所）：** 区分値を参照する画面・APIの挙動 → 各設計書。
- **使用テンプレート：** `templates/enum-design.md`
- **使用フォーマット：** §5.4（区分値）。

### 10_メッセージ定義
- **目的：** エラー/警告メッセージの一元管理。これが無いと同義メッセージが乱立し、文言・識別子が重複する。
- **書くこと：** 識別子、レベル（E/W/F）、ステータス、メッセージ、コメント。プレースホルダは `{domain}` のように記す。
- **書かないこと（正本の場所）：** どの画面でいつ出すか → 各画面設計書から識別子で参照。
- **使用テンプレート：** `templates/message-def.md`
- **使用フォーマット：** §5.5（メッセージ）。

## 3. FE記載境界（参照）

画面設計書（06）での記述境界は `design_architecture.md` §5.3 に従う。

- **書かない：** Figma で判断できる見た目（レイアウト・色・余白・文言の見た目）。
- **書く：** Web API呼び出し、イベント定義、パラメータの受け渡し、バリデーションロジック、画面遷移、データ状態（loading/empty/error/success）。

詳細なFEの実装方式（レンダリング・状態管理・コンポーネント設計）は `fe-architecture.md` が正本。本カタログでは重複定義せず参照に留める。

---

## 4. 固有成果物の追加ルール

- 標準（01〜10）に無い成果物が必要なサイトは、適切な位置に番号を挿入して追加してよい（例：サイトA `07_メタデータ定義設計`）。
- ただし標準フォルダの意味・順序は変えない。番号のずれは許容する（`design_architecture.md` §3 注記）。
- 追加した固有成果物は**第2層に閉じる**。本カタログ（第1層）には載せない。
