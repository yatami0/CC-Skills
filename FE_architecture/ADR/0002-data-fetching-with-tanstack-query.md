# ADR-0002: データフェッチ戦略（TanStack Query へ統一）

- ステータス: Accepted
- 日付: 2026-06-21
- 関連: ADR-0001, ADR-0003, ADR-0004

## コンテキスト

ADR-0001 でクライアントファースト構成を採用した。本 ADR では、サーバー状態（API から取得するデータ）の取得・キャッシュ・更新をどう扱うかを決める。

対象は一覧表示・詳細表示・マスタ更新の CRUD。求められるのは、一覧の再取得、更新後のキャッシュ無効化、リクエストの重複排除、ローディング/エラー状態の一貫した扱いなど、典型的な「サーバー状態管理」である。

データの実体は常に Spring Boot の REST API（HTTP 越し）であり、Next.js はそれを叩く BFF。`fetch` の直書きを各コンポーネントに散らすと、ローディング/エラー処理・キャッシュ・再取得が画面ごとにバラつき、1 名運用 + AI 開発では規約逸脱の温床になる。

なお TanStack Query 公式は「必要になるまで持ち込むな」と戒めている。本件はその戒めに反しないか確認したうえで採否を決める。

## 決定

**サーバー状態の取得・更新は TanStack Query（v5+）に統一する。**

- 取得は `useQuery`、更新系（Create/Update/Delete）は `useMutation` を用いる。
- コンポーネント内での `fetch` 直書き、独自の `useEffect` + `useState` によるデータ取得実装、Server Actions は禁止する（ADR-0004 の lint/規約で機械的に縛る）。
- API を直接叩く層は薄い関数（API クライアント）に閉じ込め、その型は OpenAPI から生成する（ADR-0003）。`useQuery`/`useMutation` はその関数を呼ぶだけにする。

### queryKey 規約

queryKey は構造を固定し、無効化を機械的にする。

```
['masters', masterType, 'list', params]   // 一覧
['masters', masterType, 'detail', id]     // 詳細
```

- `masterType` はマスタ種別の識別子（例: `'product'`, `'customer'`）。
- 更新成功時は `queryClient.invalidateQueries({ queryKey: ['masters', masterType] })` で該当マスタの一覧・詳細をまとめて無効化する。
- 個別最適化（特定の詳細だけ無効化）は必要になってから行う。初期は粒度を粗く保ち、規約を単純にする。

### サーバー連携の方針

- 初期は素直なクライアントサイドフェッチ（マウント時に `useQuery` が走る）とする。
- SSR プリフェッチ（`HydrationBoundary` 経由でサーバーから初期データを流す）は、初回表示パフォーマンスが要件化したときに限り、画面単位で導入する。デフォルトでは持ち込まない。
- 公式ガイドの注意に従い、`queryClient.fetchQuery` はエラー捕捉が必要な場合を除き避ける。その結果をサーバー上でレンダリングしたり、他コンポーネント（Client Component であっても）に渡したりしない。

## 「必要になるまで持ち込むな」への回答

TanStack Query 公式の戒めは「フレームワークのデータ取得手段で足りるなら入れるな」という趣旨である。本件は以下の条件が揃っており、導入の正当性がある側に倒れる。

- BE が別系（Spring Boot）で、データ実体は常に外部 API のため、RSC/fetch キャッシュの「サーバーで直接取得」の旨味が効かない。
- CRUD 中心で、再取得・楽観的更新・キャッシュ無効化といった TanStack Query の中核機能がそのまま要件に対応する。
- 1 名 + AI 開発で、取得処理のパターンを 1 つに固定したい。

## 結果

### 良い影響

- データ取得・更新のパターンが 1 つに固定され、AI も人も同じ書き方になる。
- キャッシュ無効化が queryKey 規約で機械的に決まり、「更新したのに一覧が古い」系のバグを構造的に防げる。
- ローディング/エラー状態の扱いが `useQuery`/`useMutation` の標準 API に揃う。

### 悪い影響・トレードオフ

- ライブラリ 1 つ分の学習コストと依存が増える。ただし CRUD では即座に元が取れる。
- キャッシュという状態が増えるため、「いつ無効化されるか」を規約で明文化しないと、逆に分かりにくくなる。→ 上記 queryKey 規約と「更新後はマスタ単位で invalidate」を必須ルール化して対処する。
- 楽観的更新（optimistic update）は強力だが複雑化要因。初期は導入せず、UX 要件が出てから画面単位で足す。

## 補足: 却下した代替案

- **fetch 直書き + useEffect**: 画面ごとにローディング/エラー/キャッシュがバラつき、1 名 + AI 開発で規約逸脱しやすい。
- **Server Actions / RSC でのサーバー取得**: ADR-0001 の通り、BE が別系のため旨味が薄く、メンタルモデルを二重化する。
- **重量級の状態管理（Redux 等）でサーバー状態を持つ**: サーバー状態はキャッシュであり、クライアント状態管理ライブラリで持つのはアンチパターン。クライアント状態（フォーム入力途中など）が必要になった場合のみ、別途軽量な手段（コンポーネント state / 必要なら Zustand）を検討する。
