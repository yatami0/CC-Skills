# ADR-0005: テスト戦略（Vitest + Playwright）

- ステータス: Accepted
- 日付: 2026-06-21
- 関連: ADR-0002, ADR-0004

## コンテキスト

ADR-0004 で「CI ゲートをエージェントの最終関門にする」と決めた。本 ADR では、何をどのテストで担保するかを定める。

対象は 4〜5 画面の CRUD（一覧 / 詳細 / 更新）。テストは網羅率を追うより、AI のドリフトとリグレッションを止める「検証ゲート」としての費用対効果を重視する。テストはエージェントが最適化すべきシグナル（仕様）でもある。

2026 時点の Next.js コミュニティの定石は、Vitest（単体・コンポーネント）と Playwright（E2E）の二層構成。Jest は Vitest に移行済みで、新規採用は非推奨。

## 決定

**Vitest + React Testing Library（単体/コンポーネント）と Playwright（E2E）の二層構成を採用し、CI ゲートに組み込む。**

### 二層の役割分担

| 層 | ツール | 対象 |
|---|---|---|
| 単体/コンポーネント | Vitest + React Testing Library | ロジック、Zod スキーマ、Client Component、フォームのバリデーション挙動 |
| E2E | Playwright | 各画面の CRUD ハッピーパス（一覧→詳細→更新→再取得の一連フロー） |

- 単体テストの環境は `jsdom` を明示する（Next.js は Vite-native でないため）。Vitest 設定は `@vitejs/plugin-react` + `jsdom`。
- E2E は本番ビルド（`next build` + `next start`）に対して実行する。`next dev` はホットリロード等で挙動が異なり flaky の原因になるため使わない。
- Playwright のロケータは `getByRole` / `getByLabel` 等の意味ベースを優先し、CSS セレクタ依存を避ける。

### スコープの指針（4〜5 画面向け）

- **必ず E2E で押さえる**: 各マスタの「一覧表示 → 詳細表示 → 更新 → 一覧へ反映（再取得）」のハッピーパス。これが壊れると業務が止まるため最優先。
- **Vitest で押さえる**: フォームのバリデーション（必須・形式エラー）、Zod スキーマ、一覧のフィルタ/ソートのロジック。
- **当面追わない**: ビジュアルリグレッション（フォント描画で flaky になりやすい）、CSS/レイアウトの厳密検証。網羅率の数値目標も初期は強制しない（重要フローのカバーを優先）。

### API のモック方針

- E2E では Spring Boot 実体に依存せず、Playwright のリクエスト傍受で API レスポンスをモックし、フロントの状態遷移を決定的にテストする。これにより BE の可用性やデータ状態に E2E が左右されない。
- 単体テストでは API クライアント（生成物）をモックし、`useQuery`/`useMutation` を含むコンポーネントの挙動を検証する。

### CI 連携

- `push` / `pull_request` で Vitest と Playwright を実行する。
- ADR-0004 の通り、このゲートを通過しない AI の PR はマージ不可とする。
- E2E は重要フローに絞り、パイプラインの遅さ・flaky 化を防ぐ。

## 結果

### 良い影響

- AI が壊した重要フローが CI で機械的に検出され、1 名運用のレビュー負荷を補完する。
- テストが「エージェントが満たすべき仕様」として機能し、ドリフトを抑える。
- API モックにより E2E が決定的になり、BE の状態に振り回されない。

### 悪い影響・トレードオフ

- テストの作成・保守コストが発生する。→ 4〜5 画面・重要フロー限定に絞ることで、費用対効果を確保する。
- E2E は本質的に flaky 化しやすい。→ 本番ビルド実行・意味ベースロケータ・API モックで安定化する。
- モックが実 API とズレると、テストは通るが本番で壊れる risk がある。→ モックのレスポンス型は OpenAPI 生成型（ADR-0003）に整合させ、契約のズレを型で検出する。

## 補足

- 非同期 Server Component は当面使わない方針（ADR-0001）だが、将来導入する場合は Vitest が非対応のため Playwright（E2E）側で検証する。
- テストは初期から薄く入れる（後付けは高コスト）。AI にテストを書かせる場合も、本 ADR のスコープ指針に従わせる（`AGENTS.md` に反映）。
