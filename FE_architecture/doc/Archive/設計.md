# AIでフロント実装を進めるためのメモ

## Q1. UI（margin/padding・配置・レイアウト）をAIでどう作るか

### 前提：なぜ準備が要るか
-AIはほっておくと毎回バラバラの数値を発明する
  -px指定,rem指定,数値直書きとか
  -同じUIでもpaddingとmarginが違う
-「自由に数値を書かせない＝選択肢を狭める枠」を用意する
  -理想はページを構成するためのベースとなるコンポーネントをすべて共通で定義すること
  -AIに毎回発明させないため、使ってよい部品をあらかじめ列挙しておく

#### 共通コンポーネントの分類

イメージ、共通定義は3層で考える

```
③ Patterns / Templates 層  … 配置・レイアウト・ページ組み立ての定石
② Components 層            … 役割9カテゴリでフラット分類（粒度=Atomic Design は採らない）
① Tokens / Foundations 層  … 色・余白・タイポのトークン
```

-① Tokens / Foundations を作り込んで「数値の再発明」を止める AI が取れる余白・色をトークンに限定する
-② Components は役割で分類（M3 下敷き、状態は hook ＋ フラグで表す）
-③ 配置・レイアウトは Patterns / Templates 層で組み立てる、コンポーネントの足し算だけだとページにならない

## Q2. Next.js をAIで実装するのに決めておくこと（画面項目・OpenAPI 以外）

### 前提
-Next.js(FE+BFF) 
-BFF/Token Handler
  -ブラウザは httpOnly Cookie の sessionID のみトークンは Redis にサーバー側保持
-認可は Spring Service層BFF/FE は認証（トークン受け渡し）のみ

### 決めごと
-Next.js のバージョン
  -15系
-Server/Client 境界
  -ページ骨格・layout は Server、操作する先っぽだけ Client
-データ取得経路
  -TanStack Query（クライアント）がよさそう
  -RSC fetch はたぶんテストが難しい
-状態管理の範囲
  -サーバー状態 = TanStack Query / クライアント UI 状態 = Jotai

※テスト重視 → クライアント(TanStack)寄せがよいRSC fetch は単体テストツールが弱く E2E 頼みになる

### 規約 / ディレクトリ
-コンポーネント生成先
  -app 配下のどこに置くか（private folder `_components`を使うか）
  -private folder使うか、app/をルーティング専用にするか
-hooks / Jotai Atom の置き場
  -ページ固有と共通（@core / @shared / store）の線引き
  -ページ固有のhooksをどこに置くか、共通への昇格ラインをどうするか
-`use client`を切る単位
  -境界をどの粒度で引くかの基準
  -`page.tsx`,`layout.tsx`には`use client`をつけないみたいな
  -個人的分類
    -Client
      -Overlay / TextInput / Selection 系
    -Server
      -Layout / Display

### ルーティング
-URL構成 / 画面遷移図
