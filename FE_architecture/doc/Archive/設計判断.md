# フロントエンド アーキテクチャ設計判断書

機関システム マスタデータ管理画面 / Next.js + TanStack Query

---

## 0. この文書の目的

マスタデータ管理画面のフロントエンドにおいて、データ取得層をどう設計するか（RSC単独か、TanStack Query併用か）、テストをどこにどう書くかの判断と根拠を残す。規模が小さいことを理由にした「TanStack Query不要論」に対して、何をもって採用を正当化するかを明確にする。

---

## 1. 結論

| 論点 | 採用方針 |
|---|---|
| データ取得アーキテクチャ | **RSCで初回表示 + TanStack Queryでインタラクション**のハイブリッド |
| RSCの役割 | 初回の一覧表示（initialData供給）、認証境界、初回描画速度 |
| TanStack Queryの役割 | 検索・タブ切り替え・CRUD後の再取得・楽観的更新・キャッシュ共有 |
| UI生成 / バリデーション | データ取得層とは独立した**純粋関数**に切り出す |
| テストの本体 | 純粋関数（UI生成・バリデーション・整形・パラメータ組み立て） |
| テストの副次 | カスタムフック（分岐のあるものに限定、MSWでHTTP境界をモック） |

TanStack Query採用の**主たる根拠はテスト容易性ではなく、CRUD/検索/タブのキャッシュ整合の自動化と状態管理の標準化**である。テスト容易性は副次的な利点として扱う（後述）。

---

## 2. 前提：システム構成とデータフロー

### 2.1 機能スコープ

- マスタの一覧表示
- ページネーション
- 検索
- タブでマスタ切り替え（複数マスタを1画面で扱う）
- マスタの追加・修正・削除（CRUD）

### 2.2 データフロー

```
[自前APIサーバー]   Salesforceから移行済みの綺麗なデータを返す。
      ↑ HTTP        スキーマは自分たちで設計（素直なJSON・素直なpage/limit）。
[Next.js BFF]       認証トークンの受け渡しのみ。データ変換は持たない。
      ↑
[フロント]          RSC（初回表示） + クライアントフック（TanStack Query）
```

### 2.3 この構成が設計に与える決定的な影響

- **Salesforce特有の変換問題はフロントに来ない。** `attributes`の剥がし、`nextRecordsUrl`カーソル方式の変換、SOQL組み立ては、すべて自前APIサーバー側の責務。
- 自前APIのレスポンス形式とページネーションは自分たちで決められるため、フロントの変換ロジックは薄くなる。
- BFFはトークン中継のみで、データ変換ロジックを持たない。テスト対象としては薄い。

> もしSalesforce直結だったら、変換・カーソルページネーション・SOQL組み立てがフロントに乗り、テスト価値のあるロジックが厚くなっていた。今回はその大半がサーバー側に移るため、フロントのロジックは「UI生成」「バリデーション」「検索パラメータ組み立て」「キャッシュ整合」に集約される。

## 3. なぜRSC単独では足りないのか

「RSCではダメ」という対立で捉えると誤る。正確には、**RSCには構造的に扱えない領域があり、それが今回の画面の動的部分とちょうど重なる**。

### 3.1 RSCの性質

RSCはサーバーで実行され、データを取得してHTMLを生成し、クライアントへストリームする。初回表示・SEO・キャッシュ・認証隠蔽に強い。ただし**サーバーで一度実行されたら終わり**であり、ブラウザ側で時間とともに変化していくデータを保持・管理する仕組みを持たない。

### 3.2 RSCが構造的に扱えない領域

| 領域 | RSC単独での問題 |
|---|---|
| 操作後の再取得（CRUD） | ルート全体の再検証になり部分更新ができない。タブ状態・スクロール・入力中フォームが飛びやすい |
| 楽観的更新 | ブラウザ側のキャッシュ即時書き換えが必要。サーバー往復を待つRSCには原理的に不可 |
| 検索・タブ切り替えの再取得 | クライアント操作起点の継続的なデータ変化を扱う仕組みがない |
| 一覧と詳細・複数タブのデータ共有 | クライアント側キャッシュの概念がない |

### 3.3 役割分担（対立ではない）

2025〜2026年の標準は、初回データをRSC、インタラクティブ部分をTanStack Queryが担うハイブリッド構成。明確なハイドレーション境界で接合する。

| 領域 | 担当 | 理由 |
|---|---|---|
| 初回の一覧表示 | RSC | サーバー取得・描画、速い、認証隠蔽 |
| タブ切り替え後の再取得 | TanStack Query | クライアント主導の変化 |
| 検索フィルタ変更 | TanStack Query | 操作に応じた再取得・キャッシュ |
| 追加・修正・削除後の一覧更新 | TanStack Query | 部分的な再取得、invalidate |
| 楽観的更新 | TanStack Query | ブラウザ側キャッシュ書き換え |
| 一覧と詳細のデータ共有 | TanStack Query | queryKeyによるキャッシュ共有 |

### 3.4 本画面への当てはめ

機能のうち**初回の一覧表示以外（検索・タブ切り替え・CRUD）は、ほぼ全部クライアント主導の継続的な状態変化**である。これがRSCが構造的に扱えず、TanStack Queryが担当する領域に集中している。これが採用の本質的な根拠。

> 逆に言えば、機能が「一覧を表示するだけ・編集なし・検索なし」だったらRSC単独で十分で、TanStack Queryは不要だった。CRUD・検索・タブが入ることが採用を正当化している。

## 4. TanStack Queryが解決すること

`useQuery`（読み取り）と`useMutation`（書き込み）の2つに集約される。サーバーのデータをクライアントのstateとして手で管理するのをやめ、キャッシュ層に肩代わりさせるのが本質。

### 4.1 useQuery と queryKey

```ts
const { data, isPending, error } = useQuery({
  queryKey: ['masters', masterType, page, searchParams], // キャッシュ識別キー
  queryFn: () => fetchMasters(masterType, page, searchParams),
})
```

`queryKey`がキャッシュの識別子。タブ（masterType）・ページ・検索条件をキーに含めることで、切り替えごとにキャッシュが分かれ、同じキーへのアクセスは自動でキャッシュから返る。再フェッチ・重複排除・古いデータの扱いがこのキー基準で動く。

### 4.2 useMutation と invalidateQueries

```ts
const { mutate } = useMutation({
  mutationFn: updateMaster,
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ['masters', masterType] })
    // 該当マスタのキャッシュを「古い」と印付け → 自動で再取得
  },
})
```

CRUDで最も効くのが`invalidateQueries`。「保存したら一覧を最新化」を、手動の再フェッチ結線なしにキー指定だけで実現する。これが素のReact・RSC単独との最大の差。

### 4.3 採用根拠の優先順位（重要）

1. **主：CRUD/検索/タブのキャッシュ整合の自動化** — 追加・修正・削除のたびに一覧・詳細を手動再フェッチ結線せず、宣言的に最新化。タブで複数マスタを扱うほど効く。
2. **主：状態管理の標準化** — `isPending`/`isError`等が全フックで統一。タブ×マスタ×CRUDで増えるデータ取得状態のコードが定型化し、AI・チームの判断しやすいルールになる。
3. **主：クライアント状態の削減** — サーバーデータを`useState`で抱えない設計に統一。
4. **副次：テスト容易性** — データ取得をフックに集約することで、ロジックとモック境界（HTTP）が分離される。ただし後述の通り、これ単独では採用の主根拠にならない。

## 5. テスト戦略

### 5.1 モックすべき対象は「ネットワーク境界」

```
[UIコンポーネント]
      ↓
[カスタムフック]  useMasterList / useUpdateMaster
      ↓
[queryFn / mutationFn]  ← fetch / axios を実行
      ↓ HTTP
===== ネットワーク境界（ここをMSWでモック）=====
[自前APIサーバー]  ← 自分のコードではない
```

**MSW（HTTP層のモック）を使う。** 関数を`vi.mock`で差し替える方式（やり方A）は、URL組み立て・レスポンスのパースがテストから抜け落ちる。MSWはコードを1ミリも差し替えず、実際に`fetch`が走り、URLが組まれ、レスポンスがパースされる。これにより本番と同じ状況で自分のコード全体を検証できる。

### 5.2 テスト価値のあるロジック / ないロジック

| 対象 | テスト価値 | 置き場所 |
|---|---|---|
| マスタ定義 → 列定義/フォーム生成 | **高** | 純粋関数 |
| CRUD入力バリデーション（マスタごとの必須・形式・桁数） | **高** | 純粋関数（Zod等） |
| 検索条件 → クエリパラメータ組み立て（空欄除外・複数条件結合・マスタ別対象項目） | 中〜高 | 純粋関数 |
| mutation後のinvalidateQueries対象選択 | 中〜高 | フック |
| 楽観的更新とロールバック分岐 | 中〜高 | フック |
| 日付・enum・null等の軽い整形 | 中 | 純粋関数 |
| `isPending`が最初true→成功後false | **なし（ライブラリ自体の挙動）** | テストしない |
| 変換も組み立てもない素通しフック | **なし** | 量産しない |
| staleTime・再フェッチタイミング | **なし（ライブラリの責務）** | テストしない |

### 5.3 重要な区別：UI生成の純粋関数テストは TanStack Query と無関係

マスタ定義からのUI生成を純粋関数でテストできるのは、**ロジックをコンポーネント外に切り出したからであって、TanStack Queryのおかげではない**。これはRSC/CSR/TanStackの選択と完全に独立して成立する。

```ts
// master-schema.ts （データ取得と無関係な純粋関数）
export function generateColumns(schema: MasterSchema): ColumnDef[] { ... }
export function buildFormFields(schema: MasterSchema): FieldDef[] { ... }

// master-schema.test.ts （レンダリング不要）
expect(generateColumns(userMasterSchema)).toEqual([...])
```

- RSCでも、UI生成を純粋関数に切り出していればレンダリング不要で単体テストできる。
- レンダリングまで必要になるのは、生成ロジックをコンポーネント本体に埋め込んだ場合のみ（これはRSC/CSRを問わず同じ）。
- 真の原因は「RSCかどうか」ではなく「ロジックがコンポーネントに同居しているか」。

> したがって「テスト容易性」を語るときは、フックのテスト（MSW）と純粋関数のテストを混同しないこと。後者はどの構成でも成立するため、TanStack Query採用の根拠にはならない。

### 5.4 層別テスト方針

| 層 | テスト方法 | 位置づけ |
|---|---|---|
| 純粋関数（UI生成・バリデーション・整形・パラメータ組み立て） | 依存なしの単体テスト | **テスト価値の本体** |
| カスタムフック（useQuery/useMutationラッパー） | MSWでHTTP境界をモックし `renderHook` で検証 | 分岐のあるものに限定。素通しフックは量産しない |
| BFF（トークン中継） | 結線確認の統合テスト数本 | 薄い |
| RSC初期表示 | E2E / 統合 | 結線の確認 |

## 6. コーディングルール案（AI・チーム向け）

データ取得層とUI生成層を分離し、判断を取り違えないためのルール。

### 6.1 レイヤー分離

1. **データ取得はカスタムフックに集約する。** コンポーネント内で直接`fetch`や`useQuery`を呼ばない。`useMasterList(masterType, params)` / `useUpdateMaster(masterType)` のように定義する。
2. **UI生成・バリデーション・整形は純粋関数に切り出す。** コンポーネントやフックの中に変換ロジックを埋め込まない。`generateColumns` / `buildFormFields` / `validateMasterInput` のように関数化する。
3. **BFFはトークン中継に限定し、データ変換を持ち込まない。**

### 6.2 queryKey 規約

- キーは配列で `['masters', masterType, page, normalizedSearchParams]` の順とする。
- タブ（masterType）を必ずキーに含め、マスタ間でキャッシュが混ざらないようにする。
- 検索条件はキーに入れる前に正規化（空欄除外・順序固定）する純粋関数を通す。

### 6.3 invalidate 規約

- mutation成功後の`invalidateQueries`は、影響範囲のキーのみを対象にする（無関係なマスタを無効化しない）。
- 一覧と詳細の両方に影響する操作は、両方のキーを明示的に無効化する。

### 6.4 RSC / クライアント境界

- 初回の一覧表示はRSCで取得し、`initialData`としてクライアントフックに渡して二重フェッチを避ける。
- 検索・タブ切り替え・CRUD以降のインタラクションはクライアントフックが担う。

### 6.5 テストのルール

- 純粋関数は必ず単体テストを書く（テスト価値の本体）。
- フックのテストはMSWでHTTP境界をモックする。`vi.mock`で関数を差し替えない。
- ライブラリ自体の挙動（isPendingの遷移、staleTime）はテストしない。
- 素通しフックのテストを量産しない。分岐（invalidate対象選択・楽観的更新のロールバック）があるものに絞る。

## 7. 想定される反論と応答

| 反論 | 応答 |
|---|---|
| 「規模が小さいからTanStack Queryは不要」 | 一覧表示だけなら正しい。しかしCRUD・検索・タブ切り替えはクライアント主導の継続的な状態変化であり、RSC単独では部分更新・楽観的更新・キャッシュ共有ができない。動的部分がTanStack Queryの担当領域に集中している。 |
| 「テストしやすいから採用」 | これは副次的根拠。UI生成・バリデーションの純粋関数テストはTanStack Queryと無関係に成立する。採用の主根拠はキャッシュ整合の自動化と状態管理の標準化に置くべき。 |
| 「RSC + Server Actions + revalidatePathで全部できる」 | 技術的には可能。ただし更新のたびにルート全体が再検証され部分更新ができず、楽観的更新も困難で、クライアント状態の保持を自前で設計することになる。結局TanStack Queryが標準化している仕組みの再発明になる。 |

---

## 8. まとめ

- RSCは「サーバーで一度描く」もので初回表示に最適。TanStack Queryは「ブラウザ側でデータを継続管理する」もので操作後の再取得・楽観的更新・キャッシュ共有を担う。両者は対立せず分担する。
- 本画面は動的部分（検索・タブ・CRUD）が中心であり、TanStack Queryが効く領域と重なる。これが採用の本質的根拠。
- UI生成・バリデーションは純粋関数に切り出し、データ取得層とは独立してテストする。これはTanStack Query採用とは別の設計原則。
- テスト容易性はTanStack Query採用の副次的利点であり、主根拠はキャッシュ整合の自動化と状態管理の標準化に置く。
