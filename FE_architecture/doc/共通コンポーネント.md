# 共通コンポーネントの分類

>[FE知見共有会.md](../FE知見共有会.md) の詳細版。AI にフロント実装を任せるための「使ってよい部品」をどう定義・分類するか。

共通定義は3層で考える。当初の課題「AI が margin/padding を毎回発明する」を止めるのは最下層の Tokens。「組み合わせればどんなページもできる」は3層が揃って初めて成立する。コンポーネントだけでは足りない。

```
③ Patterns / Templates 層 … ページ雛形・組み合わせの定石（component の足し算では出ない）
② Components 層      … 役割9カテゴリ（粒度でも状態でもなく「役割」でフラット分類）
① Tokens / Foundations 層 … 色・余白・タイポのトークン（数値発明を止める）
```

## ① Tokens / Foundations 層

「AI が margin/padding を発明する」を止めるのは、コンポーネントではなくトークン。コンポーネントが取れる値をトークンに限定して初めて枠が閉じる。業界標準は3層トークン。

| 層 | 役割 | 例 |
| --- | --- | --- |
| primitive | 生値。参照専用で直接は使わない | `4px`,`8px`, `#1a1a1a`|
| semantic | 用途で意味づけ。UI はこれだけを使う | `spacing.md`,`color.text.primary`, `radius.sm`|
| component | 部品固有の値（テーマ用） | `button.padding.x`|

-Layout/Overlay テンプレが取れる `gap`/ `padding`を semantic token に限定する。これが「数値を直書きさせない枠」の実体。
-数値直書きの禁止は lint で検知できるはず。
-理想は component にも部品固有の値はできるだけ持たせたくないが、たぶんそううまくいかない。

## ② Components 層

役割でフラット分類する。

-役割で分ける（粒度でも状態でも分けない）
 -Atomic Design の atoms/molecules/organisms は境界が主観的で「これは molecule か organism か」の論争に正解がない（作者の Brad Frost 本人も「ラベルは本質ではない」と明言）
 -代わりに Material Design 3 の役割カテゴリを下敷きにする。名前も業界で収束済み（Open UI 調べで Button 93% / Dialog 67% など）なので独自命名は発明しない
-M3 の `Containment`は寄せ集めなので割り直す
 -Card（配置）も Dialog（重なり）も List も同居しているので、Layout（配置・スペーシング） と Overlay（重なり・開閉） に分割し、この2つは数値とパターンを閉じ込めた自前の共通テンプレートとして持つ
-状態・振る舞いは分類軸にせず、hook とフラグで表す
 -「状態を持つか」でカテゴリを切ると日付ピッカー（値＋開閉の両方を持つ）が宙に浮く
 -状態は role の外に出し、開閉は `useXxxModal()`/ `useXxxDrawer()`へ、入力値は RHF + Zod へ切り出す
 -「状態を持つ」事実は分類ではなくフラグで記録する

### 役割カテゴリ（主軸 / フラット・入れ子なし）

| カテゴリ | 由来 | 含む部品 |
| --- | --- | --- |
| Action（操作） | M3 Action | Button, IconButton, FAB, Link |
| TextInput（テキスト入力） | M3 Text input | TextField, Textarea |
| Selection（選択） | M3 Selection | Checkbox, Radio, Switch, Select, Slider, DatePicker, FileUpload |
| Layout（配置・構造） | M3 Containment を分割（自作テンプレ） | Box, Stack, Grid, Container, Spacer, Card, Section |
| Overlay（重なり・開閉） | M3 Containment を分割（自作テンプレ） | Modal/Dialog, Drawer, Sheet, Popover, Dropdown, Tooltip |
| DataDisplay（データ表示） | Ant / Carbon の Data Display | Table, DataGrid, List（データ）, Tree, Tag, Statistic, Chart |
| Navigation（ナビゲーション） | M3 Navigation | Tabs, Menu, Breadcrumb, Pagination, Stepper, NavBar/Drawer |
| Communication（伝達・通知） | M3 Communication | Snackbar/Toast, Badge, Progress, Alert/Banner, Skeleton |
| Display（表示プリミティブ） | M3 Foundations 由来 | Text/Heading, Icon, Image, Avatar, Divider |

-入れ子は「使い方」であって「分類」ではない
 -`<Stack>`の中に`<Button>`を置いても、Button は Layout の子分類にはならない（兄弟のまま）
-内訳: M3 の6カテゴリ ＋ `Containment`を Layout/Overlay に2分割 ＋ Ant/Carbon 由来の DataDisplay ＋ 表示系の Display、の計9

### フラグ（faceted classification = 横断検索用の属性）

※こっから妄想

役割が主キー、フラグは絞り込み軸。図書館情報学のファセット分類（Amazon の絞り込みフィルタと同じ発想）で、AI が「どの部品を使うべきか」を辞書引きできるようにする。状態を分類から追い出した代わりにここで記録する。

| フラグ | 意味 | 例 |
| --- | --- | --- |
| `stateful`| 状態を持つか（持つ場合は hook 側に切り出す） | Modal=true, Button=false |
| `behaviorHook`| 振る舞いを担う hook | Modal=`useXxxModal`, Drawer=`useXxxDrawer`|
| `formBound`| RHF + Zod に紐づくか | TextField=true, Icon=false |
| `overlay`| 画面に重なって表示されるか | Dropdown=true, Card=false |
| `container`| 子要素（slot）を内包するか | Stack=true, Badge=false |

AI への辞書引き例:
-「フォームに紐づく入力部品」→ `role∈{TextInput,Selection} かつ formBound=true`
-「開閉を伴う重なり部品」→ `role=Overlay かつ overlay=true`（実装時の開閉は `behaviorHook`を参照）

## ③ Patterns / Templates 層（ページの組み立て）

コンポーネントの足し算だけではページにならない。「組み合わせの定石」はひとつ上の層になる（Nathan Curtis: component ≠ pattern ≠ template）。

-Pattern（再利用する"作り方"）: 空状態、フォームレイアウト、一覧＋詳細、検索＋結果、確認ダイアログの出し方など。同じコードの再利用ではなく「同じ作り方を踏襲」する指針
-Template（ページ雛形）: ヘッダー＋サイドバー＋本文のような骨格。アプリ層では`pages/XxxPage/`がこれを組み立てる
-この層でも状態を持つ振る舞いは Components 層と同じく hook（`useXxx*`）へ寄せる。pattern/template 自体は配置と組み合わせの規約に徹する

>まとめ: 3層で考える。① Tokens で数値を固定し、② Components を役割9カテゴリでフラット分類（Layout/Overlay は自作テンプレ、状態は hook ＋ フラグ）、③ Patterns/Templates で組み合わせる。粒度（Atomic Design）は採らない。
