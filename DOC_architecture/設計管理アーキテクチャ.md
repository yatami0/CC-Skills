# 設計書管理アーキテクチャ（全体像）

> このドキュメントは、本プロジェクトの基本設計書をどう構成・配置・記述するかを定める最上位の標準である。
> サイトA/B/C のいずれにも依存しない。各サイトはこの標準に従って設計書を作成する。
> 新規参画者・Claude は、まずこのファイルを読めば設計書一式の構造と作成方法が分かることを目的とする。

---

## 0. 30秒サマリ

- 設計書は 3層構造 で管理する。
  - 第1層：標準（`00_standards/`） — サイト非依存の規約。1セットのみ。本ファイルが属する層。
  - 第2層：サイト設計書（`siteA/`, `siteB/`, ...） — 標準に従って各サイトが埋める。
  - 第3層：個別成果物 — 各サイトフォルダ内の実ファイル（画面設計書・API設計書など）。
- 設計書は FE用/BE用の縦割りでは分けない。成果物の種類（画面/API/データモデル/区分値/メッセージ）= 横割りで分ける。
- アーキテクチャは「横断ルール」と「サイト固有の構成」を分離する。
  - FE/BEの横断ルール（実装方式の標準）は第1層（`fe-architecture.md` / `be-architecture.md`）に置く。全サイトが Next.js + Java で統一されているため共通化できる。
  - サイト固有の構成（システム構成図・認証・外部連携）は第2層（各サイトの `04_アーキテクチャ/`）に置く。サイトごとに異なるため。
- 全サイトが Next.js（FE/BFF）+ Java（BE） で統一されているため、強い標準（フォルダ番号体系・章立て・フォーマットまで全サイト固定）を採る。
- 設計書は 専用リポジトリ で一元管理する（コードリポジトリとは分離）。
- ファイル形式は Markdown + Git。図は PlantUML / Mermaid / draw.io。API は OpenAPI。

---

## 1. なぜこの構造なのか（判断基準）

設計書に何を書き、どう分けるかは、一貫して次の基準で判断する。

> それが決まっていないと、2人以上の開発者が別々の実装をしてしまうか？
> Yes なら設計書に書く。No なら設計書に書かず、別の正本（型定義 / Figma / Storybook / Lint設定）に置く。

この基準から導かれる方針が3つある。

1. 二重管理をしない。 同じ情報の正本は1箇所のみ。他は参照する。
2. 見た目は設計書に書かない。 Figma で判断できる見た目はFigmaが正本。設計書には API 呼び出し・イベント・パラメータ・バリデーションを書く。
3. 想像で項目を足さない。 サイト固有の事情を標準に混ぜない。標準はサイト非依存の最小限に保つ。

## 2. 3層構造の定義

設計書管理は次の3層に分離する。層を混同しないことが最重要。

### 第1層：標準（サイト非依存・1セットのみ）

全サイトが従う規約。ここには特定サイトの業務・方式は一切書かない。
（例：メタデータ駆動・EAV・特定の data_type の解釈などは、サイト固有なのでここには書かない。）

アーキテクチャのうち「実装方式の横断ルール」はこの層に置く。スタックが全サイト Next.js + Java で統一されているため、FE/BEそれぞれの実装標準を1セットに固定できる。

配置：`00_standards/`

| ファイル | 内容 |
|---------|------|
| `design_architecture.md` | 本ファイル。3層構造と全体方針 |
| `fe-architecture.md` | FEの横断アーキテクチャ標準（レンダリング・状態管理・コンポーネント設計・品質ガードレール等） |
| `be-architecture.md` | BEの横断アーキテクチャ標準（Java層の責務・API設計方針等） |
| `document_guideline.md` | 各成果物に何を書くか（成果物カタログ §4） |
| `diagram_format.md` | 図のフォーマット規約（§5.1） |
| `naming_convention.md` | 命名規約（フォルダ番号・ファイル名・画面ID等） |
| `templates/` | 各成果物の空テンプレート（§6） |

### 第2層：サイト設計書（サイトの数だけ）

第1層の標準フォルダ体系に従って、各サイトが実際に埋める層。
サイト固有の成果物は、この層でのみ番号を足して追加してよい（標準フォルダ体系は変えない）。

アーキテクチャのうち「サイト固有の構成」はこの層に置く。システム構成図・認証方式・外部連携はサイトごとに異なるため、各サイトの `04_アーキテクチャ/` に置く。第1層の横断ルール（`fe-architecture.md` / `be-architecture.md`）を参照しつつ、サイト固有部分だけを記述する。

配置：`siteA_xxx/`, `siteB_xxx/`, ...

例：サイトA（マスタデータ管理）はメタデータ駆動なので、標準にない `メタデータ定義設計` を固有成果物として挿入する。また、メタデータ駆動・EAV といった方式そのものもサイトA固有なので、第2層内に閉じる。これらは標準（第1層）には登場させない。

### 第3層：個別成果物（実ファイル）

各サイトフォルダ内の実ファイル。第1層の `templates/` を複製して作成する。
例：`siteA_master-data/06_画面設計書/screen-SC-001.md`

## 3. リポジトリ構成

設計書は 専用リポジトリ で管理し、コードリポジトリ（FE/BFF・Java BE）とは分離する。

理由：API設計・データモデル・区分値・メッセージは FE と BE が共有する正本である。どちらかのコードリポジトリに置くと、もう片方からの参照・更新で二重管理が起きる。中立な専用リポジトリに置くことで SSOT を保つ。

```
design-docs/                         # 設計書専用リポジトリ
├── 00_standards/                    # 第1層：標準（サイト非依存・1セット）
│   ├── design_architecture.md       #   本ファイル
│   ├── fe-architecture.md           #   FE横断アーキテクチャ標準
│   ├── be-architecture.md           #   BE横断アーキテクチャ標準
│   ├── document_guideline.md
│   ├── diagram_format.md
│   ├── naming_convention.md
│   └── templates/
│       ├── screen-list.md
│       ├── screen-design.md
│       ├── api-design.md
│       ├── enum-design.md
│       └── message-def.md
│
├── adr/                             # 設計判断の記録（ADR）
│   └── ADR-NNN-*.md
│
├── siteA_master-data/               # 第2層：サイトA
│   ├── 01_キャッチアップ
│   ├── 02_環境構築
│   ├── 03_開発規約
│   ├── 04_アーキテクチャ            #   ★サイト固有の構成図・認証・外部連携（横断ルールは第1層を参照）
│   ├── 05_UI設計
│   ├── 06_画面設計書
│   ├── 07_メタデータ定義設計        #   ★サイトA固有（標準には無い）
│   ├── 08_API設計書
│   ├── 09_データモデル
│   ├── 10_区分値設計
│   ├── 11_メッセージ定義
│   └── README.md
│
├── siteB_xxx/                       # 第2層：サイトB（標準体系に従う）
│   └── ...
│
├── siteC_xxx/
│   └── ...
│
└── README.md
```

> サイトAでは固有成果物 `07_メタデータ定義設計` を挟んだ結果、以降の番号が標準とずれる。
> これは許容する。番号には体系をもたせず、必要時にインクリメントする方針のため、ずれても破綻しない。

## 4. 標準フォルダ体系（第2層の各サイト共通）

各サイトは次の体系に従う。先頭に新規参画者が欲する情報（キャッチアップ・環境構築）を置く。

| 番号 | フォルダ | 内容 | 正本/参照 |
|------|---------|------|----------|
| 01 | キャッチアップ | ドメイン知識・前提・用語 | 正本 |
| 02 | 環境構築 | ローカル構築手順 | 正本 |
| 03 | 開発規約 | Gitフロー・リリース方式・CI/CD | 正本 |
| 04 | アーキテクチャ | システム構成図・認証方式・外部連携（サイト固有）。実装方式の横断ルールは第1層 `fe-architecture.md` / `be-architecture.md` を参照 | 正本（固有部分）／参照（横断ルール） |
| 05 | UI設計 | Figma のパス（見た目の正本はFigma） | 参照 |
| 06 | 画面設計書 | 画面一覧（`screen-list.md`）+ 画面別設計書 | 正本 |
| 07 | API設計書 | `openapi.yaml` + 各BL（ビジネスロジック）設計 | 正本 |
| 08 | データモデル | ERD・テーブル定義 | 正本 |
| 09 | 区分値設計 | 区分値（ENUM）の正本。スコープに frontend/backend を明記 | 正本 |
| 10 | メッセージ定義 | エラー/警告メッセージの一元管理 | 正本 |

> 固有成果物の追加ルール：標準にない成果物が必要なサイトは、適切な位置に番号を挿入して追加してよい。
> ただし標準フォルダの意味・順序は変えない。追加した固有成果物は第2層に閉じる。

> `04_アーキテクチャ` の分担：実装方式（レンダリング・状態管理・コンポーネント設計・品質ガードレール等）は第1層の横断標準が正本。各サイトの `04_アーキテクチャ` には、そのサイト固有の構成図・認証・外部連携だけを書き、横断標準を参照する。

## 5. フォーマット規約（全成果物共通・サイト非依存）

### 5.1 図

| 用途 | ツール | 指定 |
|------|--------|------|
| シーケンス図・状態遷移・ER等 | PlantUML | テーマは `toy` を指定 |
| 同上（代替可） | Mermaid.js | — |
| システム構成図など複雑な図 | draw.io | 拡張子 `.drawio.png` / `.drawio.jpg` / `.drawio.svg` |

図は Git 差分と相性の良いテキストベース（PlantUML/Mermaid）を基本とする。

### 5.2 API

- API 定義は `openapi.yaml` に記載する。
- プログラム設計書では、`openapi.yaml` と重複する自明な項目（リクエストパラメータ・レスポンス項目）は省略する。
- 複数テーブルを参照する検索APIは、項目の由来表を定義する。

| Parameter | Description | Settings | Note |
|-----------|-------------|----------|------|
| 物理名 | 論理名（openapi側にあれば省略可） | 取得元テーブル | 加工があれば計算ロジック |

### 5.3 フロントエンドの記載境界

- 書かない：Figma で判断可能な見た目（レイアウト・色・余白・文言の見た目）。
- 書く：Web API 呼び出し、イベント定義、パラメータの受け渡し、バリデーションロジック、画面遷移、データ状態（loading/empty/error/success）。

詳細なFEの実装方式（レンダリング・状態管理・コンポーネント設計）は `fe-architecture.md` に従う。

### 5.4 区分値（ENUM）

概要に「目的・物理名・型・スコープ（frontend/backend）・マスターテーブル」を、本体に下表を記載する。

| 論理名 | 物理名 | 値 | バージョン | コメント |
|--------|--------|-----|-----------|---------|

### 5.5 メッセージ定義

| 識別子 | レベル | ステータス | メッセージ | コメント |
|--------|--------|-----------|-----------|---------|

レベルは E（Error）/ W（Warning）/ F（Fatal）等。プレースホルダは `{domain}` のように記す。

### 5.6 Markdown の限界に関する例外規定

1つの成果物で項目数が数十以上になり、Markdown の表で保守性が著しく落ちる場合は、Markdown に固執せず Excel 等の形式を採用してよい。
（例：項目数が可変・大量になりうるサイトの画面項目定義。）
この判断は各サイトに委ねるが、採用した場合は当該フォルダの README にその旨を記す。

## 6. テンプレートの使い方（新規参画者・Claude向け手順）

新しいサイトの設計書、または新しい成果物を作る手順。

1. `00_standards/templates/` から該当テンプレートを複製する。
2. 配置先は §4 の標準フォルダ体系に従う。
3. 実装方式は第1層の横断標準（`fe-architecture.md` / `be-architecture.md`）に従う。
4. フォーマットは §5 に従う。見た目は書かず、API/イベント/バリデーション/状態を書く（§5.3）。
5. サイト固有の成果物が必要なら、第2層に番号を足して追加する（標準＝第1層は変えない）。
6. 図は §5.1、API は §5.2、区分値は §5.4、メッセージは §5.5 のフォーマットを使う。

> 層を間違えないチェック：書こうとしている内容は「全サイトに共通か？」
> Yes → 第1層（`00_standards/`）。No（特定サイトの業務・方式・構成）→ 第2層（`siteX/`）。

## 7. 設計判断の記録（ADR）

本構造に至るまでの設計判断は `adr/` に ADR（Architecture Decision Record）として記録する。
「なぜこの形なのか」を後から追えるようにし、再議論のコストを下げる。
命名規則：`ADR-{NNN}-{タイトルをケバブケースで}.md`

> 本セッションでの追加判断（第1層にFE/BEの横断アーキテクチャ標準を新設し、`service-common.md` を廃止して内容を各層へ振り分けたこと）は、別途 ADR として記録する。
