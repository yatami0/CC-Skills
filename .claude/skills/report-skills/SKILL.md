# Report Skills

AIが書いた日本語は読めばすぐ分かる。文章を書く・直すときは以下に従い、人間が書いたように自然な文章にする。
やり取り・成果物はすべて日本語で行う。文章を直すときは元の意味を変えない。

## 大前提 — 人は怠惰である

人間は基本的に怠惰なので、できるだけ簡単な書き方・言い回し・変換を選ぶ。
凝った表現や手間のかかる記号を避けるだけで、文章はかなり自然になる。まずこれを念頭に置く。

## 助詞を省略しない

日本語は助詞が重要なので、助詞を絶対に省略しない。

## 記号と表記

### 冗長な補足

```
共通化（抽象化）
別の例（仮想ファイルシステム VFS）
```

前の語彙にカッコで補足を付ける書き方は基本的に冗長。本当に必要なときだけ使う。

### 余計な強調

`**` のような強調はまず使わない。見出し代わりに太字を使うのも避ける。

### 人間が使わない記号

`「」` カッコや `・` 中点、`—` emダッシュは変換で出しにくいため、人間はあまり使わない。

- `・` は `/` スラッシュに置き換えることが多い。
- カッコは `""` ダブルクォーテーションに置き換えることが多いが、そもそもあまり使わない。
- emダッシュ（`—`）は使わない。読点や「つまり」で言い換える。

### 段落番号をハードコードしない

後からの編集で順番や内容の増減が起きるため、番号を直接マークダウンに振らない。

ダメな例:

```
1. 有線LANと無線LANについて、物理層の違いからデータリンク層の実現方法の違い、
   そしてネットワーク層から見た共通化までを順に検討する。
2. 下位層は違うのに、ある層から上では同じに見え、途中の層の実現が違う、
```

書くなら標準のリスト形式にする:

```
* 有線LANと無線LANについて、物理層の違いからデータリンク層の実現方法の違い、
   そしてネットワーク層から見た共通化までを順に検討する。
* 下位層は違うのに、ある層から上では同じに見え、途中の層の実現が違う、
```

見出しに番号を振るのも禁止:

```
## 1. 課題1：有線LANと無線LANの比較

### 1.1 物理層の違い
```

### アスキーアートで図を描かない

```
+-------------------------------------------------------------+
|                         Kubernetes                          |
|  +----------------------+      +--------------------------+  |
|  |  API Server Service  |----->|  Go + Gin Deployment     |  |
|  +----------------------+      +------------+-------------+  |
|        +-------------------+              +----------------+ |
|        | PostgreSQL        |              | MinIO          | |
|        +-------------------+              +----------------+ |
+-------------------------------------------------------------+
```

このようなアスキーアートは人間は書かない。特に複雑なものは書かない。
図が必要なら Mermaid などコードで表記できるものを使い、アスキーアートは使わない。

## 文のリズム

### 文末を単調にしない

同じ語尾を3回以上続けない。「〜です。〜です。〜です。」「〜である。〜である。」が続いたら崩す。
である調なら「だ」「体言止め」を混ぜ、ですます調なら語尾を変える。

```
NG: 課題は3つだ。1つ目は速度だ。2つ目はコストだ。3つ目は保守性だ。
OK: 課題は3つある。速度、コスト、そして保守性。なかでも保守性が後々効いてくる。
```

### 接続詞を多用しない

「さらに」「また」「加えて」「したがって」を毎段落の頭に置かない。順接の接続詞は最小限にする。
無くても文がつながるなら削る。

### 段落の長さと閉じ方を揃えない

全段落を同じ長さに揃えない。短い段落と厚い段落を混ぜる。
毎回「以上がポイントである」のようにきれいに閉じない。閉じ方を変えるか、余韻を残す。

## 語彙と文体

### 受動態を過剰に使わない

「検討が行われた」「分析が実施された」のような受動態を連発しない。能動態にする。

```
NG: 比較が行われた結果、差が確認された。
OK: 比較した結果、差が出た。
```

### 根拠のない評価語を使わない

「非常に」「大きな」「重要な」「本質的」「最適化」など、根拠なしの評価語を避ける。
評価するなら根拠を添えるか、何がどうなるかを動詞中心の具体表現にする。

```
NG: コストと品質の両面で非常に非効率である。
OK: トークン消費が増え、重要な指示が埋もれやすくなる。
```

### AI語彙を避ける

次の語が高密度で出ると一気にAIっぽくなる。平易な日本語に置き換えるか削除する。

> さらに / また / 加えて / 包括的 / 革新的 / シームレス / 多角的 / 本質的 / 不可欠 /
> 重要な役割を果たす / 大きな意義を持つ / 注目に値する / 示唆に富む / 興味深いことに

### 三点セットを無理に作らない

何でも「A、B、C」の3項目に揃えるクセを出さない。項目は自然な数にする。2つでよければ2つにする。

### 言い換え連打をしない

同じ対象を「重要・大切・欠かせない」と言い換えて繰り返さない。1回で言い切る。
用語も統一する。同じものを「ユーザー」「利用者」「顧客」と混ぜない。

### 保険・ヘッジを常設しない

「一概には言えないが」「場合による」を逃げ道として毎回置かない。
条件があるなら具体的に書く。無いなら言い切る。

### 定型の導入・締めを使わない

「参考になれば幸いです」「ポイントは以下の通りです」「〜ではないだろうか」のような
テンプレ的な決まり文句や読者への語りかけを避ける。直接内容を述べる。

## 提出前の自己チェック

- [ ] 助詞を省略していない
- [ ] `**` 強調・見出し代わりの太字を使っていない
- [ ] `「」`・中点・emダッシュ・カッコ補足を多用していない
- [ ] 見出し・段落に番号をハードコードしていない
- [ ] アスキーアートで図を描いていない
- [ ] 同じ語尾が3回以上続いていない
- [ ] 「さらに」「また」「加えて」を連発していない
- [ ] 受動態を過剰に使っていない（能動態に直す）
- [ ] 根拠なき「非常に」「重要」「本質」がない
- [ ] AI語彙（包括的 / 革新的 / 示唆に富む 等）がない
- [ ] 定型の導入・締めの句がない
- [ ] 用語が統一されている（言い換え連打がない）
