# web-design-distill

`web-design-mock` の**逆向き**スキル。あちらは「権威ある哲学 → モック」。こちらは
「**モック → 再利用可能な哲学**」。1枚の良いモックに埋め込まれた暗黙のルールを、
`references/<name>/<name>.md` と**同じスキーマ**の明示的な哲学へ蒸留する。

> 親スキルの設計言語(二層ループ / フェーズ間ゲート / `00-state.md` baton / progressive
> disclosure / 値を捏造しない / 本物感の源)をそのまま引き継ぐ。スキーマと機械チェックは
> `web-design-mock` と**共有契約**(別物を作らない)。

---

## 0. 設計の核心(最初に読む — このスキルの全部はここに収束する)

Apple/Carbon が哲学として機能するのは**外部権威(公式デザインシステム)**が値を保証するから。
**1枚のモックから起こした哲学には外部権威が無い** — 放置すると「このHTMLがたまたまこうだった」
という**過学習スナップショット**にしかならない。本スキルは 2 つの原則でこれを防ぐ:

1. **トークンは「実測」、原則は「推論」**
   `:root` は計測可能な地の真実 → **逐語抽出のみ・捏造ゼロ**。§1原則・§4規約は解釈なので
   必ず `inferred` と明示し、**HTML の実使用と照合して反証可能**にする(言ったルールを mock 自身が
   守っているか)。
2. **再利用性は「主張」でなく「検証」で得る**
   別画面で再生成して崩れなければ初めて哲学。これを最終ゲート(D4 ラウンドトリップ)にする。
   D4 を通らないものは哲学に昇格させない。

## 1. 最初に必ずやること(セッション開始時)

蒸留の作業状態は**作業中ワークスペース**の `web-design-mock/<slug>/distill/` に置く
(ソースモックと同じプロジェクトフォルダに同居)。昇格後の最終哲学は
`web-design-mock/_philosophies/<name>/` に置く(§4)。スキル本体(`.claude/skills/...`)には
**書かない**(配布物が汚れる)。

1. **既存の蒸留作業を洗い出す**(再開のため):

   ```bash
   node "${CLAUDE_SKILL_DIR}/scripts/list-distills.mjs"
   ```
   - 1件以上あれば各 `00-distill-state.md` の `current_phase`/`next_action` を示し、
     **再開 or 新規**を尋ねる。再開なら `next_action` から続ける(セッション横断の真実の源)。
   - 0件なら新規へ。

2. **ソースモックを確定する**(蒸留の入力 = 地の真実)。MVP の入力は
   **このスキル群が生成した `output/mock-vN.html` のみ**(`:root` が既に揃っているので抽出が確実)。
   - 候補が複数あれば一覧してユーザーに選ばせる。
   - 任意 HTML / URL / 画像はスコープ外(計測ツールが要る)。指定されたら MVP 範囲を伝え、
     まず HTML 化を促す。**値を目分量で捏造しない**。

3. 新規なら哲学名(slug)を仮決めし、`web-design-mock/<slug>/distill/` を作って D1 から開始、
   ログ一式(§5)を作る。

## 2. 4フェーズ(計測 → 言語化 → 草案 → 汎化検証)

外側 = 4フェーズのウォーターフォール。**フェーズ間に検証ゲート**(ユーザーが検証・批判するまで
進まない。Claude は自己承認しない)。各フェーズ共通: (a) 理解を2〜4行で言い換え → (b) 方向を分ける
1〜3問だけ確認 → (c) 作業してフェーズファイルに書く → (d) **ゲートで止まる**。

### D1 — 計測 (Capture) → `D1-measure.md`
**一切推論しない**フェーズ。ソースモックから機械的に事実を抜く。
- **`:root` を逐語抽出**(地の真実)。1トークンも改変・補完しない。
- **実使用の棚卸し**: 余白リズム(実際に使われた space スケール)/ タイプスケールの実適用
  (どの見出しがどのサイズか / **未使用の段も記録**)/ 影と奥行きの作り方(drop shadow か 素材/層か)/
  accent の使われ方(塗りCTA か フォーカスのみか・**ブランド色がどの経路で出るか**)/ 角丸の階層運用 /
  色の面構成(層の数)。
- **親哲学が宣言されていればデルタで計測する(重要)**: ソースが base 哲学を持つ場合
  (例: `01-requirements.md` が「Apple base」、`:root` コメントが哲学名を書いている)、その親リファレンスを
  読み、**同値 / 上書き / 追加 / 省略**の4区分で差分を取る。最も情報量が多いのはこの差分
  (= 後段で「派生哲学」にするか「独立哲学」にするかの判断材料。§3)。親が無い/不明なら独立計測。
- 各観測に**出典(行番号/セレクタ)**を付け、後で反証できるようにする。
- **ゲート観点**: 抽出が逐語か? 推論が混入していないか? 観測に出典が付いているか?
  親哲学があるのにデルタを取っていないことはないか?

### D2 — 原則の言語化 (Articulate) → `D2-principles.md`
計測から**コア原則**と「**本物感の源**」を推論する。Apple の Clarity/Deference/Depth に
あたる、その哲学の背骨。
- **原則の数は哲学が決める(固定しない)**。背骨が 1〜2 本で足りる哲学もあれば 4〜5 本要る哲学もある。
  「3つ揃えるため」に薄い原則を水増ししない / 本物感を説明しきるなら少なくてよい。**各原則は計測で
  裏付けられること**が唯一の採用基準(数でなく根拠で決める)。
- 各原則に `inferred` タグと**根拠(D1 の観測への参照)**を必須化。
- **非自明な原則を取り逃さない(重要)**: ブランド/個性が「予想外の経路」で出ていることが多い。
  既定の思い込み(「ブランド色 = accent の塗り」)で計測を読まない。例: accent は実はフォーカスリング
  だけで、ブランドは**濃紺の chrome ゾーン(面)**で表現 — この「brand-via-chrome, not accent-fill」を
  原則化しないと再現できない。D1 の差分・実使用から**当たり前でない規律**を拾うのが D2 の主目的。
- **ゲート観点(最重要)**: 原則が計測と**一致**するか。例: 「余白主導」と書いたのに実測スペーシングが
  詰まっている → 却下。「影で奥行き」と書いたのにモックは素材/層で表現 → 却下。
  **モック自身が守っていないルールは原則にしない**。非自明な原則が抜けていないか(accent/chrome 等)?

### D3 — 哲学草案 (Draft) → `_philosophies/<name>/<name>.md`(草案・status: draft)
`references/apple/apple.md` の構造を**踏襲**して §0〜§6 を執筆(下の §3 出力テンプレ)。
- **§2 出所表を正直に**: `provenance: empirical` を新クラスとして導入し、各値を
  **実測(mock由来) / 推論(inferred)** で区分。authoritative(Apple/Carbon)と混同させない。
- §3 = 抽出 `:root` を正規化(命名を親スキーマに寄せる。値は変えない)。
- §0 ルーター用メタは**保守的に**(得意な画面タイプは D4 で実証できたものに後で絞る。草案段階では
  「検証中」と明記)。
- **ゲート観点**: スキーマ準拠か? 実測と推論の区別が全トークン/規約で付いているか?

### D4 — 汎化検証 / ラウンドトリップ (Generalize) → `D4-validation.md` + 再生成 HTML
**このスキルの主ゲート。** D4 が答える問いは1つ:**「この哲学は再利用可能か、それとも 1枚の
モックのスナップショットに過ぎないか」**。哲学ファイルだけを入力に**別ページを再生成**し、同じ
"らしさ"が出るかで判定する。**2つの独立した軸**を混同しないこと。

**軸1 — どの画面で試すか**
- **同型**(同じ画面タイプ・別コンテンツ): 測るのは**再現性**。「この種なら今後も同じ見た目が出る」
  という核心の主張。**必ず通す必要がある**。
- **異型**(別の画面タイプ): 測るのは**汎化の境界**。ここで崩れるのは欠陥ではなく、§0 ルーターの
  得意/不得意を**発見する手段**(LP 由来の哲学が密ダッシュボードで崩れるのは正常)。

**軸2 — 崩れ方(失敗モード)**
- **不足(gap)**: 再生成に要るトークン/規約を哲学が供給できず、ジェネレータが値を**捏造**した
  → **哲学の穴=欠陥**。
- **ずれ(drift)**: 哲学は揃っていたが結果が**別物に見えた**。

この 2×2 で差し戻し先が機械的に決まる:

| | **不足(gap)** | **ずれ(drift)** |
|---|---|---|
| **同型で発生** | 哲学の穴 → **D3/D2 差し戻し** | 過学習 → **D2 で原則を直す** |
| **異型で発生** | ※下記の判別が要る | スコープ外 → **§0 に `unfit` 記録**(正常) |

> **異型での「不足」は2種類ある(判別する / D4 実走で判明)**: 欠けたトークンが
> (a) 哲学の**得意(in-scope)画面に要る**もの → 真の穴 → 差し戻し。
> (b) 哲学が**意図して省略**したもの(§3.省)で、その異型ジャンルだけが要求する → **穴ではない。`unfit`**。
> 例: admin 哲学が省略した largetitle を LP が要求 → (b)。**異型では捏造より忠実遵守を優先**し、
> 足りなければ無理に作らない。忠実に従えば結果は「ジャンル的に壊れた=ずれ」になり、正しく `unfit` へ落ちる
> (捏造して無理に成立させると (a) と誤判定する)。

> **機械チェックは異型の unfit を検出できない(重要 / D4 実走で判明)**: 哲学に忠実な異型は
> `validate.mjs` も `anti-slop.mjs` も **PASS/CLEAN になりうる**(捏造していないので機械的には綺麗)。
> なのにジャンルとしては壊れている。よって**異型の境界判定はルーブリック項目6(親子/ジャンル適合)=
> 人間 or 盲検エージェントが決定打**。機械チェックだけで「異型OK」と判断しない。

#### 循環の罠への防御(必読 — D4 を「哲学の」テストにする条件)
`web-design-mock` は単体で有能(anti-slop / 良い既定値)。普通に再生成すると「**ジェネレータが
上手いだけ**」で哲学の穴が隠れる。よって鉄則:
> 再生成は**哲学ファイル 100% から導出**(Apple/Carbon と全く同じ経路)。**ソースモックの HTML は
> 見ない**(コピー防止)。ジェネレータが捏造せざるを得なかったトークン/規約は**すべて「不足」として
> ログ**し、黙って埋めさせない。

#### サブステップ
- **D4.1 選定**: **同型1枚(必須)+ 異型1枚(既定)**。過学習を厚く炙るなら同型を別コンテンツで
  もう1枚、境界を広く取るなら異型を足す(増減自由)。
- **D4.2 再生成**: 哲学のみを入力に `web-design-mock` の内側パイプライン(§5)を回す。捏造は
  「不足」としてログ。**ここは親スキルの起動を伴う**ので、昇格前にユーザーへ起動を促す(勝手に
  親を走らせない)。
- **D4.3 採点(ルーブリック)**: 再生成 vs ソースを**哲学レベルの属性**で比較(コンテンツ/ピクセル
  一致ではない)。各項目を **再現 / ずれ / 不足** で判定:
  1. **トークン被覆** — 必要トークンを哲学が全供給したか(捏造ゼロ=合格)※半機械的(`validate.mjs`
     + 哲学に無い `:root` 追加の有無)
  2. **余白リズム** — 同じ space スケール / セクションリズムの系列か
  3. **タイポ階調** — hero→body→caption の比率関係が同じか
  4. **奥行きの作り方** — shadow か 素材/層か、戦略が同じか
  5. **accent 規律** — 使われ方(数・配置の作法)が同じか
  6. **親子に見えるか** — 全体として「同じデザインシステム産」と言えるか(ホリスティック)。
     **採点はユーザーゲート**(任意で、ソース/再生成を見ていない独立エージェントに盲検の第二意見を
     取らせてよい — 過学習の自己ごまかし対策)。
- **D4.4 確定**:
  - **昇格条件(ハードゲート)**: 同型で **不足(gap)ゼロ**。穴が1つでもあれば D3/D2 へ差し戻し
    (捏造を含む哲学は昇格させない)。
  - **ずれの扱い**: 軽微なら可・本質的なら差し戻しを**ユーザーが判断**(同型の本質的ずれ=過学習)。
  - **スコープ地図**: 各画面タイプを `validated`(同型再現)/ `partial`(一部ずれ)/ `unfit`(異型で
    崩れ)で §0 メタに記録し続ける(二値にしない)。`validated_screens` には `validated` のみ。
  - 通れば草案を `status: approved` にし、`web-design-mock` のルーターから選べるようにする(§6)。

## 3. 出力テンプレート(哲学リファレンスの形 — 親スキーマと共有)

`references/apple/apple.md` の §0〜§6 を厳守。差分は **front matter と §2 の出所クラス**のみ。

### 3.1 まず「独立」か「派生」かを決める(D1 デルタから判断)
D1 のデルタ計測(§D1)で、トークンの大半が既存の authoritative 哲学と**同値**だった場合、それは
ゼロから組んだ独立哲学ではなく、**既存哲学の variant(派生)**。正直に派生として書く(複製しない =
親スキルの「ポインタであって複製ではない」を継承):

- **独立哲学(standalone)**: 親に依らず `:root` を全量持つ(Apple/Carbon と同格)。
- **派生哲学(variant)**: `extends: <base>` を宣言し、§3 トークンは**デルタ(上書き + 追加 + 省略)だけ**
  を書く。同値トークンは base を参照し再掲しない。§1 原則も「base の原則 + この variant が足す/変える原則」
  の差分で書く。**過学習だけでなく冗長な再掲も防ぐ**(変わっていない所まで書くと base の更新に追従できない)。
  - **「省略」は明示的に書く(重要)**: base にあるが**意図して使わない**トークン(例 `blur-material` /
    `caption2`)を §3 に**ラベル付きで列挙**する。「使わない判断」も哲学の一部(例: blur 不使用 = 奥行きを
    素材でなく面で作る V1 の裏返し)。黙って消すと、後で base マージ時に復活して原則と矛盾する。

### 3.2 front matter
```yaml
---
name: <philosophy-name>
provenance: empirical            # authoritative(Apple/Carbon) と区別する新クラス
kind: standalone                 # standalone | variant
extends:                         # kind: variant のときだけ。例 apple(base リファレンス名)
derived_from: <slug>/output/mock-vN.html
validated_screens: []            # D4 で同型再現を実証できた画面タイプだけ(空=未実証)
screen_scope:                    # D4.4 スコープ地図(二値にしない)
  validated: []                  #   同型再現できた
  partial: []                    #   一部ずれ
  unfit: []                      #   異型で崩れた(=不得意。欠陥ではない)
status: draft                    # draft | approved(D4 で同型・不足ゼロを満たすと approved)
updated_at: <date>
---
```
> **variant のとき §3 トークンブロックはデルタのみ**。最終モック生成時は親パイプラインが
> `base の :root` ← `variant のデルタ` の順でマージして `:root` を組む(D4 再生成もこの経路)。

| 節 | 内容 | 蒸留での扱い |
|---|---|---|
| §0 ルーター用メタ | 得意/不得意な画面タイプ・トーン・本物感の源 | **保守的に**。得意画面は `validated_screens` に同期 |
| §1 原則 | コア原則(数は可変・哲学が決める) | D2 から。各原則 `inferred` + 根拠 |
| §2 トークンの出所 | provenance 表 | **実測(mock由来) / 推論** の2区分で全トークンを分類 |
| §3 デザイントークン(`:root`) | 正規化した抽出トークン | 値は逐語。命名のみ親スキーマへ寄せる。**variant はデルタのみ(§3.1)** |
| §4 レイアウト規約 | グリッド/余白リズム/タイポ/奥行き/a11y | D1 観測から。各規約に `inferred` と出典 |
| §5 look を決める数個の決定 | 保存後の報告事項 | accent/階層/背景/タイポの要点 |
| §6 範囲限定ハイブリッド注意 | 名前空間トークン規律 | 親と同文 |

## 4. 昇格先と置き場所の規約

```
<workspace>/
└── web-design-mock/
    ├── <slug>/
    │   ├── output/mock-vN.html        # 蒸留のソース(地の真実)
    │   └── distill/                    # ← 本スキルの作業状態
    │       ├── 00-distill-state.md     # 薄い baton: 現フェーズ/ゲート状況/唯一の next-action
    │       ├── D1-measure.md
    │       ├── D2-principles.md
    │       ├── D4-validation.md
    │       └── output/regen-<screen>.html   # D4 の再生成物
    └── _philosophies/                  # ← 昇格した empirical 哲学(配布物を汚さない)
        └── <name>/
            └── <name>.md               # references/<name>/<name>.md と同形
```

- **`_philosophies/` は underscore 前頭**でプロジェクト slug と区別(「プロジェクトではない」signal)。
- スキル本体 `references/` には**直書きしない**(authoritative 哲学の棚を empirical で汚さない)。
- 共有/除外は任意。スキルは自動で `.gitignore` を書き換えない。

`00-distill-state.md` は親の `00-state.md` と同じ薄さ(現フェーズ・各ゲート状況・唯一の next-action・
各ファイルへのポインタのみ)。どのセッションも最初にこれを読む。

## 5. `web-design-mock` への接続(フィードバックループ)

蒸留哲学を親スキルが**選べる**ようにするのが最終目的。最小接続点:

1. 親 SKILL.md §3 ルーターに「**ユーザー哲学(`_philosophies/`, provenance: empirical)も発見・候補に含める**」一文を足す。
2. 親 §5 パイプライン「哲学を選ぶ」で empirical 哲学を許可。選択時は `provenance` と
   `validated_screens` を**表示してユーザーに舵を渡す**(権威の出自を隠さない)。
