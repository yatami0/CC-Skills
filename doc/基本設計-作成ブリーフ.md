## 3. このブリーフが伝える「統合済みの認識」（会話で確定した内容）

新セッションは下記を所与として設計書に織り込む。

### 3.1 全体アーキの骨格
- **`contracts/` が全システム間インターフェースの正（一次情報）**。FE↔BE の HTTP は **OpenAPI**、BE↔外部システムのファイル連携は **JSON Schema**。`contracts/` は OpenAPI 専用ではない。
- **codegen は契約→コードの一方向**（コードから契約を生成しない。AI に契約を直接編集させない＝ADR-0002/0009）。
- FE は **TS 世界**（React monorepo・@core 基盤）、BE は **Java 世界**（Spring Boot・サービス縦割り）。両世界とも契約から生成し、生成物の手書き改変を禁止。
- **正しさを散文でなく機械ゲートに寄せる**（型/lint/dependency-cruiser/ArchUnit/codegen:check/contract test）。

### 3.2 検証項目 V-1〜V-5 と FE/BE の住処
PoC 親設計 §1 の検証項目を、FE-native / BE-native で分類する。

| V | 項目 | 住処 | PoC 実証状況 |
|---|---|---|---|
| V-1 | 契約→双方向codegen破壊 | FE(TS)＋**BE(Java)** | TS側のみ実証済。**Java側（双方向）は BE フェーズ** |
| V-2 | 越境・改変の機械検知 | FE中心（＋BEはArchUnit） | FE側実証済（ESLint/depcruise/codegen:check） |
| V-3 | モックによる並行開発 | FE | **経路結合まで実証済**。画面(render→DOM)結合は V-5 で完成 |
| V-4 | CSV契約の機械検証 | **BE(Java)** | **TS試作→revert済・BEフェーズへ**（`v-4-見送り判断.md`） |
| V-5 | メタ定義駆動UI | FE | 未実装。**React/Next/ui-engine をここで導入** |

### 3.3 フェーズ・ロードマップ
- **FE フェーズ（現在・TS-only PoC）**: V-1(TS)/V-2/V-3 実証済。**V-5 を実装すると FE-native（V-1,2,3,5）が出揃い、かつ V-5 で React/Next/ui-engine を導入して V-3 が真の画面結合へ昇格・テストランナーも本決め → FE 一旦完了**。
- **BE フェーズ（次）**: **V-4（CSV契約・Java DTO＋バリデータ・batch 出力前照合）**＋**V-1 の Java 側（双方向 codegen）**＋**ArchUnit（Java レイヤ・生成IF implements 強制）**＋**双方向 contract test（モックと本物 BE が同一契約に従う／Pact・schema 突合）**。
- **本番化軸（別軸・親設計 §9）**: 認可スタブ→本番スキーマ、固定JWT→Cognito、ローカル batch→StepFunctions/CronJob。

### 3.4 V-4 をどう書くか（重要・誤解防止）
- ファイル連携（CSV）は **BE↔外部システムの責務**。FE は最小バリデーション（拡張子・サイズ）＋ API を叩くのみ。
- V-4 を TS(ajv)で組んでも、本番の Java ツールチェーンとは別物＝「検証」にならない。**①全体には「検証計画上 V-4 は BE で実施」、③BE に V-4 の具体設計**を置く。FE 設計書(②)に V-4 は書かない。
- 持ち越す気づき（③へ）: 「契約→生成→I/O境界で機械照合＋codegen:checkでドリフト検知」は HTTP でもファイルでも同型／取込・出力は同一バリデータ／ファイルメタも契約に同居。

## 4. 各ドキュメントの骨子（見出し＋各節の要点）

新セッションはこの構成で起こす。各節は「出典のどこから引くか」を併記してあるので統合に徹すること。

### ① 全体基本設計書（`00-全体.md`）
1. **目的とスコープ** — 契約駆動の実システム全体。FE+BE を貫く設計を定義（PoC は検証エビデンス）。
2. **設計思想** — 契約駆動・モノレポ戦略・状態責務分離・不要useEffect排除・層で基準を分ける配置・正しさを機械に寄せる（出典: steering/00）。
3. **全体アーキテクチャ** — `contracts/`（正）→ codegen → FE(TS世界)/BE(Java世界)。構成図（PoC 親設計 §2.1 を本番版に一般化）。
4. **契約（一次情報）** — `contracts/http`(OpenAPI)・`contracts/files`(JSON Schema)・`contracts/shared`。一方向 codegen・design-first・AIに契約を直接編集させない（出典: steering/02・親設計 §6・ADR-0002/0009）。
5. **システム間インターフェース** — FE↔BE=HTTP(同期API)／BE↔外部=ファイル(CSV配布)。エラー型(共通ErrorResponse・6コード)・ページング・相関ID。
6. **機械ゲート（横断）** — 型(tsc)/ESLint/dependency-cruiser/ArchUnit/codegen:check/contract test/VRT。どの規約をどのゲートで落とすか一覧（出典: steering/05・親設計 ci/）。
7. **横断的関心事** — 認証(Cognito/JWT)・認可(BE Service層・ADR-0008)・エラー正規化(common-web)・i18n・ログ/監視。
8. **検証計画 V-1〜V-5** — §3.2 の表をベースに、各 V の合格基準と達成状況（PoC エビデンスへのリンク）。
9. **ロードマップ** — §3.3（FE フェーズ→BE フェーズ→本番化軸）。
10. **ADR・制約一覧** — ADR-0001〜0012 と「やってはいけないこと」（出典: steering/00 §やってはいけない・親設計 §7.2）。

### ② FE 基本設計書（`10-FE.md`）
1. **目的とスコープ** — FE = React 19 + TS monorepo（`@app`/`@app-admin`/`@app-ext`/`@shared`/`@core`）。
2. **アプリ構成と依存方向** — pnpm workspace・アプリ間直接import禁止・@shared/@coreへの昇格基準（出典: steering/01）。
3. **配置規約** — @core=Atomic Design（atoms〜templates）/ アプリ層=ページコロケーション（pages/XxxPage/{components,dialogs,hooks}）。アプリ直下に components/dialogs/hooks を置かない（出典: steering/01）。
4. **状態管理とフック責務** — Jotai・store集約・useXxxState(読)/useXxxAction(書)/useXxxDrawer/useXxxRedirect・useSemaphoreCallback/withAppLoading（出典: steering/06・doc/jotai_patterns・state_boundaries）。
5. **API 消費** — 生成 api-client 経由のみ（生fetch禁止）・Zod実行時検証・ケース変換・ApiError（出典: steering/02・doc/api_client_migration）。
6. **React 絶対ルール** — 純粋性・Rules of Hooks・useEffect 禁止用途（react-you-might-not-need-an-effect 全ルール error）（出典: steering/03）。
7. **契約消費フロー** — OpenAPI→codegen(型/client/MSW)。モックによる並行開発（V-3。examples を源泉・手書きしない）。
8. **メタ定義駆動UI（V-5）** — ui-engine：メタ定義（項目/型/必須/コード値）でマスタ画面を1コードで描画。RHF+Zod フォーム（出典: 親設計 §6.3・doc/rhf_patterns）。
9. **機械ゲート（FE）** — tsc(strict)/ESLint(命名/import順/no-raw-fetch)/dependency-cruiser(層・生成物直参照)/codegen:check/Vitest/Playwright/Storybook+reg-suit VRT（出典: steering/04,05・doc/storybook_msw,testing_output）。
10. **検証と残作業** — V-1/V-2/V-3 実証済（PoC リンク）。**V-5 未実装**。V-3 の画面結合昇格・ランナー本決めは V-5 とセット。

### ③ BE 基本設計書（`20-BE.md`）
1. **目的とスコープ** — BE = Spring Boot・サービス縦割り（master api/batch、libs-java common-web）（出典: 親設計 §2.1/§2.2/§3）。
2. **サービス構成と依存** — `services/master/{api,batch,db}`・`libs-java/common-web`。サービス間直接依存なし・横断資産に業務ロジックを置かない（ADR-0001）。
3. **レイヤと責務** — Controller(生成IF implements・JWT検証・400/401) → Service(業務チェック・**認可**・トランザクション) → Mapper。認可は Service 層のみ（ADR-0008）。
4. **契約消費（双方向 codegen）** — OpenAPI→Java interface/model（**V-1 の Java 側**：契約改変で Controller がコンパイルエラー）。JSON Schema→Java DTO＋バリデータ。生成物手書き改変禁止。
5. **ファイル連携（V-4）** — 配布CSV を batch が出力。**出力直前に生成バリデータで契約照合（契約外は異常終了＋件数ログ）**。ファイルメタ（文字コード/区切り/ヘッダ/改行）も契約由来。取込/出力で同一バリデータ。バッチ共通枠（冪等・0件正常終了・処理時間ログ・ADR-0011）（出典: 親設計 §4.3/§5.4/§6.2・v-4-見送り判断.md §3）。
6. **認証・認可** — JWT 署名/期限検証→クレーム解決→Service で マスタID×CRUD 認可照合→監査ログ。スタブ認可（モデル未確定）→本番スキーマ差し替え（出典: 親設計 §5.3・ADR-0008）。
7. **エラー処理** — common-web が例外→6コード＋ErrorResponse 正規化・相関IDログ（出典: 親設計 §3・error-standards）。
8. **機械ゲート（BE）** — **ArchUnit（レイヤ依存・生成IF implements 強制）**・codegen:check（生成物ドリフト）・**双方向 contract test（モックと本物 BE が同一契約／Pact・schema 突合）**（出典: 親設計 §2.2 ci/・§9）。
9. **本番化** — 固定JWT→Cognito、ローカルbatch→StepFunctions/CronJob、スタブ認可→本番（親設計 §9）。
10. **検証** — V-4＋V-1 の Java 側＋双方向保証。FE フェーズで TS のみ実証した部分の Java 側を埋める位置づけ。

## 5. 守る制約・トーン（設計書の書き方）

- **出典に忠実**。値（マスタ名・エラーコード・認可モデル）はダミー/未確定を明記（親設計 §7 の前提表に倣う）。FE 単独都合で契約・型を歪めない。
- **散文でなく機械ゲートで担保する思想**を貫く（規約は「どのゲートが落とすか」とセットで書く）。
- **未確定は「前提の明示」として残す**（ランタイム契約検証=ADR-0012 は Proposed のまま等）。勝手に確定させない。
- 図は mermaid。表で「規約↔強制手段↔タイミング」を示すと PoC ドキュメントと一貫する。
