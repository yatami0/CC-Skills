# Skills ガイド

このリポジトリでは、繰り返し使う作業手順や専門知識を Claude Code の Skill として蓄積していく。
このドキュメントは Skill の仕組みと使い方、新しく追加する手順をまとめた正本。

## なぜ Skill をためるのか

Claude に毎回同じ前提や規約、手順を口頭で説明するのは無駄が多く、説明のたびに内容がぶれる。
Skill はこのリポジトリ特有のやり方を 1 ファイルに固定し、必要なときだけ Claude の文脈に
読み込ませる仕組み。次の効果がある。

- 再現性。誰がいつ実行しても同じ品質の手順が走る。
- 文脈の節約。常時プロンプトに含めず、関連する作業のときだけ読み込まれる。
- 資産化。一度作った手順がリポジトリに残り、レビューや改善の対象になる。

口頭指示やその場のプロンプトと違い、Skill はコードと一緒にバージョン管理される。
チームの暗黙知を形式知として積み上げられる。

## 仕組み

### 配置とスコープ

```
.claude/skills/
└── <skill-name>/
    └── SKILL.md        # 1スキル = 1ディレクトリ = 1 SKILL.md
```

- `.claude/skills/` に置いた Skill はこのリポジトリ内でのみ有効（プロジェクトスコープ）。
- 個人の全プロジェクトで使いたいものは `~/.claude/skills/`（ユーザースコープ）に置く。
- このリポジトリで蓄積するのは原則プロジェクトスコープ（`.claude/skills/`）。

### SKILL.md の構造

先頭の YAML フロントマターと本文（Markdown）で構成する。

```markdown
---
name: skill-name
description: 何をするか + いつ使うか。Claude はこの一文だけを見て発火を判断する。
---

# 本文
Claude に読ませる手順・規約・知識。
```

- `name` は kebab-case で、ディレクトリ名と一致させる。スラッシュ起動名にもなる。
- `description` が最重要。Claude は会話の文脈とこの description を照合し、この Skill を
  使うべきか判断する。何をするかと、いつ使うか（トリガー語）を具体的に書くこと。
  曖昧だと発火しない、または誤発火する。

### 読み込まれるタイミング

- 自動発火。ユーザーの依頼が description のトリガーに合致すると、Claude が自律的に呼ぶ。
- 明示起動。ユーザーが `/skill-name` と打つか、"〇〇スキルを使って" と指示する。

本文は呼ばれて初めて文脈に入る（常駐しない）ので、長めの手順を書いてもセッションの
コンテキストを圧迫しない。

## 使い方

- 自動で使う場合は、関連する作業を依頼するだけ。たとえば "メール作成用の Claude Project を
  設定したい" と頼めば `project-blueprint` が起動する。
- 明示的に呼ぶ場合は、`/project-blueprint` のように Skill 名を直接打つ。
- 発火しないときは、description のトリガー語が依頼文と噛み合っていない可能性が高い。
  description を調整する（[メンテナンス](#メンテナンス)参照）。

## 新しい Skill を追加する手順

1. ディレクトリと SKILL.md を作る
   ```
   .claude/skills/<skill-name>/SKILL.md
   ```
   `name` とディレクトリ名を一致させる。

2. フロントマターを書く
   - `name`: kebab-case。
   - `description`: 何をするかと、いつ使うか（具体的なトリガー語）。
     一般語だけにしない。例の良し悪し:
     - ✕ `description: コードを手伝う`
     - ◯ `description: このモノレポの ESLint 規約に沿って差分をレビューする。"レビューして" "lint 違反を直して" 等で使う`

3. 本文を書く。下記の [本文の推奨セクション](#本文の推奨セクション) を満たす。

4. カタログに登録する。[カタログ](#カタログ) の表に 1 行追加。

5. 動作確認する。新しいセッションで `/skill-name` で起動するか、トリガー語を含む依頼で
   自動発火するかを確認。

### 本文の推奨セクション

Skill 本文は Claude への指示書。次を含めると品質が安定する。

- When this applies / 適用範囲。いつ使い、いつ使わないか。1回きりの作業なら使わない、など。
- Procedure / 手順。番号付きの実行ステップ。途中で確認を取る箇所を明示。
- Output / 成果物。何を、どの形式で出すか。
- Conventions / 規約。このリポジトリ固有の制約。パスや命名、既存文書への準拠など。
- 必要なら Reference。手本となる既存ファイルへのリンク。

## メンテナンス

- description は育てる。発火しない、または誤発火するたびにトリガー語を調整する。
- 手順は修正のたびに追記する。Claude の出力を直したら、その修正を Skill 本文のルールに反映する。
  口頭で直し続けるのではなく Skill に蓄積するのが、このリポジトリの方針。
- 重複を避ける。新しい Skill を作る前に、既存 Skill の拡張で済まないか確認する。
- 1 Skill は 1 目的。何でも屋の Skill は精度が落ちる。ワークフロー単位で分割する。

## 設計方針（このリポジトリの規約）

- 蓄積先は `.claude/skills/`（プロジェクトスコープ）を基本とする。
- カタログ（[カタログ](#カタログ)）を単一の索引とし、Skill 追加時の更新を必須とする。
- 命名は kebab-case、ディレクトリ名 = `name`。
- ユーザーの言語に合わせて応答する Skill は、その旨を本文に明記する（このリポジトリは
  日本語でのやり取りが主）。
